# OpenMousse server

[中文](README.zh-CN.md) · **English**

Thin API layer (FastAPI): auth, chat relayed to your claw (OpenClaw's Gateway, or any OpenAI-compatible API, see [Other claws](#other-claws)), Agent creation and deletion, board data, attachments and voice, push notifications, and hosting of the web build.

## Install

The one-line installer at the repository root (`install.sh`) does all of the below, including the systemd service. By hand:

```bash
cd ~/openmousse/server
pip install -r requirements.txt
mkdir -p ~/.openmousse && cp server.example.json ~/.openmousse/server.json   # edit paths and timezone
python3 tokens.py add phone      # generate an access token for the app's connection page
python3 run.py                   # or install as a systemd service, see openmousse-server.service.example
```

To try it on a Mac (or any machine) without changing much: `MOUSSE_TRIAL=1 bash install.sh` (or `bash install.sh --trial`). It uses the built-in engine, listens on `127.0.0.1` only, doesn't ask about public HTTPS and doesn't touch OpenClaw. A login service is optional: without one it starts the server once in the background. At the end it says where the web version is (`http://127.0.0.1:8080`) and how a phone connects (Tailscale, or the same Wi-Fi with `MOUSSE_BIND`). On macOS the installer looks for Homebrew's Python 3.11+ (the system one is 3.9), installs git through `xcode-select --install`, and runs the services under launchd. Every run records what it put on the machine (services, symlinks, folders, edited files, a background process and how to stop it) in `~/.openmousse/install-manifest.json`, which uninstalling follows. On a machine that already has a real install, the trial changes nothing and exits.

Every field of `server.json` is documented at the top of [`config.py`](config.py). Changing tokens or adding Agents needs no restart; changing the bind address does. With the built-in engine (no OpenClaw: `bash install.sh` and answer `builtin`), pick models, web search and memory with `python3 setup_ctl.py` in a terminal on the server (see [Choosing models, search and memory](#choosing-models-search-and-memory-built-in-engine)). `python3 settings_ctl.py user-name <name>` sets what prompts to the model call you (`user_name`, no restart) and records it as one line in the profile USER.md; the main chat runs it while showing a new user around.

## Docker

`docker compose -f docker/compose.yaml up -d --build` from the repository root runs the server with the built-in engine in one container, with everything that changes in the `/data` volume ([`docs/docker.md`](../docs/docker.md)). The first start writes `/data/server.json` (claw `builtin`, random tokens, name / language / timezone from `MOUSSE_NAME`, `MOUSSE_LANG`, `MOUSSE_TZ`), creates the memory tree and prints a pairing link for `MOUSSE_PUBLIC_URL`. Later starts leave it alone. The port is published on the host's `127.0.0.1` only, and phones come in through the host's Tailscale. The container has no Docker sandbox and no Claude Code / Codex CLI. `MOUSSE_INSTALL=docker` tells `mousse update` to ask for a new image instead.

## Operations: `mousse doctor`, backups, updates, config, audit and cleanup

Day-to-day upkeep from a terminal on the server ([`ops/`](ops/), one module per command; `bin/mousse` runs them, link it with `ln -s ~/.openmousse/repo/bin/mousse ~/.local/bin/mousse`). They work with the server stopped, never print tokens or keys, and never read, store or pass on a subscription token: whether Claude Code or Codex is signed in is asked of their own commands, as [`engine/runners.py`](engine/runners.py) does.

- **`mousse doctor [--json] [--fix] [--yes] [--strict]`** ([`ops/doctor.py`](ops/doctor.py)): a health check, section by section, each item ✓ / ! / ✗ / · with one line and how to fix it. System (Python 3.11+, `requirements.txt`, free disk, Docker for the sandbox), install (`~/.openmousse/repo`, the venv, `mousse` on PATH), `server.json` and its `claw`, every layer from the setup overview (models, search, memory, embeddings, connections, hands), sign-ins (Claude Code, Codex, the ChatGPT plan), data (permissions of the data folder, `secrets.env`, `server.json`, the ChatGPT plan's folder and the memory tree's config; SQLite `quick_check`; the memory search FTS index; expired pairing codes), the memory tree, services (systemd / launchd, the nightly digest, `/api/health` and whether the running code matches the repository) and the last update check. `--fix` does only safe, reversible repairs: tighten permissions (0600 / 0700), create missing folders, recreate the `~/.openmousse/repo` link, rebuild the FTS index (the text stays), drop expired pairing codes (`server.json` is backed up first, as `server.json.bak-<time>`); each repaired item is checked again. Anything that stops or restarts a service also needs `--yes` (and waits for replies in progress, like `safe_restart.py`); without it you get the command. `--json` follows OpenClaw's health contract: every item has `id`, `section`, `status` (`ok` / `warn` / `error` / `info`), `title`, `detail`, `fix`, `fixable`, `needsYes`, `fixed`, `note`. Exit code 0 without ✗ (`--strict`: without ! either), otherwise 1. `check.sh` stays for when the venv itself is broken: it only needs the system's python3.
- **`mousse status [--json]`** ([`ops/status.py`](ops/status.py)): one screen: is the server up, version and commit (and whether it runs older code than the repository), the claw, the main chat's model, today's turns and spend, scheduled jobs, cards waiting in the inbox, and whether a newer version is out (only what the last `mousse update --check` saved: no network). Exit code 1 when the server isn't answering.
- **`mousse logs [-f] [-n 200] [--since 1h] [--grep WORD] [--unit server|daily-close|tree]`** ([`ops/logs.py`](ops/logs.py)): Linux with systemd reads `journalctl --user -u openmousse-server`; macOS and hand-started servers read `~/.openmousse/logs/<name>.log` (those lines carry no time, so `--since` only works with journalctl). Every line goes through the engine's scrub plus this machine's real tokens and keys before it's printed.

- **`mousse backup create [--out FILE|FOLDER] [--no-secrets] [--no-workspace] [--no-tree] [--keep N]`**, **`mousse backup verify FILE`**, **`mousse backup list`**, **`mousse restore FILE [--dry-run] [--yes]`** ([`ops/backup.py`](ops/backup.py)): one `openmousse-backup-<date-time>.tar.gz` (0600) in `backups/` next to `server.json` by default; `--keep` keeps the newest N (5). It holds `server.json`, `secrets.env`, the whole data folder (SQLite databases are copied live with sqlite3's `backup()`, never the file being written; `-wal`, `-shm`, locks and logs stay out), `db` / `uploads` if `server.json` puts them elsewhere, the memory tree's home (and its Markdown notes folder if that lives outside), and every Agent's workspace (links are recorded, not followed). `--no-secrets` leaves out `secrets.env` and the key files in the data folder (`chatgpt/`, `apps/`, `sentinel/`, `gateway-device.json`, `social/identity.json`); `server.json` still holds your access tokens, so keep every archive as safe as a key. `manifest.json` records the format, time, version, commit, whether keys are in, where each part lived (paths under your home are stored as `~/…`, so another machine or user name works) and every file's size, sha256 and mode. `verify` checks one root folder, regular files only, no absolute or `..` paths, every listed file with the right size and sha256 and nothing extra, and `PRAGMA quick_check` on each database. `restore` verifies first and writes nothing if that fails, snapshots the current state as `openmousse-snapshot-pre-restore-<time>.tar.gz` (undo with `mousse restore <snapshot>`), refuses while the server runs unless `--yes` (then it stops it, and the memory tree service if the tree is restored, and starts them again; exit code 2 otherwise), extracts to a staging folder, checks every hash again and swaps files in one by one, removing a database's old `-wal` / `-shm` first. Files that aren't in the archive are left alone, and nothing is written through a link that leads out of its folder. `mousse update` takes its snapshot the same way.

- **`mousse update [--check] [--plan] [--channel stable|main] [--yes] [--stash]`** ([`ops/update.py`](ops/update.py)): two channels: `stable` = the remote's newest `v<VERSION>` tag (made at each release, see [`version.py`](version.py)), `main` = the remote's `main`. A `--channel` you pick is remembered in `server.json` as `update.channel` (default `stable`); `update.remote` (default `origin`) and `update.wait` (seconds to wait for the server to answer, default 90) are optional. It stops and says why (exit code 2) when it can't update: a Docker install (`MOUSSE_INSTALL=docker`: pull the new image and recreate the container), not a git checkout (rerun the installer), uncommitted changes (`--stash` puts them in `git stash`), or a commit outside the channel's history (another development branch: no forced switch). Being ahead of the channel is not an update; it never goes backwards. The installer's shallow clone gets its history first. `--check` fetches, compares and saves the result for `mousse status` and `doctor` (which never go online); `--plan` lists the commits, dependency changes and services it would restart, and changes nothing. A real update asks in a terminal (or takes `--yes`): snapshot (as `mousse backup`), check out the target, install `server/requirements.txt` and `./tree` with the venv's python, `python -m compileall -q server` (fails → back to the old commit, dependencies reinstalled), restart the services once replies in progress finish (without a service manager it prints the command instead), wait for `/api/health`, and roll back (old commit, dependencies, restart) if it doesn't answer. Every step is logged in `update/logs/update-<time>.log` next to `server.json` (scrubbed), the last receipt in `update/last.json`. No automatic updates and no background checks; it never changes `VERSION` or makes tags. `safe_restart.py` now restarts through launchd on a Mac too.

- **`mousse config validate [--json] [--file PATH]`**, **`config get DOTTED.PATH`**, **`config set DOTTED.PATH JSON-VALUE`**, **`config unset DOTTED.PATH`** ([`ops/confcheck.py`](ops/confcheck.py)): the whole of `server.json` against a table of known keys (types and allowed values, from the top of [`config.py`](config.py), [`engine/models.py`](engine/models.py) and the engine modules; top-level keys and the main `engine` keys so far). An unknown key is only a warning, never an error: other work adds keys all the time, and a newer config must still start an older version. Wrong types and out-of-range values are errors (exit code 1). `get` masks anything key-like (`auth.tokens` entirely) and never shows `secrets.env`. `set` reads the file fresh (a broken one is never overwritten), changes a copy, validates the whole result and writes nothing if it fails, backs up (`server.json.bak-<time>`) and writes atomically; a value that isn't JSON is taken as a string (`mousse config set engine.model moonshot/kimi-k3`). Keys and tokens are refused there: API keys go into `secrets.env` with `setup_ctl.py add`, access tokens with `tokens.py`. `mousse doctor` reports the result as `config.valid`, and `setup_ctl.py` mentions any errors after it writes (it still writes as before).

- **`mousse security audit [--json] [--fix]`** ([`ops/audit.py`](ops/audit.py)): a cold check of the config and files, after OpenClaw's audit: every finding has an id, a severity (✗ critical, ! warn, · info), what the danger is and how to change it. It covers the permissions of `secrets.env`, `server.json`, the data folder, the ChatGPT plan's credentials, connector tokens (`data/apps`), Doorman's keys (`data/sentinel`), the device and friend identity keys, the memory tree's config and the backups; keys written right in `server.json` (a provider's `key`, the claw's `token`, MCP `env` values that aren't `${NAME}`); access tokens that are too short or shared (a program token equal to a person's is critical: its holder could use `/api`); `auth.trust_loopback`; listening on anything other than loopback or Tailscale (`0.0.0.0` is critical); Funnel exposing `/api` or the whole server (only when the `tailscale` command exists; the installer's `/t`, `/m`, `/s`, `/f` are fine); `engine.api` letting callers approve; `security: full` in `engine.host_exec`; `engine.tools.levels` set to `auto` for things that needed your OK; MCP write tools on `auto`; the ChatGPT plan allowed in the background; a sandbox network that bypasses Doorman (`host` is critical); expired pairing codes. `--fix` only tightens permissions and drops expired pairing codes (backing up `server.json` first). Exit code 1 while anything critical is left.

- **`mousse sessions cleanup [--older-than 90d] [--agent ID] [--dry-run] [--yes] [--no-vacuum] [--json]`** ([`ops/sessions.py`](ops/sessions.py)): removes the built-in engine's old session transcripts (what the model saw: `engine_sessions` and their `engine_entries`) last touched more than `--older-than` ago (default 90 days; `1d` at least, `12w`, `6m`, `1y` work too), then runs `VACUUM`. The app's chat history, the activity page, usage and spend, memory, the memory tree and workspaces aren't touched. It never removes today's sessions, ones with a turn still running, an inbox card waiting for your OK, a background task not finished or not yet delivered, a scheduled job running, or (while writeback is on) owner sessions from the last 3 days that haven't been written back to memory yet; they're counted by reason. API session rows whose transcripts are all gone go too, unless an approval result is waiting for them. It lists what it would do first (`--dry-run` stops there) and asks unless `--yes` (no terminal and no `--yes`: refused, exit code 2); the removal checks everything again inside one write transaction. `VACUUM` waits up to a minute for a running turn and is skipped with a note if the server stays busy. No tables are created or changed.

- **`mousse owner migrate [--to owner] [--apply] [--db PATH] [--json]`** ([`ops/owner.py`](ops/owner.py), 2026-10-20): the schedule, goals, projects and meal-log tables record what you changed yourself under one id, `owner_id` in `server.json`. A new install writes `"owner"`; without the key it is `"leo"`, the value older installs have always used, so an existing install doesn't change by a byte. Both values (and whatever `owner_id` says) count as you when read, in the server and in the app, so nothing has to be migrated. This command only exists to leave one value in the database: by default it lists which table, which column and how many rows would change; `--apply` checks that `server.json` still validates with `owner_id` set, backs up the database (into `backup_dir`, default `<data_dir>/backups/`) and `server.json`, replaces the values in one transaction, writes `owner_id`, and sweeps once more. `--to leo` goes back. The before / after snapshots in the change logs and memory tree leaves are left alone. Nothing runs it automatically.

- **`mousse diagnostics [--out FILE.zip|FOLDER] [--print] [--lines 2000]`** ([`ops/diagnostics.py`](ops/diagnostics.py)): a zip (0600) for whoever helps with a problem, in `diagnostics/` next to `server.json` by default (`--print` prints the documents instead). It holds what `doctor`, `status`, `security audit` and `config validate` report (checks only, nothing repaired); the shape of `server.json` (every key, but only safe values such as model references, the claw kind, language, time zone, switches and numbers; other strings become markers like `<str:12>`, `<url>`, `<set>`, and `auth.tokens` keeps only the names); the engine's models, fallbacks, aliases, whether each has a key, and cooldowns; each SQLite file's size, `quick_check` and rows per table; the last 7 days of usage, summed; the last update check; and signals from the last log lines (counts by `[module]` and level, HTTP status classes, error types and the code lines they came from). No log line is copied, since lines can hold bits of conversations. Conversations, messages, memory, keys, tokens and email addresses are never included: every document is scrubbed (key-like strings and this machine's real tokens and keys), emails become `<email>`, the home folder and user name in paths become `~`, and a last check over the whole bundle leaves out any document that still holds a real token, key or email.

- **`mousse uninstall [--full] [--keep-tree] [--no-backup] [--backup-to DIR] [--dry-run] [--yes] [--json]`** ([`ops/uninstall.py`](ops/uninstall.py)): by default it only removes what runs and keeps all data: the services (systemd units stopped, disabled and deleted, then `daemon-reload`; launchd agents booted out and their plists deleted; hand-started servers stopped), the crontab lines that run the nightly digest (nothing else in crontab), and the links (`~/.openmousse/repo`, `~/.local/bin/mousse`, the workspaces' `skills/` links into the repository). `--full` also deletes `~/.openmousse`, the memory tree's home (unless `--keep-tree`) and the installer's copy of the repository (`~/openmousse`) if it has no uncommitted, stashed or unpushed work. It warns first with every path and size, backs up first (like `mousse backup create`, into your home folder or `--backup-to`, never inside what gets deleted; `--no-backup` skips it; a failed backup means nothing is deleted) and asks you to type `delete`. It never deletes anything outside your home or without `mousse` in its path, and never touches your Obsidian vault, OpenClaw's own settings and rules (it says what's left there) or Tailscale (it prints the commands to turn off `/t`, `/m`, `/s`, `/f`). `~/.openmousse/install-manifest.json`, if an installer wrote one, is followed too (`services`, `links`, `paths`, `repo`, `cron`, `funnel`), under the same guard. A Docker install is removed with Docker instead.

Service manager detection matches the installer (systemd only when `/run/systemd/system` exists); `MOUSSE_SERVICE_MANAGER=systemd|launchd|none` overrides it.

## Auth

`/api/*` requires `Authorization: Bearer <token>` (`X-API-Key` also works; `?token=` only on GET for files: `/api/files/…`, Think attachments and saved originals, podcast audio — for image views and the web build's `<audio>`, which can't send headers). No credentials → 401. Two token-free doors are off by default: `auth.tailscale_nodes` (a whitelist of Tailscale device names; needs tailscale on this machine) and `auth.trust_loopback` (never enable it when a reverse proxy runs on the same host). The web build's static files are public. The `mcp` and `mcp-<agent id>` tokens only work on `/mcp` (403 on `/api`, so a claw holding only that token can't approve its own inbox cards or pair devices), `sentinel` only on `/api/egress`, and `api` / `api-<agent id>` only on `/v1` (the built-in engine's OpenAI-compatible API and its ACP adapter, off unless `engine.api` is set; see [`engine/openai_api.py`](engine/openai_api.py) and [`engine/acp.py`](engine/acp.py)); local scripts (`*_ctl.py`, `safe_restart.py`, `check.sh`) use the first token that isn't one of those, whatever the order in `server.json`.

## Letting the phone connect

- **Tailscale** (least effort): bind the service to the Tailscale address, install Tailscale on the phone, enter `http://100.x.x.x:8080` in the app.
- **Pairing code** (no token to copy): `python3 tokens.py pair` makes a one-time code ([`pairing.py`](pairing.py): 10 minutes, one use, only its hash is stored, too many wrong tries lock it for 10 minutes), draws a QR code in the terminal and prints an `openmousse://pair?s=<address>&c=<code>` link. Scan it with the phone's camera or tap the link → the app's connect page has the address and code filled in → **Connect with code** → `POST /api/pair` hands the app a new token of its own (`device-<device>-<time>`, removable with `tokens.py remove`). `--json` is for claws (see [`docs/connect.md`](../docs/connect.md)). `/api/pair` is under `/api`, so only on the Tailscale network. The installer makes one at the end (30 minutes).
- **Devices** (app: Settings → your claw): `GET /api/devices` lists the tokens people use (names only; program tokens like `mcp`, `mcp-<id>` and `sentinel` are left out), `DELETE /api/devices/{name}` revokes one (not the one making the request), and `POST /api/pair/new` `{server, name}` makes a pairing code for another device from an app that's already connected (link + QR as an SVG path, same rules as `tokens.py pair`).
- **Public HTTPS**: `tailscale serve` / `tailscale funnel`, or Caddy / nginx reverse-proxying to 127.0.0.1:8080; enter `https://your.domain` in the app.

## Devices as nodes (built-in engine)

A node is one of your own devices doing for an Agent what the server can't: run a command or take a screenshot on your Mac, read and write the folders you share from it, show a notification, get the phone's location or take a photo with it. Modelled on OpenClaw's nodes (device pairing, then a separately approved command surface), but over long polling: the node always connects out to the server, nothing listens on the Mac or the phone. See [`nodes.py`](nodes.py).

- **Off by default.** It needs the built-in engine and `"nodes": {}` under `engine` in `server.json`; without it every `/api/nodes/*` answers 404 and no Agent gets the `nodes` tool. `engine.nodes.agents` lists the Agents that get the tool (default `["main"]`).
- **Pairing a computer**: `python3 tokens.py pair --node` (or **Add a computer** under Settings → Hardware → Devices and nodes, `POST /api/nodes/pair`) makes a one-time code (10 minutes, once) and prints the command to run on that computer. The node host trades it for a `node-<device>` token (`POST /api/pair` with `"node": true`; a phone's code and a node's code never cross). That token only works on `/api/nodes/*` (403 elsewhere: a computer holding it can't read your chats or approve anything), isn't listed as a device, and local scripts never pick it.
- **Approving what it can do**: when a node connects (`POST /api/nodes/hello`) it reports its platform, commands, system permissions and shared folders. The server sends an inbox card (kind `node`); only once you approve it can Agents use those commands (`engine.nodes.<node>.approved`). If it later reports more, only the new ones get a card; the already approved ones keep working meanwhile. A declined set isn't asked about again for 30 days; the node's page in the app can approve it directly. The phone is different: the app uses its own device token, and turning a capability on in the app is the approval, so there's no card.
- **Private commands stay off**: running commands, writing files, screenshots, photos, location and controlling the computer stay off even after you approve the surface. Turn each on per node: `engine.nodes.<node>.allow` = `{"<command>": "off" | "ask" | "allow"}` (`ask` = an approval card every time, `allow` = straight away). For `system.run`, `allow` means commands on that node's allowlist (`engine.nodes.<node>.exec`) run straight away and the rest ask; risky ones always ask. `computer.act` goes up to `ask`. Other approved commands (notifications, listing and reading shared folders, finding a program) default to `allow` and can be set to `off`. The app sets these with `POST /api/nodes/{id}/allow {command, level}`.
- **Talking to a node**: the node long-polls `GET /api/nodes/poll?wait=20` and gets `{invokes: [{id, command, params, timeoutMs}], cancel: [...]}`; it answers with `POST /api/nodes/result {id, ok, payload | error: {code, message}}` and says `POST /api/nodes/bye {reason}` when it leaves (the phone going to the background, the node host stopping). The server never waits on a node that isn't there: offline, the phone app not in the foreground, a command not reported, not approved or off all fail at once with a stable code (`NODE_OFFLINE`, `NODE_BACKGROUND_UNAVAILABLE`, `NODE_COMMAND_NOT_APPROVED`, `NODE_COMMAND_OFF`…). A node that drops off after taking a job fails it with `NODE_LOST`; a timeout or a stopped turn sends `cancel` on the next poll.
- **Managing them** (your own devices only): `GET /api/nodes`, `GET /api/nodes/{id}`, `POST /api/nodes/{id}/allow`, `POST /api/nodes/{id}/approve` and `DELETE /api/nodes/{id}`, which forgets the node, its approvals and levels and revokes a computer's `node-…` token.
- **The `nodes` tool** ([`engine/nodes.py`](engine/nodes.py)), only in your own turns and only for `engine.nodes.agents` (outsider turns stay tool-free, cyber turns don't get it; scheduled jobs and heartbeats that run in their own session, `mousse agent` and background sub-agents don't get it either): `list`, `describe`, `notify`, `camera_snap`, `location_get`, `screen_snapshot`, `run`, `which`, `file_list`, `file_read`, `file_write`, `computer`. `run` follows the node's allowlist like `host_exec`: on it → runs; off it → two cards (just this once / always allow, which adds the exact command to `engine.nodes.<node>.exec`); risky (the same `danger()` check) → asks every time, never "always". Writing files, photos, screenshots and location follow the level you set: `allow` runs, `ask` sends a card. Even at `allow`, nothing on a node runs directly unless you started the turn in the chat: in a turn started by a schedule, a heartbeat, a trigger, a workflow, the API, or the one that carries on after you approve a card, the `allow` actions (commands on the list, reading and writing files, notifications, photos, screenshots, location) are refused; `ask` still sends a card. For photos and screenshots, approving the card allows the same call once within 10 minutes, so the picture lands in the turn that asked for it. `computer` always asks. A phone notification goes out as a push, so it works with the app in the background. What a node sends back (command output, file contents, its error messages) is wrapped as outside data, and a node's own name keeps only letters, digits, spaces and `.'-` (the tool's description lists ids only); pictures go to the image store and the session keeps a reference. `engine.tools.levels.nodes = "off"` removes the tool.

```json
"engine": {"nodes": {"agents": ["main"],
                     "node-mac-mini": {"approved": ["system.notify", "system.run", "fs.list", "fs.read"],
                                       "allow": {"system.run": "allow"}, "exec": ["/usr/bin/uname", "git status ..."]}}}
```

- **The Mac (or Linux) node host** ([`node_host.py`](node_host.py)): one file, standard library only, runs on the `python3` that comes with macOS (3.9); copy it to the computer, or use `mousse node …` where OpenMousse is installed. `pair '<link>'` stores the token in `~/.openmousse-node/node.json` (0600), `run` works in the foreground, `install` / `uninstall` set it up to start with your login (macOS launchd `ai.openmousse.node`, Linux systemd user unit `openmousse-node.service`; `loginctl enable-linger` keeps it running while you're logged out), `status` shows what it offers and whether the server answers. It reconnects with backoff, stops cleanly (exit 0) when its token is revoked, and says `bye` when it stops. What it offers is up to its own `~/.openmousse-node/config.json`, a second gate that the server's approval doesn't bypass (like OpenClaw's node-local exec approvals):

  ```json
  {"allow": ["/usr/bin/uname ...", "git status"],
   "folders": {"Documents": "~/Documents", "Code": {"path": "~/code", "write": true}},
   "notify": true, "screen": false, "computer": false}
  ```

  `system.run` only for commands on `allow` (same pattern syntax as `host_exec`; paths are matched as resolved on that computer), without a shell, with key-like environment variables removed, a time limit, head-and-tail output and the whole process group stopped on timeout or cancel. `fs.list` / `fs.read` / `fs.write` only inside `folders` (paths start with the folder's name; no `..`, symbolic links aren't followed, key-like files such as `.env` or `.ssh` are off-limits; writing only where `write` is true, and never to a script `allow` runs or the subfolder it sits in, so an Agent can't rewrite a listed script and then run it. Don't list tools that read files from the current folder, such as `make`, `npm`, `pytest` or `python3 …`, for a writable folder: those files aren't recognised). `screen.snapshot` with `screencapture -x` on macOS (needs Screen Recording permission for that Python) or `grim` / `gnome-screenshot` / `scrot` / `import` on Linux; `system.notify` with `osascript` (title and text passed as arguments, never pasted into the script) or `notify-send`. `computer.act` (macOS only, needs `computer` and `screen` both on, plus Accessibility permission for the program running the node host: Terminal when you run it yourself, that `python3` for the service): click, double-click, right-click, move, scroll, press keys (`cmd+s`, `enter`, `pagedown`…) and type. Mouse and key events are CoreGraphics events posted through `osascript`'s JavaScript, with the coordinates passed as arguments; typing goes through the clipboard (`pbcopy` and ⌘V, then the clipboard's previous text is put back). `x` / `y` are pixels in the latest screenshot of screen 0 taken in the last 10 minutes, converted to screen points as measured when that screenshot was taken; without one it answers `COMPUTER_NEEDS_SCREENSHOT`, and without Accessibility `PERMISSION_MISSING`. Every action is an approval card on the server. Edits to the file are picked up without a restart.

- **The phone as a node** (the app, Settings → Hardware → This phone; location needs app 1.0.7 for expo-location): three items, all off until you turn one on, each explained before it's enabled. Location (foreground permission only, no background location; "Allow" or "Ask each time", every read listed on the page), photos (each request opens a full-screen camera view on the phone and nothing is taken until you tap), notifications (sent by push, so they arrive with the app in the background). The app uses its own device token, long-polls only while it's in the foreground and says `bye` when it goes to the background, so Agents get `NODE_BACKGROUND_UNAVAILABLE` at once. Settings → Hardware → Devices and nodes lists every node, approves what's waiting, sets each level, removes a node and pairs a computer.

## Other claws

By default the server talks to OpenClaw. For any other claw or agent with an OpenAI-compatible chat API, add a `claw` section to `server.json` (the installer writes it when you give it a URL instead of pressing Enter at "your claw"):

```json
"claw": {"kind": "openai", "name": "My claw", "url": "http://127.0.0.1:8642/v1", "token": "…", "model": "default"}
```

- `url` goes up to `/v1`; the server POSTs to `<url>/chat/completions` with `stream: true` (a plain JSON reply works too) and checks `<url>/models` on the Connections page. `token` (or `token_env`, a variable name looked up in the environment and in `env_file`) is sent as a Bearer token. `models` lists what the app may switch between; `headers` adds headers your claw needs.
- `session` says how a conversation continues: `{"mode": "history", "turns": 40}` (default) sends today's messages of that conversation every time, for APIs with no sessions of their own (a model's API, say); unsending just drops messages here. Claws that keep sessions get only the new message and a session key: `{"mode": "header", "header": "X-Session-Id"}`, `{"mode": "body", "field": "session_id"}` or `{"mode": "user"}`. The key is `mousse:<conversation>:<day>`, a new one every day at 04:00 (most claws never reset on their own; the daily digest carries yesterday over); `"daily": false` keeps `mousse:<conversation>`. `"model": ""` leaves `model` out of the request.
- Presets ([`claw_presets.py`](claw_presets.py)), which the installer fills in when you answer with the name: **Hermes Agent** (`hermes`: port 8642, `X-Hermes-Session-Id`, the token read from `API_SERVER_KEY` in `~/.hermes/.env`, skills in `~/.hermes/skills`), **nanobot** (`nanobot`: port 8900, `session_id` in the body, no `model`), **Letta Code** (`letta`: port 4500, `x-letta-chat-key`, the agent's name as `model`).
- Not yet: claws without an OpenAI-compatible chat API (ZeroClaw's webhook, Moltis's RPC, NullClaw's A2A, PicoClaw's WebSocket, Agent Zero, NanoClaw, TinyAGI) and IronClaw's Responses API need a driver of their own.
- Agents: each Agent is a conversation of its own with the same claw. Its first message of the day carries its name and role, and the last daily digest.
- Daily digest: at 03:45 `daily_close.py` asks each conversation that talked today for 5–10 lines on the day; the server keeps the reply in `<data_dir>/digest/<conversation>/<day>.md` and puts it in front of the next day's first message.
- Skills and rules: give the installer your claw's skills folder and the rules file it reads every turn (AGENTS.md or similar), and OpenMousse's skills are linked in and a short rules section appended. Skills run `python3 ~/.openmousse/repo/server/…_ctl.py`, so your claw needs a shell tool to use them. A claw that can connect to MCP doesn't need that: it can use `/mcp` instead (see "MCP" below).
- `/api/health` reports `claw: {kind, name, caps}`; the app hides what the claw can't do: cutting into a running reply, background tasks, exec approvals, OpenClaw scheduled jobs, model billing, per-Agent workspaces. Those endpoints answer with empty lists instead of calling `openclaw`.

## MCP: the features without a shell

The server has an MCP endpoint at `/mcp` (Streamable HTTP, stateless, [`mcp_bridge.py`](mcp_bridge.py)) through which a claw uses boards, the inbox, goals, projects, the schedule, Agents, the background-task allowance, nightly proposals, the journal, handing off to an Agent, what to call the user, the memory tree and pages. Sandboxed Agents, Hermes on a docker or ssh terminal backend, and claws hosted in the cloud can't run the skills' commands; they can use this.

- Address: `http://<server>/mcp/<token>` (token in the path), or `/mcp` with `Authorization: Bearer <token>`. The token is the one named `mcp` under `auth.tokens` in `server.json` (the installer creates it; `python3 tokens.py add mcp` works too); `/mcp` accepts no other token. A token named `mcp-<agent id>` is bound to that Agent and can only act for it.
- Host check (against DNS rebinding): `/mcp` only answers requests whose `Host` is this machine (`127.0.0.1`, `localhost`, `[::1]`, any port), the address in `bind`, the host of `share.public_url`, or one listed in `mcp.allowed_hosts` (`["desk.example:8080", "https://mcp.example.com"]`; read on every request, no restart). Anything else gets 421, and a browser `Origin` that doesn't match gets 403. A claw on another machine that reaches a wildcard bind (`0.0.0.0`) by its Tailscale address or name, or a reverse proxy that passes the public `Host` through, needs that host in the list.
- Tools: each one bridges an existing command, written exactly as in the skills: `args` = the words after the script name (one word per item, no shell, no quoting), `input` = what would go to standard input, `agent` = which Agent you are (the command runs in its workspace and boards and the inbox know it's that Agent; Agents of other claws, which have no workspace, are recognised too). Each call starts a subprocess (about 0.1 s), at most 4 at a time, 120 s at most (handoff: 300 s).
- OpenClaw: the installer adds `openmousse` under `mcp.servers` in `openclaw.json` (the Gateway hot-reloads it, no restart); the tools are named like `openmousse__board`. The skills' commands still work; both paths exist side by side and each skill says to prefer the tools when they're there.
- Other claws: the installer prints the address and how to add it to that claw (Hermes's `mcp_servers`, nanobot's `tools.mcpServers`, Letta Code's `/mcp add`). An Agent's note carries its id, to put in `agent`.
- `mcp.scripts` in `server.json` replaces or adds the command behind a tool (`{"journal": ["python3", "~/…/my_journal.py"]}`; `null` = don't offer it); restart the server after changing it.
- The tools of the apps you connect (see [Connectors](#connectors-apps-over-mcp)) are listed after these, named `<app id>__<tool>`; connecting, removing or changing a permission needs no restart.
- With the built-in engine, `/mcp` also accepts short-lived tokens the engine gives the user's own logged-in Claude Code or Codex for one turn or one background task (kept in memory only, revoked when it ends, never in `server.json`). Such a token sees that Agent's engine tools (`claude-code/…` models, background-task helpers) through the engine's own approval gate, not the tools above. See [`engine/mcp_engine.py`](engine/mcp_engine.py) and [`engine/claude_brain.py`](engine/claude_brain.py).
- Context per turn: the 11 tool definitions come to about 7,500 characters, about the same as the 11 skill descriptions.
- Scripts started through `/mcp` carry `X-Mousse-Via: mcp` back to the server (`MOUSSE_VIA` in their environment), so a handoff or trigger an outside MCP client starts never runs on your ChatGPT plan (see below).

## Your ChatGPT plan (built-in engine)

With the built-in engine, `chatgpt/<model>` runs on your own ChatGPT Plus / Pro plan through OpenAI's [Sign in with ChatGPT](https://developers.openai.com/siwc/token-sharing-open-source) flow for open-source and local apps, and the public Responses API (`https://api.openai.com/v1/responses`). See [`engine/chatgpt_plan.py`](engine/chatgpt_plan.py).

- Connecting: `POST /api/engine/chatgpt/login` starts a sign-in and returns the authorization `url`. The server listens on `http://127.0.0.1:<port>/auth/callback` first. Open the link in any browser and approve. On the server itself (or through `ssh -N -L <port>:127.0.0.1:<port> …`, the `tunnel` field) the browser lands on that listener and you're done. On a phone that page doesn't load: copy the whole address from the address bar and send it with `POST /api/engine/chatgpt/callback {"url": "…"}`. The code exchange, the PKCE verifier and the tokens stay on the server.
- Status: `GET /api/engine/chatgpt` (also `chatgpt` in `/api/engine/status`) says whether it's connected, which plan, your email, whether the token expires soon, the last error and the background setting. It never returns tokens. `POST /api/engine/chatgpt/disconnect` revokes the session and clears the tokens. Only one account is connected at a time: connecting another one revokes the old one.
- Tokens live only in `<data_dir>/chatgpt/` on this server (folder 0700, files 0600, written atomically). They're refreshed before they expire, one refresh at a time. A rejected token is refreshed once; if it's still rejected, the status asks you to connect again.
- Models: `chatgpt/<slug>` from your account's catalog appear in the app once you're connected and allowed plan use. `engine.chatgpt.models` in `server.json` picks them instead; `"chatgpt": false` turns it all off.
- Who may use it: only your own turns, and one-shot calls you start yourself (see the Claude plan section below). Cyber chats, friends and other agents (card agent, A2A, Doorman), the OpenAI-compatible `/v1` and ACP, anything started through `/mcp`, and one-shot calls nobody reported as yours use a model with an API key instead. Background tasks, scheduled jobs and heartbeats use the plan only after you allow it once: `PUT /api/engine/chatgpt/background {"allow": true}` (the time is recorded).
- A plain OpenAI API key can use the Responses API too: `"providers": {"openai": {"api": "openai-responses"}}` under `engine`. Providers without `api` keep using `/chat/completions`.

## Your Grok subscription (built-in engine)

With the built-in engine, `grok/<model>` runs on your own SuperGrok / X Premium+ subscription, with no API key and no pay-as-you-go. This isn't an integration xAI has named or supports: xAI's announcements name the third-party agents that can sign in with a subscription (Hermes, OpenClaw, OpenCode, Kilo Code, Warp), and OpenMousse isn't one of them. It borrows the OAuth device-code sign-in those agents share (the consent page may say "Grok Build"), and xAI may refuse it (403) at any time; if it does, use an API key instead (see below). The server calls xAI's public API (`https://api.x.ai/v1`, the Responses API) with your token. See [`engine/grok_plan.py`](engine/grok_plan.py).

- Signing in: run `python3 setup_ctl.py grok login` on the server. It prints a link and a code; open the link on your phone or computer, check the code and approve, and the terminal finishes by itself. The app or a script can do the same with `POST /api/engine/grok/login` (returns `url`, `code`, `expiresAt`), `GET /api/engine/grok/login` (progress) and `DELETE /api/engine/grok/login` (cancel). No callback page and no SSH tunnel: the server polls xAI until you approve.
- Tokens live only in `<data_dir>/grok/` on this server (folder 0700, files 0600, written atomically). They never go into logs, URLs or answers to the app. They're refreshed before they expire (a sixth of their lifetime, between 2 minutes and an hour), one refresh at a time. `python3 setup_ctl.py grok logout` or `POST /api/engine/grok/logout` revokes the sign-in at xAI and deletes the local copy; if xAI doesn't confirm the revocation, the answer says to revoke it at [accounts.x.ai](https://accounts.x.ai).
- Status: `python3 setup_ctl.py grok`, `GET /api/engine/grok` (also `grok` in `/api/engine/status`): signed in or not, the email, whether the token expires soon, whether it needs signing in again, whether xAI refused the account, the last error, the background setting, the models and this period's allowance. Never tokens. These endpoints only answer your own devices (scripts with `X-Mousse-Via` get 403).
- When xAI says no: this sign-in isn't one xAI supports for OpenMousse, xAI decides which accounts and apps can use it, and some SuperGrok accounts get 403. The sign-in then ends as refused and says so; signing in again won't help. Use an API key instead: get one at [console.x.ai](https://console.x.ai), save it as `XAI_API_KEY` (Settings → Models → xAI) and pick an `xai/<model>` model (pay as you go; API credit is billed separately from the subscription). A 403 on one thing only (search, images, speech…) says the subscription may not include it, and nothing else is turned off.
- Other errors: an expired or revoked sign-in is refreshed once; if it's still rejected, the status asks you to sign in again. A 429 says this period's allowance may be used up. When xAI can't be reached the old token keeps working while it's valid.
- Models: once you're signed in, the chat models from your account's catalog show up as `grok/<model>` (image, video, speech and multi-agent models aren't listed). `grok/grok-4.7` comes first and is the default pick. They can be chosen for the main chat, background work, writing and one-shot calls, but not for other people's turns. `engine.grok.models` lists them yourself.
- Who may use it: the same rules as the ChatGPT plan. Your own turns and the one-shot calls you start: yes. Background tasks, scheduled jobs and heartbeats: only after you allow it once, separately from ChatGPT: `python3 setup_ctl.py grok background on` or `PUT /api/engine/grok/background {"allow": true}` (the time is recorded). Other people's turns (card agent, A2A, Doorman, cyber chats), the OpenAI-compatible `/v1`, ACP and anything started through `/mcp`: never. They switch to a model with an API key, or don't run and say why.
- Web search: when you're signed in and web search uses the `grok` provider (`engine.web.search.provider = "grok"`), searches go through the subscription first. xAI hasn't said whether search is included in the subscription, so keep an eye on the allowance (below); usage logs these searches with no money. `XAI_API_KEY` is the fallback, used only when the subscription can't be used for that turn (not signed in, needs signing in again, refused by xAI, or a turn that may not spend it); then xAI bills each search tool call plus the model's tokens. A 429 or an outage on the subscription is reported and never quietly switched to pay-as-you-go. Signing in doesn't make `grok` your search provider by itself. `engine.grok.search = false` keeps web search on the API key.
- X search: the `x_search` tool (search public posts on X, read-only; [`engine/xsearch.py`](engine/xsearch.py)) is new and off until you set `engine.web.x_search = true`. By default it doesn't use the subscription: xAI hasn't said whether `x_search` is included, and on the API it's billed at $5 per 1,000 posts and $10 per 1,000 user profiles fetched, plus tokens (xAI's pricing page, 2026-10-10). So it runs on `XAI_API_KEY`, and usage logs each call without a price (the amount fetched isn't known here), so it doesn't count toward spend caps; without a key the tool isn't offered. `engine.grok.x_search = true` (default `false`) lets it go through the subscription first, under the same who-may-use rules; `XAI_API_KEY` is then the fallback. It checks handle and date filters before calling xAI. With subscription tokens xAI sometimes answers without any X posts as sources (from the model's own knowledge); the result then says so.
- Images, video and speech: off by default. Once you're signed in, the purpose settings (`/api/setup/purposes`, the `media` rows) list `grok` for image generation, video generation and speech; or set `engine.use.image = "grok/grok-imagine-image"`, `engine.use.video_gen = "grok/grok-imagine-video"`, `engine.use.tts = {"model": "grok/grok-tts", "voice": "eve"}` ([`engine/grok_media.py`](engine/grok_media.py)). They count against the allowance, are logged in usage with no money and aren't stopped by spend caps. Videos are 1–15 seconds without sound, and each one still asks you first. Voice replies count as background work. xAI has refused speech (403) for some subscription tokens; then pick another provider for it.
- Allowance: `GET /api/setup/usage` has `plans.grok` (plan name, weekly or monthly, how much is used, when it resets); `GET /api/engine/grok/usage` asks xAI right away; `python3 setup_ctl.py grok` and `python3 setup_ctl.py usage` print it. Only the allowance included in the subscription counts: xAI's prepaid API credit is a separate, pay-as-you-go account.
- Settings, under `engine` in `server.json` (all optional, re-read each time): `"grok": false` turns it all off. `"grok": {…}` takes `models` (default: your account's catalog), `route` (`"api"`, the default, or `"proxy"` to send chat through the Grok CLI's subscription proxy `https://cli-chat-proxy.grok.com/v1`), `headers` (extra request headers for chat), `search` (default `true`; `false` = web search uses only `XAI_API_KEY`) and `x_search` (default `false`; `true` = `x_search` goes through the subscription first). `engine.web.x_search`: `true` or `{"model": "…"}` (default off). `engine.use.image` / `video_gen` / `tts`: `grok/<model>` (default unset).

## Other sessions, handing over between Agents, and `mousse agent` (built-in engine)

- **Seeing other sessions** ([`engine/sessions.py`](engine/sessions.py)): three read-only tools in your own turns. `sessions_list` lists sessions: which Agent, conversation and day, the last line, how many turns, whether it's running (newest first; the last 7 days and 20 rows by default). `sessions_history` reads the last messages of one (10 by default, at most 40): only what you and the Agent said, each message cut at 2,000 characters; `include_tools` adds the tool calls. `session_status` says whether one is running, which step it's on and what it's waiting for (approval cards, an `ask_user` answer, queued messages, a handoff that hasn't come back, background tasks), plus the last turn's model and tokens. An Agent sees its own sessions (its chats, its study desk, API conversations, the background tasks it started); the main chat sees every Agent's. In `server.json`: `"engine": {"sessions": {"visibility": "agent" | "self" | "all", "agents": {"fitness": ["main", "diet"]}}}`, where `self` = only the conversation it's in and `agents` overrides the mode for one Agent (`"*"` = all). Cyber and outsider turns never get these tools. What they return starts with an `[Inter-session message] … isUser=false` line, as in OpenClaw, and the content sits in a `<prompt-data>` block the model treats as data, not instructions.
- **Handing over between Agents**: `handoff` (`ask_agent.py`) now works from any Agent, not only the main chat: fitness can hand something to `main`, health to diet. Approval rules and handoff cards stay the same; meetings (`--meet`) are still started by the main chat. The engine tells the script which conversation it hands over from (`MOUSSE_FROM`), so the card records the real source, and the receiving model sees the message marked `[Inter-session message] sourceSession=… sourceAgent=… sourceTool=handoff hop=1/2 isUser=false`: data from another session that carries no approval from you. One message goes at most two hops (`engine.handoff.max_hops`, 1–4), and never back to an Agent in the chain that is waiting for its answer, or to itself. `"handoff": {"agents": false}` under `engine` makes it main-only again. The OpenClaw path is unchanged.
- **`mousse agent`** ([`mousse.py`](mousse.py) → `POST /api/engine/agent`, [`engine/agent_cli.py`](engine/agent_cli.py)): say one thing to an Agent from a terminal or from another coding assistant's session, where you used `openclaw agent` before.

  ```bash
  echo "Is the deploy plan in my notes sound?" | mousse agent --agent main --message-file -
  mousse agent --agent fitness --model chatgpt/gpt-6.1-sol --message-file question.md
  ```

  `bin/mousse` runs `server/mousse.py` (link it into your PATH: `ln -s ~/.openmousse/repo/bin/mousse ~/.local/bin/mousse`). Each call is a fresh session with that Agent's usual background and read-only tools (looking things up works, changes come back "not run", nothing becomes an approval card). It prints one JSON object: `ok`, `status`, `answer`, `model` (with `requested`, and `fallbackFrom` when a backup model answered), `tools` (name, title, status), `used` (manuals, skills, memory leaves), `usage` (input, output and cache tokens, `total`, `cost`, which is `null` on a plan), `conversation`, `turn`, `ms`; or `ok: false` with `code` and `error`. Exit codes: 0 answered, 1 not answered, 2 bad arguments. Without `--model` it uses the model picked for that Agent's chat. `chatgpt/<model>` runs on your own ChatGPT plan: the command line is you, so it counts as your own turn; if the plan isn't connected, plan use isn't allowed, or the request came through `/mcp`, it says so; the model must be in `engine.chatgpt.models` or, without that, your account's catalog. `claude-code/<model>` runs your own signed-in Claude Code. The token is the local scripts' one on the server itself, or an app token with `--token` / `MOUSSE_TOKEN`; `--server` / `MOUSSE_SERVER` points at another machine. The claw must be `builtin`.
- **`mousse chat`** (2026-10-19, [`termchat.py`](termchat.py)): chat with the main chat, or an Agent with `--agent <id>`, from a terminal. Each line goes to that conversation as your own message through `/api/chat/send`, exactly as if you typed it in the app (it shows up there, and queueing and cutting in work the same), and the reply prints as it streams, with one line per tool step (`·` when it starts, `✗` when it fails, `✓ … awaiting your approval` when it became an approval card). `/stop`, or Ctrl-C while a reply runs, stops that reply (what was already said stays); `/quit`, `/exit` or Ctrl-D quits, and quitting mid-reply doesn't stop it. Anything this turn submitted for your OK is listed at the end with a line asking you to confirm it in the app; the terminal never approves. A multiple-choice question from the built-in engine (`ask_user`) can be answered right there (`POST /api/engine/answer`), or skipped with Enter to answer in the app. A dropped stream reattaches through `/api/chat/stream`. Standard library only for the network; token and address as for `mousse agent`. It refuses to run inside an Agent's own command (`MOUSSE_AGENT`).

## Slash commands and conversation basics (built-in engine)

Each item below has its own key in the `engine` section of `server.json`; leaving a key out keeps an existing instance exactly as it was. Built-in engine only: the OpenClaw path is unchanged.

- **Slash commands** (`engine.commands`, [`engine/commands.py`](engine/commands.py)): a message you type yourself in the app that starts with `/name` is handled before it reaches the model. The command and its answer stay in the chat but never enter the model's session; a `/xxx` in anyone else's words (friends, the card agent, channels) is plain text. An unknown name answers that there's no such command. `true` turns them on; `{"off": ["btw", "goal"]}` turns them on without those. `GET /api/engine/commands?thread=` lists them (empty when off); the app's composer shows them as you type `/`.

  | Command | What it does |
  | --- | --- |
  | `/help` (`/commands`) | Lists the commands |
  | `/status` | Whether this chat is running, what it waits for, its model and thinking level, the last turn's tokens |
  | `/usage` | Tokens and cost for this chat today, for today and for the last 7 days |
  | `/context` | How many tokens the opening, the tools and the conversation take, and how far from compacting |
  | `/tools` | The tools this Agent has this turn |
  | `/model [name]` | Shows or switches this chat's model |
  | `/stop` | Stops the reply that's running |
  | `/new [notes]` (`/reset`) | Starts a new session now, opening with where the last one left off (or with your notes) |
  | `/compact [#id] [focus]` (`/compress`) | Compacts the earlier conversation now; a focus keeps its details; `#id` = everything before that message |
  | `/think [level]` (`/thinking`) | Shows or sets this chat's thinking level: `low`, `medium`, `high`, `xhigh`, `max` or `default` |
  | `/queue [mode]` | What a message sent while a reply runs does: `steer` (the default), `followup`, `collect`, `interrupt` |
  | `/btw <question>` (`/side`) | A quick side question about this chat: no tools, not kept in the session, doesn't interrupt |
  | `/bg <what to do>` | Runs it in the background as a task: the chat carries on and the result comes back here (not while the emergency stop is on or a spend cap is reached) |
  | `/resume [n]` | Lists earlier sessions of this chat; `/resume 2` picks one up in a new session |
  | `/export [md\|json\|html] [tools]` | Exports the current session as a file attached to the answer (key-like strings become `***`) |
  | `/goal [goal\|status\|pause\|resume\|stop]` | A standing goal (needs `engine.goal`) |

  `/new`, `/compact` and `/resume` wait until a running reply ends; the others work at any time. Chats run by Claude Code (`claude-code/…`) take the same commands: after `/new`, `/compact`, `/resume` or a fork, the next message starts a new Claude Code session instead of `--resume`. Other modules add commands with `commands.register(Command(...))`, or a per-Agent group (skills) with `commands.add_source(name, fn)`; channels call `commands.handle(conversation, text, who=...)`, which returns `None` for anything that isn't the owner's command.
- **New sessions and the day boundary** (`engine.reset`): `{"at": "04:00", "idle_minutes": 240}`. `at` moves the built-in engine's logical day boundary (default 04:00); `idle_minutes` starts a new session, carrying over where the last one left off, when a chat has been quiet that long (default: never). New sessions keep the key `mousse:<chat>:<day>`, so everything that reads session keys works as before.
- **Compaction** (`engine.compaction`): `"notify": true` leaves a grey line in the chat after an automatic compaction; `"writeback": true` also queues a writeback of the session when writeback is on; `"prune": true` (or `{"keep_turns": 3, "min_chars": 4000, "head": 1500, "tail": 1500}`) trims old text tool results in what goes to the model, a batch at a time, while the stored record stays complete. `POST /api/engine/compact {"thread", "before": "db123", "focus"}` compacts everything before one message.
- **The tool loop** (`engine.loop`): `"parallel": true` (or `{"max": 8}`) runs adjacent read-only calls together: calls that need your OK, change things or interact split the batch, results keep their order, Stop cancels them all, and a tool marked `sequential` never joins. `"guard": true` (or thresholds and `"hard_stop": "unattended" | "always" | "never"`) notices a tool failing over and over or returning the same result: a warning in the result, and a hard stop for turns nobody is watching (scheduled, heartbeat, background). `"spill": true` (or `{"keep_days": 7, "store_max_mb": 512}`) saves a tool result longer than its limit to a file in the data directory and gives your turns a `read_output` tool to page through it. `"resume": true` (or `{"within_minutes": 30}`) picks a turn that a restart cut off back up once, telling the model which calls have no result. Claude Code turns: the guard also checks their `/mcp` calls; batching and paging inside their loop stay with Claude Code, and a resumed turn `--resume`s its session.
- **Thinking level** (`engine.think`): `{"main": "high", "*": "medium"}` sets per-Agent defaults, and `/think` sets one chat (kept with the chat). Your turns send it as the request's effort and Claude Code gets it as `--effort` (ahead of `engine.claude_code.effort`); a level the model doesn't have becomes the nearest lower one it has. Not set: nothing is sent, as before.
- **Earlier sessions, forks and branches**: `GET /api/engine/chats/{thread}/sessions`, `POST …/resume {"session"}`, `POST …/fork {"session"?, "entry"? | "message"?}`, `GET …/branches`, `POST …/branch {"leaf"}`, `GET …/export?format=md|json|html&tools=1` (response shapes at the top of [`engine/history.py`](engine/history.py)). Session titles are the first line; `engine.titles` (`true` or `{"model": "provider/model"}`) has a small model name the ones you list.
- **Standing goals** (`engine.goal`): `true` or `{"max_turns": 20, "max_tokens": 1000000, "judge": "provider/model"}`. After each turn a cheap zero-tool call judges whether the goal is met; if not, the chat gets an automatic "keep going" turn, until it's done, blocked, at a limit or stopped, and your own messages always come first. It keeps running and spending by itself, so it is never on by default. While the emergency stop is on, a goal pauses after the turn instead of judging or carrying on.

## Your Claude plan for one-shot calls (built-in engine)

With the built-in engine, your own one-shot calls can run on the Claude Code you've signed in to on this computer, so they use your Claude Pro / Max plan like your `claude-code/…` chats do. OpenClaw used to keep the plan's token and ran these through its `llm-task`; the built-in engine never reads, stores or passes on a Claude token, so it starts the official `claude` in one-shot mode instead (`claude -p`, `ask` in [`engine/claude_brain.py`](engine/claude_brain.py)).

- What counts: one-shot calls you start yourself: meeting minutes and picking who speaks, the podcast's prep, host questions and summary, study pages, flashcards and course outlines, people notes, forwarding, Zen's "done thinking" draft and meeting speeches, plus the summaries that compact your own long chats. Each caller says where the call came from (`kind` / `origin` in `llmjson.ask` and `owner.stream`); a call that doesn't say counts as someone else's.
- What doesn't: the card agent (friends and A2A), Doorman, other people's turns, cyber chats, the OpenAI-compatible `/v1` and ACP, background tasks and anything started through `/mcp` keep using a model with an API key, the same rule as chats (`models.may_spend`). Nor does anything when the claw isn't the built-in engine: with OpenClaw or another claw, `engine.route` never hands one-shot JSON, writing or summaries to a plan (since 10/20). It picks a pay-as-you-go model (`models.outside()`) or returns nothing, and the caller keeps its own path, such as OpenClaw's `llm-task`, as before 10/19.
- How it runs: one `claude -p` per question, with no tools at all (no built-in tools, no MCP server) and no saved session. Your settings, hooks, plugins, CLAUDE.md and skills aren't loaded, and key-like environment variables are removed, so it can only use its own login. The caller's instructions replace Claude Code's system prompt.
- Setting it up, in the `engine` section of `server.json`: `use.json` for one-shot JSON calls and `use.compact` for summaries. A list adds pay-per-use backups for when the plan call fails (signed out, plan limit reached, or no answer by the timeout, waiting in the queue included). With a backup the plan call gets at most half of the time and the backup the rest (one-shot JSON, one-question answers such as Zen's draft, and summaries alike, since 10/20), so a plan that hangs still leaves time to switch. A summary gives the plan 240 s (120 s with a backup; it used to wait 300 s and then give the backup another 300 s). An instance moved over from OpenClaw, with its chats, one-shot calls and summaries on the plan, and the card agent and Doorman on keys as before (they never use the plan):

```json
"engine": {
  "model": "claude-code/opus",
  "models": ["deepseek/deepseek-flash"],
  "use": {
    "json": ["claude-code/sonnet", "deepseek/deepseek-flash"],
    "compact": ["claude-code/haiku", "deepseek/deepseek-flash"],
    "card": "anthropic/claude-opus-5-5",
    "doorman": "moonshot/kimi-k3"
  }
}
```

- Without a backup a failed plan call says why (signed out, plan limit reached, the command broken, no answer in time, overloaded) and where to switch, and nothing else runs: since 10/20 `llmjson` no longer falls back to its old path after a plan call. That path ran the same plan a second time when the default model is a plan too (and waited a whole timeout again), or quietly used the pay-as-you-go default model. Only backups you wrote down are used (the rest of the `use.json` list, or `engine.fallbacks`); when a backup fails too, the error says both. Calls that don't use a plan keep the old path. Without `use.compact`, summaries use the chat's own model as before; when a plan summary fails it moves on to the rest of the list (or `engine.fallbacks` if it isn't a list), then the chat's own model. Zen's draft and meeting speeches follow the chat's model: `claude-code/…` runs them on the plan. A refusal is never sent to a backup.
- Sharing the machine: one-shot calls count toward `engine.claude_code.max_concurrent` (default 2) like chats, always wait behind chats, and at most `engine.claude_code.max_oneshot` of them run at once (default one less than `max_concurrent`, at least 1), so a batch of background scoring never takes the last slot from your chat. Since 10/20 short one-shot calls (given at most 120 s, waiting included: picking who speaks, the podcast's suggestions, prep and questions, minutes, a summary with a backup) go ahead of long ones (study pages, course outlines) in the queue, and `engine.claude_code.burst` (default `0`: off, as before) lets that many extra `claude` processes start for short calls when the usual slots are taken, so a study page holding the one-shot slot for a quarter of an hour doesn't make a 45 s call time out while it waits. Chats and long calls never use those extra slots; at most `max_concurrent + burst` processes run at once (about 0.3 GB each). Waiting has no separate cap: it already counts toward the call's own timeout (half of it when there's a backup).
- Scripts on this computer (a job scorer, a check script) can ask the same way: `POST /api/engine/oneshot {"prompt": "…", "input": {…}, "required": ["score"]}` with the `local` token returns `{"json": …, "via": …}`. Requests that came through `/mcp` (`X-Mousse-Via: mcp`) don't use the plan.
- Seeing it and switching by hand (feature `setup.purposes.oneshot`): `GET /api/setup/purposes` has a row for one-shot answers (`json`) and one for compaction summaries (`compact`). Every row, the older ones too, says which model your own call really uses now (`effective`; one-shot answers without `use.json` take the old path, which on the built-in engine is the main chat's model, shown as `follows: "chat"`), whose plan that is (`plan`: `claude-code`, `chatgpt`, `codex`, `copilot`…, `null` for pay-as-you-go), whether it can run on this computer right now (`planReady`), whether the purpose may use a plan at all (`mayPlan`), what it switches to when the plan call fails (`backups`, in order: the rest of the `use.<purpose>` list, otherwise the model's own list or `engine.fallbacks`, only ones with a key), and the last plan call that failed and hasn't worked since (`lastFailure`: `at`, `kind` = `auth` / `quota` / `broken` / `timeout` / `error`, from the engine's turn log). Empty `backups` means nothing switches by itself: when the plan has trouble, pick another model in the app (Settings → Models by purpose → One-shot answers) or send `PUT /api/setup/purposes {"json": "provider/model" | "default" | null, "compact": "provider/model" | "default" | null}`. For `json`, `"default"` follows Background and scheduled and `null` removes `use.json`; for `compact` both mean the chat's own model. A plan can be picked (whether a call may use it is still `models.may_spend`'s call); a list keeps its backups when you change its first model. These two rows can be changed only on the built-in engine (409 otherwise; with OpenClaw they're listed and say your claw handles them).
- Changed on 10/20: `PUT /api/setup/purposes {"background": …}` used to set `use.json` to the same model every time. Now it only does that while one-shot answers still follow Background and scheduled: `use.json` unset, `true`, or the same as `use.background`, and not picked on its own in the app (that choice is remembered in `<data_dir>/setup/pins.json`).

## Scheduled jobs that only run a script (built-in engine)

A scheduled job can run a command instead of the model: give `command` instead of `task` ([`engine/jobs.py`](engine/jobs.py)). No model is called, so a check every few minutes costs nothing.

- What can run: a command-line tool from `BRIDGES` in [`bridges.py`](bridges.py) (`board`, `schedule`, …, with the same rules as when that Agent calls it), or a script listed by absolute path under `engine.jobs.scripts` in `server.json`. Arguments are one word each, never go through a shell, and are checked by `bridges.guard` (no reading server files through `--file` and the like). Both are checked again before every run.
- Each run is a subprocess in the Agent's workspace (`MOUSSE_AGENT`; `MOUSSE_VIA=auto`, so whatever it starts counts as background), stopped together with its children after `timeout` seconds (the tool's own limit, or 120 for scripts; at most 600). Exit code 0 is a success. Its output (stdout, plus stderr when there is some) goes to the run log (`GET /api/engine/jobs/{id}` → `runs[].output`), not to a chat: the script decides for itself whether to say something.
- Failures are logged and, unless you ask, not retried: the next run comes at its usual time, the first failure gets one line in the chat, and five in a row pause the job. With `"retry": true` (or a number of retries, 1–5) in `command`, a failed run is retried on the ladder under [Retries](#retries); only do that for scripts that are safe to run twice. These runs don't count toward `engine.jobs.daily_limit`, which caps model runs.
- Who sets them up: you in the app (`POST /api/engine/jobs {"agent", "when", "command"}`, on at once), or an Agent through its `cron` tool. Like every new job, an Agent's stays off until you approve its card, which shows the exact command and its time limit.
- Schedules are the same as for other jobs: `every 5m`, `weekdays 07:30`, `mon,wed 18:00`, cron.

Example: ask once, an hour before practice. Every 5 minutes the script reads the schedule; when something that looks like practice starts within the hour and it hasn't asked about it yet, it asks the main chat to check in through `/api/chat/trigger`. Otherwise it does nothing. List it, then add the job:

```json
"engine": {"jobs": {"scripts": ["/home/me/scripts/practice_check.py"]}}
```

```
POST /api/engine/jobs
{"agent": "main", "name": "Before practice", "when": "every 5m",
 "command": {"script": "/home/me/scripts/practice_check.py", "timeout": 30}}
```

<!-- example: practice_check.py -->
```python
#!/usr/bin/env python3
import json
import os
import re
import urllib.request
from datetime import datetime, timedelta
from pathlib import Path
from zoneinfo import ZoneInfo

conf = json.loads(Path(os.environ.get("MOUSSE_SERVER_CONFIG") or "~/.openmousse/server.json").expanduser().read_text())
bind = conf.get("bind") or {}
host = bind.get("host") if bind.get("host") not in (None, "", "0.0.0.0", "::") else "127.0.0.1"
base = f"http://{host}:{bind.get('port') or 8080}"
token = ((conf.get("auth") or {}).get("tokens") or {}).get("local") or ""
local = urllib.request.build_opener(urllib.request.ProxyHandler({}))
state = Path(__file__).with_name("practice_check.state.json")
practice = re.compile(r"practice|training|训练|练习", re.I)


def api(path, body=None):
    req = urllib.request.Request(base + path, data=None if body is None else json.dumps(body).encode(),
                                 headers={"Authorization": f"Bearer {token}", "Content-Type": "application/json"})
    with local.open(req, timeout=30) as r:
        return json.loads(r.read())


now = datetime.now(ZoneInfo(conf.get("timezone") or "UTC"))
asked = json.loads(state.read_text()) if state.exists() else {}
asked = {k: v for k, v in asked.items() if k.rsplit("@", 1)[-1] >= now.date().isoformat()}
for e in api("/api/schedule?days=2")["events"]:
    if e.get("kind") != "event" or not e.get("start") or e.get("done") or not practice.search(e.get("title") or ""):
        continue
    starts = datetime.fromisoformat(f"{e['date']}T{e['start']}").replace(tzinfo=now.tzinfo)
    key = f"{e['id']}@{e['date']}"
    if timedelta(0) < starts - now <= timedelta(hours=1) and key not in asked:
        if str(conf.get("language") or "en").startswith("zh"):
            text = f"【开练前一小时】{e['start']} 开始「{e['title']}」：问问用户今天状态怎么样，要不要调整强度。"
        else:
            text = f"[An hour before practice] \"{e['title']}\" starts at {e['start']}: ask the user how they feel today and whether to adjust it."
        api("/api/chat/trigger", {"thread": "main", "text": text, "level": "quiet"})
        asked[key] = now.isoformat(timespec="seconds")
        print(f"asked about {e['title']} at {e['start']}")
state.write_text(json.dumps(asked))
```

## Weekly skill review (built-in engine)

Once a week each Agent's own skills are looked at as one set, and you get one inbox card with the suggested changes, one per line ([`engine/skill_review.py`](engine/skill_review.py)). This is separate from `engine.skills.review`, which looks after a turn whether something is worth saving as a new skill.

- Off unless `server.json` says so: `"engine": {"skills": {"weekly": true}}` = every Saturday at 09:00 (the server's time zone), or `{"weekly": {"day": "sun", "hour": 20, "model": "claude-code/opus"}}`. The server checks once an hour. Each Agent is reviewed at most once per ISO week (a review that fails waits for the next week), and this week's card withdraws last week's if you haven't decided it.
- Who: the main chat and each Agent with a `skills/` folder of its own (not a link; Agents working in the sandbox are left out), only the switched-on skills in its own workspace. An Agent with none isn't asked.
- How: one call per Agent with no tools ([`engine/oneshot.py`](engine/oneshot.py)), counted as your own background work (`kind` owner, `origin` auto), so it runs on your plan when `may_spend` allows it (a ChatGPT plan in the background only after you've allowed that). The model: `weekly.model` when given (if this run may not use it there's no review that week; nothing else is tried), otherwise where `engine.use.json` routes, then `engine.use.background`, then `engine.model`. It sees each skill's name, description, when-to-use phrases, the whole SKILL.md (past 120,000 characters in total the longest are cut to their start), its other files, when it was last used and how often in 30 days, its age, and the scheduled jobs and rules files (`AGENTS.md`…) that name it.
- What it may suggest: reword (a new description and when-to-use), merge (one skill rewritten, the others switched off), split (new skills created, the original rewritten), disable. Each comes with a reason; the skills it keeps, and why, are in the card's text. The rules follow OpenClaw's and Hermes' weekly reviews: merge by purpose, never into a catch-all, not being used is no reason to remove a skill, and when unsure keep it. The server checks every suggestion again and drops the ones that break a rule: a skill a job or rules file names is never disabled or merged away, nor is one that another Agent's skills list (`engine.skills.agents`) names while that Agent's `skills/` links to this folder (that one isn't split either), an Agent with a skills list of its own gets no splits (the new skills wouldn't be on its list), one that was never used is not disabled before it's 30 days old (or before the usage records are), one with other files is not merged away, new names must be free, every new SKILL.md passes the format and content checks, a skill is in one change only, and there are at most 12 changes and 2 merges or splits a week.
- The card (kind `skill`, quiet, `itemsKind` `skill-review`, expires after a week): disabling is off by default, the rest on. Submitting does only the approved items; the old app's single approve goes with each default. Each change keeps the previous version first (`skill_manage restore` brings it back), disabling writes `disable-model-invocation: true` and deletes nothing, and the memory gate records the approval. An item whose text was changed on the card, and a merge or split of a skill edited after the review, are skipped. Nothing is posted to the chat; the result is on the card. Revising one item on the card isn't supported yet: reply to the card in the chat, and the Agent makes the change with `skill_manage` (which asks first).

## Channels: Telegram, Discord and email (built-in engine)

Talk to your own Agents from Telegram, Discord or email, and let people you know send messages in through them: [`channels/`](channels/) (the map is in [`channels/__init__.py`](channels/__init__.py)). It only runs when the claw is `builtin` (OpenClaw keeps its own channels, unchanged), and only for what you turn on: no `channels` in `server.json` means nothing starts, and each channel also needs `"enabled": true`. Existing installs stay off until you turn it on.

Who gets which kind of turn:

- **You (the owner).** On Telegram or Discord, the account you claimed with an owner code (or listed under `owners`); by email, a sender in the account's `owners` whose mail passed DMARC (or DKIM aligned with the From domain). What you say goes down the same path as the app (`/api/chat/send`): a private chat lands in the bound Agent's conversation, the same one you see in the app, with the same approvals and records; your own plans can be used, as in the app (`origin` `user`). The reply goes back to the channel. The app keeps the record, but that turn doesn't push a notification: you already have the reply where you asked. While it replies you see "typing…"; an `ask_user` question is sent at once (with buttons for its options on Telegram and Discord); several messages that were merged into one turn get one reply.
- **People you know (contacts).** Paired or listed people with a tier (close / friend / mate) and an Agent they're bound to. Their messages go to your card agent ([`cardagent.py`](cardagent.py)): no tools, only what their tier shows, Doorman reviews what it says, anything that needs your yes or no becomes a `social` card, and each person has a daily limit. It's an outsider turn, so it never runs on your plans.
- **Strangers.** A private message gets a pairing code and nothing else (no model call); you approve it on its inbox card, in the app or with `mousse channels approve`, choosing the tier and Agent. Codes last an hour, each account has at most 3 waiting, and a stranger only hears from the bot once per code. `dm` can also be `allowlist` (only `allow_from`, who become contacts at the account's `tier`) or `ignore`. Email strangers are ignored by default and never get a code.
- **Groups** are off by default. In a group you turn on (`groups.allow`, or `"*"`), the bot answers only when it's @-mentioned, replied to, or called by an Agent's name (`groups.names`, plus the bound Agent's name); other messages are kept (the last `groups.history`, default 30) and shown to the model as quoted data when it is called. Each group (or forum topic) is its own conversation (`ch-…` threads, answered by `main` for now). Other people in a group get your card agent, or nothing when `card.strangers` is off.
- Display names, group titles, forwarded-from, replied-to text, locations and contact cards are marked untrusted and kept in a separate block the model reads as data (`<channel_context>`, `<group_history>`); they're never mixed into the message. Nothing said in a chat can make anyone the owner: only an owner code made on your own device can.

Reliable delivery: every incoming update is stored first (deduplicated by the channel's own id) and only then acknowledged (Telegram's offset, the email watermark); each chat is handled one message at a time, and after a restart the rest are picked up. Outgoing messages queue too: they're split to the channel's length without breaking code blocks, sent in order per chat, retried with backoff (Telegram's `retry_after` is respected), and land in dead letters after 7 tries, where you can see and resend them. Each person also has an hourly cap (`limits`: contacts 30, strangers 5). When batch 4's emergency stop (`engine/estop.py`) is paused, the bot stops answering other people and sending pairing codes; your own messages still go through.

Cards: with `cards: "turn"` (the default), cards from a turn you started in a channel are sent back to that chat, and the card agent's and pairing cards to that account's owner, with Approve / Decline buttons where the channel has them (Telegram, Discord). A click goes through the same path as the app; only your clicks count; replying to a card with a message is "Revise" with that note. `"all"` sends every new card to you, `"none"` sends none. Email can't click: the reply says to look in the app.

Bindings, most specific first: `bindings: [{"account"?, "chat"?, "peer"?, "agent"}]` under a channel (a person beats a chat beats an account; the first one wins a tie), then the Agent set on the contact, then the account's `agent`, then `main`.

```json
"channels": {
  "telegram": {
    "enabled": true,
    "accounts": [{"id": "mousse", "token": "${TELEGRAM_MOUSSE_TOKEN}", "agent": "main",
                  "dm": "pairing", "tier": "friend", "cards": "turn",
                  "groups": {"enabled": false, "allow": [], "require_mention": true, "history": 30, "names": []}}],
    "bindings": [{"chat": "-1001234567890", "agent": "fitness"}]
  }
}
```

Settings (owner's devices only: an app token or one of your Tailscale devices; scripts and `/mcp` get 403). Tokens and passwords only go to `secrets.env`; `server.json` keeps `${NAME}`, the API never returns them, and `server.json` is backed up before each write:

### Telegram

[`channels/telegram.py`](channels/telegram.py) calls the Bot API with `httpx` (no new dependency), by long polling; webhooks need a public address and aren't done yet. Make a bot with @BotFather, save its token in settings (it goes to `secrets.env` as `TELEGRAM_BOT_TOKEN`, or `TELEGRAM_<ACCOUNT>_TOKEN` for a named account), then make an owner code and send `/start <code>` to the bot from your own Telegram account (the `t.me/<bot>?start=<code>` link does it in one tap).

- Only one program can poll a bot token. If something else reads it (another install, another gateway, a webhook), Telegram answers 409: the account pauses, says so in status, and tries again after 30 s, 60 s … up to 10 minutes, without fighting it or deleting the other side's webhook. Give each install its own bot.
- In groups the bot has to be added; for it to see messages that don't call it (names, history), turn off privacy mode with @BotFather's `/setprivacy` or make it an admin. Forum topics are separate conversations.
- Replies are Markdown turned into Telegram's HTML (headings, lists, code blocks, tables as preformatted text), up to 3800 characters a message; if Telegram rejects the formatting, the same text goes again as plain text. "typing…" is refreshed every 4 seconds. `/start` and `/stop` are in the bot's menu; `/stop` stops the reply in progress, like the app's stop button; any other `/command` is sent on as ordinary text.
- Your photos, voice messages and files (up to `max_media_mb`; bots can't download more than 20 MB) are saved to the conversation as if you'd uploaded them in the app. Voice is transcribed with your transcription setting and labeled as a machine transcript, or "[Voice message, not transcribed]" when that fails. Other people's media is only described ("[sent an image, 52 KB, not opened]") and never downloaded.
- Cards come with Approve / Decline buttons (a card with several items says to look in the app instead); only your clicks count. An `ask_user` question gets its options as buttons.

| Key (an account's, or the whole channel's) | Default | |
|---|---|---|
| `token` | — | `${NAME}`; the token itself is in `secrets.env` |
| `owners` | `[]` | Telegram user ids that are you, besides the ones claimed with a code |
| `allow_from` | `[]` | With `"dm": "allowlist"`: user ids that become contacts |
| `poll_timeout` | `25` | Seconds each long poll waits |

### Discord

[`channels/discord.py`](channels/discord.py) uses `aiohttp`, which the server already depends on: the Gateway (a WebSocket) to receive and the REST API to send. In the Developer Portal, create an application with a bot, copy its token into settings (it goes to `secrets.env` as `DISCORD_BOT_TOKEN`, or `DISCORD_<ACCOUNT>_TOKEN`), invite the bot to a server you're in (scopes `bot`; permissions to view channels, send messages and read message history), then send it `/start <code>` in a private message.

- Discord doesn't stop two programs from using the same bot the way Telegram's 409 does, so both would answer: give each install its own bot and don't share one with another gateway.
- It identifies with the Guilds, Guild Messages and Direct Messages intents. That's enough for private messages and for messages that @-mention the bot. To also see other messages in channels (calling an Agent by name, the group history), turn on Message Content Intent on the bot's page in the Developer Portal and set `message_content: true`; if it's on here but not there, Discord refuses the connection (close code 4014) and the status says where to turn it on. A rejected token (4004) also stops with a clear status instead of reconnecting over and over.
- If the connection drops it resumes the session, and Discord sends what was missed. The last event stored is kept with the messages, so after a restart it resumes from there too; once a session has expired (a few minutes), messages sent in between are lost, because Discord doesn't keep them for bots.
- Servers count as groups: off by default, and a server's messages aren't even stored until a channel is in `groups.allow`. There the bot answers when it's @-mentioned (its role counts too), replied to, or called by an Agent's name; threads and forum posts are separate conversations under their channel. Other bots and webhooks are ignored unless `allow_bots` is on.
- Replies keep their Markdown (Discord shows it), up to 1900 characters a message, and never ping anyone: `@everyone` or a mention in a reply stays plain text. Card buttons work like Telegram's; Discord needs an answer within 3 seconds, so a click is acknowledged first and the result comes after, visible only to you.

### Email

[`channels/email.py`](channels/email.py) reads a mailbox over IMAP and answers over SMTP with Python's standard library. Give the Agent a mailbox of its own (a separate account or folder).

- It checks the folder every `poll` seconds (default 60, at least 15) and opens it read-only: nothing is marked read or moved. The first check only notes where the mailbox is (a baseline), so mail that was already there is never handled; if the folder's UIDVALIDITY changes, it takes a new baseline. Each mail's headers are read first, and the body only when the sender is someone it will answer.
- A sender's address only counts when your mail server vouches for it: the first `Authentication-Results` line written by your server (`authserv_id`) has to say `dmarc=pass` for the From domain, or `dkim=pass` with a signing domain aligned with it. No such line, another server's line, or a failure: the mail is treated as a stranger's. Without `authserv_id` nobody is verified, so set it to the name your server writes at the start of that header (look at the raw source of a mail in the mailbox, e.g. `mx.example.org`). The server also has to drop such lines that arrive from outside claiming its name (RFC 8601); mainstream providers do.
- You: a verified sender listed in `owners`. Your mail goes into the bound Agent's conversation as in the app, attachments included (up to `max_media_mb`). The reply is plain text in the same thread (`In-Reply-To`, `References`, `Re:`), marked `Auto-Submitted: auto-replied`. Cards can't be clicked in an email: the reply says how many are waiting in the app.
- Contacts: verified senders you've added (in the app, or `mousse channels contacts`) get the card agent, and each email thread is its own conversation. Strangers are ignored by default (`"dm": "ignore"`; their mail isn't even downloaded); with `"dm": "pairing"` a verified stranger gets a pairing code, and with `"allowlist"` the addresses in `allow_from` become contacts.
- Never answered: auto-replies (`Auto-Submitted`), mailing lists and bulk mail (`List-Id`, `List-Unsubscribe`, `Precedence`), bounces and no-reply addresses, and its own mail coming back. Each address gets at most `replies_per_hour` replies an hour (default 5; you get 60); the rest go to dead letters.
- Quoted earlier mail ("On … wrote:", lines starting with `>`) is cut off; HTML-only mail is turned into text; a charset it doesn't know is decoded with replacement characters. Other people's attachments are only described, never saved.
- It polls; IMAP IDLE isn't done yet. Don't also set the same mailbox up as a mail trigger (`engine.triggers.mail`): the status warns when both read one folder.

### The message tool

With a channel on, your Agents' own turns get a `message` tool ([`channels/tool.py`](channels/tool.py)):

- `to: "owner"` (the default) sends to you on the first channel that knows you (Telegram before email, or the one named in `channel`), right away and without a card, like a push notification. A message from an Agent other than `main` starts with its name.
- `to: "<contact id>"` sends to one of your contacts. That goes out and can't be taken back, so it always makes an approval card first, and the server sends exactly that text, once, when you approve. `action: "contacts"` lists who it can message: everyone for `main`, only the contacts bound to it for other Agents.
- Turn it off with `engine.tools.levels.message: "off"`. Inside the server, `channels.send_to_owner(text, channel=None)` sends you a line the same way (for scheduled jobs and notices; wiring jobs to it comes later).

## Choosing models, search and memory (built-in engine)

`/api/setup/…` ([`engine/setup_api.py`](engine/setup_api.py)) is the API for choosing models, search and memory; [`setup_ctl.py`](setup_ctl.py) runs the same three steps in a terminal (`python3 setup_ctl.py`, or `status`, `models`, `add <id>`, `test <id>`, `use chat <provider/model>`, `search <id>`, `memory sqlite`). Nothing is tied to one vendor: each layer offers a cloud provider with your key, something running on this computer, a tool you're already signed in to, your own address, or nothing.

- Models: the catalog ([`engine/catalog.py`](engine/catalog.py)) lists 24 cloud providers (each base URL checked against the provider's own docs, sources in the file), Ollama, LM Studio, vLLM, llama.cpp, MLX and oMLX on this computer (detected on their default ports), Claude Code / ChatGPT / Grok / Codex you've signed in to here, and any OpenAI-compatible address. Several can be connected at once; each purpose picks its own model: the main chat (`engine.model`), background and scheduled work (`engine.use.background`), writing (`engine.use.writing`: long pieces and documents; with a Gemini key the guide recommends `google/gemini-4-argon`; the skill that writes them comes later), one-shot answers (`engine.use.json`) and compaction summaries (`engine.use.compact`; both in "Your Claude plan for one-shot calls" above), other people's turns (card agent and Doorman, never your plan; the guide recommends them separately from the 2026-10-19 evals: pay-as-you-go `anthropic/claude-opus-5-5` for the card agent, or `moonshot/kimi-k3` without Anthropic connected, and `moonshot/kimi-k3` for Doorman) and embeddings (`engine.recall.embeddings`). With only one connected, it's used automatically.
- Keys you type in the app go to `secrets.env` next to `server.json` (0600, written atomically) and are looked up after the process environment and before `env_file`. They're never sent back: the app only sees whether there is one, where it comes from, its last four characters and when it was saved.
- Nothing is written until you save, and `server.json` is backed up next to itself first (`server.json.bak-<time>`, the last 20 kept). An existing OpenClaw setup is shown as it is and never changed on its own.
- `GET /api/setup/usage` (also `/api/engine/usage`) sums the engine's tokens and cost by day, model and purpose; plan turns count as "plan" with no money. With your Grok subscription signed in, `plans.grok` also shows how much of this period's allowance is used (see "Your Grok subscription"). Each turn is priced as of its own day (`PRICES` / `PRICES_FROM` in [`engine/models.py`](engine/models.py): Gemini 4 Argon goes from $2 / $10 to $4 / $20 per million tokens on 2026-12-01). Embedding calls (indexing, the search query, the settings test) are counted too, in their own `embeddings` section by day, model and kind: tokens as the provider reports them, or estimated from the text length and marked as estimated; money only for models in the price table.

## First run in the app (built-in engine)

When the app connects to a server whose features include `setup` ([`version.py`](version.py)), the claw is `builtin` and `/api/health` says `no_model`, it walks through three steps before the chat: choose a model (a cloud provider with your key, something running on the server, Claude Code / ChatGPT you're signed in to, or your own address; the key is tested before it's saved, then the main chat's model answers one real request), web search, and where memory lives, then a summary. It's the same `/api/setup/…` as `setup_ctl.py`, so only the owner's devices can do it. An install that's already in use only sees it while it has no usable model; other claws (OpenClaw, Hermes, any OpenAI-compatible one) skip it, and servers without `setup` keep the old order (what friends call you, then connecting apps). Every step has Later, remembered on that device. `GET /api/setup/models` also says whether the server is a Mac (`host.mac`, for the Mac-only local runtimes) and gives each region its own key page (`regions[].keyUrl`).

After "You're set" on a new server (features include `naming`, claw `builtin`) comes **Name your assistant**, before what friends call you, and it can be skipped: a name (the current `app_name` to start with), one optional line of character and the look (lens / eclipse / orbit, as on the Look page). It's [`naming.py`](naming.py): `GET` / `PUT /api/naming` `{name?, vibe?}`, owner devices only, built-in engine only (409 otherwise). The name goes into server.json's `app_name` (backed up first) and takes effect at once, without a restart (`/api/health`, "You are …" at the start of each turn). The character becomes one `- **Vibe:** …` line in the main workspace's `IDENTITY.md`, with a version kept first (`engine/versions.py`); a `- **Name:**` line that still has the old name is updated too. Settings → Name and character opens the same page later.

The app's settings home is laid out the same way: Connections (sign-ins, MCP servers, skills, memory, hands), Keys (models, models by purpose, embeddings, search, voice, usage), General (security, appearance) and More (everything else). The numbers come from `GET /api/setup` and `/api/setup/usage`; the Hands page (read-only) reads `layers.hands.agents` (one entry per Agent: files, web pages, search, its own sandbox and browser, host commands) and the host-command allowlists in `/api/security`.

## Moving over from OpenClaw or Hermes (built-in engine)

`mousse migrate openclaw [--openclaw-home ~/.openclaw]` and `mousse migrate hermes [--hermes-home ~/.hermes]` ([`migrate/`](migrate/__init__.py)) read the other agent's home and print a report in three parts: converted, needs you, not converted. Nothing is written. `--out <folder>` also writes `server.patch.json` (what would be merged into server.json), `jobs.json` (the scheduled jobs) and `report.md`. `--apply` writes it, on a `builtin` claw only: server.json is backed up first (`server.json.bak-<time>` next to it) and so is the database (`<backup_dir>/mousse.db.<time>.pre-migrate`), then new keys are added. Keys that already exist and differ are left alone and listed under "needs you", and running `--apply` again creates nothing twice. A copy of the report is kept in `<data_dir>/migrate/`. When `install.sh` sets up the built-in engine (not a trial) and finds `~/.openclaw/openclaw.json` or `~/.hermes/config.yaml`, it asks first, before choosing models: the report comes first, and it only writes when you say yes a second time (Enter = no). With `MOUSSE_NONINTERACTIVE` it only prints the command.

- **The source is read only.** Files are opened read-only and the SQLite databases (`state/openclaw.sqlite`) are copied to a temporary folder and opened read-only there, so not even a `-shm` file appears in the source. Workspaces aren't moved: `workspace` (only while it's still the installer's `~/.openmousse/workspace`) and `agent_workspaces` point at OpenClaw's, and OpenClaw's other Agents get a row in the app's Agent list. Don't run both against the same workspace at once.
- **Keys:** only the variable names are recorded; the values stay in the source's `.env` and `env_file` points there. `--copy-secrets` copies them into `secrets.env` (0600). Sign-in tokens (Claude setup-tokens, ChatGPT / Codex OAuth) are never copied: sign in to Claude Code on the server, or Continue with ChatGPT in the app.
- **Models:** a model that ran on your Claude plan (OpenClaw's `auth.order.anthropic` starts with a subscription profile; Hermes has only a plan token) becomes `claude-code/<model>` when Claude Code is signed in on this machine, and otherwise stays `anthropic/<model>`, billed per use, with a line in the report. Models from a Codex / ChatGPT sign-in become `chatgpt/<model>` in `engine.chatgpt.models`. Fallbacks only keep pay-as-you-go models. The card agent, Doorman and one-shot JSON aren't chosen for you. With `--apply`, chats set to `anthropic/…` switch to `claude-code/…` in the same case.
- **Scheduled jobs** become kernel jobs ([`engine/jobs.py`](engine/jobs.py)) and all arrive paused and unapproved: `mousse migrate on` lists them, `mousse migrate on <id>` turns one on. Command jobs are kept only when the command is one of the command-line tools or in `engine.jobs.scripts`. Heartbeats arrive with `every: "0"`, and the report says which value turns them back on.
- **Host commands:** OpenClaw runs them without approval by default; here they stay off. Only spelled-out allowlist entries become `engine.host_exec.agents.<id>.allow`, never `security: full`. That holds even when Hermes's `approvals.mode` was `off`.
- **Hermes files:** `SOUL.md` is copied only when there isn't one. New `memories/` entries (separated by a `§` line) are appended to `MEMORY.md` / `USER.md`, a version is kept first, and entries already there are left alone. Skills pass [`skill_write.guard`](engine/skill_write.py) and arrive off (`disable-model-invocation: true`, `migrated-from: hermes`): `mousse migrate on skill:<name>` turns one on after you've read it. Each profile becomes an Agent with its own workspace.

## More hands: patches, processes, media and browsers (built-in engine)

Everything here is off until you turn it on in the `engine` section of `server.json`; an instance that doesn't write these keys behaves exactly as before. Tools only exist in your own turns (never in cyber or other people's turns), and what they bring back from outside (pages, files, picture or video descriptions) is marked as data, not instructions.

- **Patches** ([`engine/patch.py`](engine/patch.py)): `"files": {"patch": true}` gives Agents with file tools `apply_patch`: one `*** Begin Patch … *** End Patch` that adds, updates, renames and deletes several files in the Agent's workspace, all or nothing (OpenClaw's format; whitespace and curly-quote drift tolerated). Same path guard as `write_file`, and every file keeps its old version first, so `restore_file` undoes each one. Touching a rules file (AGENTS.md, skills/…) or deleting a file over 10 MB (no old version can be kept) asks you first.
- **Host commands through a shell** ([`engine/host_exec.py`](engine/host_exec.py)): `"host_exec": {"agents": {"main": {"shell": true, …}}}` sends the whole command to `bash -c`, so pipes, redirects, `&&` and `$VAR` work. Every part is still checked: the whole line against the risky-command patterns, then each piece of a pipeline or list, each `$( )` / backquote / `<( )`, every redirect target (outside the workspace, secrets and allowlisted scripts are risky), `cd` targets, `eval` / `source`, `LD_*` / `PATH` assignments, and `… | sh`. Commands after `if` / `then` / `while` / `do` / `!` / `{` are checked like any other; `case` / `for` / `select` / `function` / `[[` / `((` always count as risky (what follows them isn't a plain command). The allowlist is matched against the whole command (a plain one-part command still matches word by word); anything else asks, as before. Without `shell` nothing changes.
- **Background host commands** ([`engine/host_process.py`](engine/host_process.py)): `"background": true` in the same block lets `host_exec` take `background` (start and return an id) or `yield_ms` (move to the background if it isn't done by then), with `watch` for "tell me when this line shows up"; the new `host_process` tool lists, polls, pages the log, writes to standard input and kills an Agent's own background commands. Output goes to `<data_dir>/engine/processes/`; `max_background` (default 4) and `background_timeout` (default 3600 s) cap them. When one ends, a line and the result's last part go into the chat it was started from (the model then replies, as with background tasks; `"notify": false` turns that off). A restart stops them and says so in that chat. Not available in scheduled runs, heartbeats or background tasks.

- **Viewing images** ([`engine/vision.py`](engine/vision.py)): `"use": {"vision": "google/gemini-3.5-flash-lite"}` (any model that sees images; an object `{"model": …, "prompt": …, "max_tokens": …}` works too) does two things. (1) Agents get `view_image`: one image from the workspace, a stored screenshot path, an attachment of this chat (its path or id) or a public URL (public internet only, like `web_fetch`), plus a question. A main model that sees images gets the picture itself in the result (free); one that doesn't gets the vision model's answer. (2) A main model that can't see images (DeepSeek, or one that refused images recently) gets the vision model's description of your photos and of tool screenshots in place of "there was an image here". Descriptions are kept by the image's SHA-256, so the same picture is paid for once. `"media": {"view_image": true}` gives `view_image` without a vision model (for main models that see images); `"media": {"describe": false}` keeps `view_image` but stops the descriptions.
- **Reading PDFs** ([`engine/pdf.py`](engine/pdf.py)): `"use": {"pdf": "google/gemini-3.5-flash-lite"}` or `"media": {"read_pdf": true}` gives `read_pdf` (same sources as `view_image`, plus `pages` like `1-5,8` and `mode: "text"` for text only). A main model that reads PDFs as they are (Claude's API, OpenAI's own chat endpoint) gets the PDF itself, up to `"media": {"pdf_pages": 20}` pages; otherwise the PDF model answers (Google's own API with the PDF inline, Claude / OpenAI with a document block), or the text is extracted. Scanned pages (no text) are turned into images with `pdftoppm` when it's installed: shown to a model that sees images, read out by the vision model otherwise. PDFs are stored by content in `<data_dir>/engine/docs/` and only referenced in the session.
- **Transcription** ([`engine/stt.py`](engine/stt.py)): `"use": {"stt": "openai/gpt-4o-transcribe"}` (or `groq/whisper-large-v3-turbo`, `google/gemini-2.5-flash-lite`, `deepgram/nova-3`, `elevenlabs/scribe_v1`, or `{"model": "local/whisper-cli", "model_path": "~/models/ggml-base.bin"}` when whisper.cpp's `whisper-cli` is on the server; options `language` and `prompt`) gives Agents `transcribe` (a recording from the workspace, an attachment or a public URL → text) and sends attachment transcription and voice input to the same provider. Without it, uploads and voice input keep using OpenAI's `gpt-4o-transcribe`, then `whisper-1`, exactly as before. Long Gemini audio goes through its Files API; local runs convert to 16 kHz WAV with `ffmpeg` when it's installed. For channels: `engine.stt.transcribe_file(path, *, mime=None, language=None, prompt=None, conversation=None, agent=None)` → `Transcript(text, seconds, provider, model)`.
- **Speech** ([`engine/tts.py`](engine/tts.py)): `"use": {"tts": "openai/tts-1"}` (or `openai/gpt-4o-mini-tts`, `{"model": "elevenlabs/eleven_multilingual_v2", "voice": "<voice id>"}`, `google/gemini-2.5-flash-preview-tts`, `deepgram/aura-2-thalia-en`, or a local command such as `{"model": "local/piper", "args": ["--model", "/…/voice.onnx", "--output_file", "{out}"], "stdin": true, "format": "wav"}`; options `voice`, `format`, `instructions`, `speed`) gives Agents `speak`: the text becomes an audio file saved as an attachment of the conversation, hung under the reply when the turn ends, where the app's file preview plays it (the current app shows it once the chat reloads its history). "Reply with voice" is a per-conversation switch with only a server interface so far (`engine.tts.set_voice_reply(thread, True, voice=None)`): every reply in that chat then gets a spoken copy in the background. Microsoft Edge's free voices (Hermes's default) aren't included: that's an unofficial protocol that needs an extra package and breaks when Microsoft changes it; use a local command for free speech. For channels: `engine.tts.synthesize(text, *, voice=None, format=None, instructions=None, conversation=None, agent=None)` → `Speech(data, mime, ext, seconds, provider, model)`, and `speech_file(…)` also writes it to `<data_dir>/engine/speech/` (`Speech.path`).
- **Image generation** ([`engine/imagegen.py`](engine/imagegen.py)): `"use": {"image": "openai/gpt-image-1"}` (or `openai/gpt-image-2`, `google/gemini-3.1-flash-image`, `fal/fal-ai/flux/dev`, or a local ComfyUI: `{"model": "comfyui/workflow", "workflow": "~/comfy/workflow_api.json", "prompt_node": "6"}` with its default address `http://127.0.0.1:8188`) gives Agents `image_generate`: a prompt, optional reference images to edit (workspace paths, attachment ids, public URLs; up to 4), `count` (1–4), `size` or `aspect_ratio`, `quality`, `background`, `format`. Each image goes into the image store (the model sees it in the tool result) and becomes an attachment of the conversation, shown as a thumbnail under the reply. It's classified `undo` (it only adds files on your server and sends nothing out besides the request to your provider; costs are logged per call); `"tools": {"levels": {"image_generate": "ask"}}` makes it ask each time. It runs in the turn (no background mode): providers take seconds to a minute, well inside the tool's 6-minute limit.
- **Watching videos** ([`engine/video.py`](engine/video.py)): `"use": {"video": "google/gemini-2.5-flash-lite"}` gives Agents `video_analyze` (a video from the workspace, an attachment or a public URL, up to 200 MB, plus a question; `start` / `end` in seconds or mm:ss pick a part). Gemini gets the video itself (inline up to 20 MB, otherwise through its Files API, deleted afterwards). Another model that sees images (OpenAI, Claude…) gets evenly spaced frames taken with `ffmpeg` (`frames`, default 16) and no sound. With `ffmpeg` on the server, videos longer than 40 minutes are watched 40 minutes at a time and ones over 100 MB are shrunk to 360p first. `"media": {"describe_video": true}` also has videos you send in the app watched once on upload, the description going into the message like a document's text (off by default: uploads stay as they are).
- **Making videos and music** ([`engine/mediagen.py`](engine/mediagen.py)): `"use": {"video_gen": "google/gemini-omni-1.1-flash"}` (Gemini Omni Flash through Google's Interactions API: 3–10 s with sound, `aspect_ratio` 16:9 or 9:16, `resolution` 360p–4k; `{"delivery": "uri"}` fetches big ones through the Files API) or `"fal/<model path>"` (fal's queue, e.g. `fal/fal-ai/kling-video/v2/master/text-to-video`) gives Agents `video_generate` (a prompt, an optional starting `image`, `seconds` where the provider takes it). `"use": {"music": "google/lyria-3-clip-preview"}` (30-second clips; `google/lyria-3.5` for whole songs), `"elevenlabs/music_v1"` (`music_v2`, `music_v2_5`) or `"fal/<model path>"` gives `music_generate` (`prompt`, `lyrics`, `instrumental`, `seconds`). The file is saved as an attachment of the chat. Each call waits a little in the turn (25 s for video, 60 s for music); if it isn't done by then it carries on in the background and, when it's ready, a line comes into the chat and starts a turn, with the file under that reply (like background host commands). Calling again with the same prompt while it's running returns its status, and `action: "status"` lists them; at most 2 at a time per Agent; stopping the turn while it waits stops it; a server restart stops the ones still running and says so in their chat. `video_generate` costs real money (Omni Flash is about $0.10 a second at 720p), so it is `ask`: each one sends a card with the model and the estimated cost, and an approved one runs in the background; `"tools": {"levels": {"video_generate": "auto"}}` skips the card. `music_generate` is `undo` like `image_generate` (Lyria $0.04–0.08 a song, ElevenLabs $0.15 a minute). OpenAI's Sora 2 API closed on 2026-09-24 and Veo 3.1 previews close on 2026-10-22, so neither is offered. Not available in scheduled runs, heartbeats or background tasks.
- **Your own Chrome** ([`engine/chrome.py`](engine/chrome.py)): `"chrome": {"agents": {"main": true}}` (off by default, per Agent; `"*"` for the rest) gives that Agent `chrome`, which drives your real browser over CDP with all your logins, directly online and **not through Doorman**. The address and token are keys, never in `server.json`: `CHROME_CDP_URL` (`http://<host>:9222` for a Chrome started with `--remote-debugging-port=9222` and reachable from the server, e.g. over Tailscale or an SSH tunnel; or a `ws(s)://…` address from Browserless / Browserbase) and optional `CHROME_CDP_TOKEN` (sent as a Bearer token); save them in the app's keys or the server's environment (`engine.chrome.save_address(url, token)` does it from code). Looking (`snapshot`, `text`, `tabs`, `tab`, `screenshot`, `pdf` = save the page as an attachment) runs right away and pages open in a tab of its own, never the one you're on; clicking, typing, selecting, pressing keys, running scripts, closing your tabs, and opening an address that carries your private details all send a card saying which site and what, and an approved action isn't done if the page has moved to another site. Page text is marked as material. Not available in scheduled runs, heartbeats or background tasks. A device-node add-on can hand over an address through `chrome.ADDRESS_HOOKS` or `chrome.connect_to(agent, address, token)`.
- **Sandbox browser: a lasting login profile, and PDFs** ([`engine/sandbox.py`](engine/sandbox.py), [`engine/browser.py`](engine/browser.py)): `"sandbox": {"agents": {"main": {"profile": true}}}` keeps that Agent's sandbox browser profile (cookies, logins made through Doorman) in `<data_dir>/engine/browser-profiles/<Agent>` (0700) across container rebuilds; it's mounted only into that Agent's browser container, which then runs as the server's user. Off by default (the profile is thrown away as before). Ordinary Agents' sandbox `browser` also gains `pdf`: the page saved as a PDF attachment of the chat.
- **More search backends, and rendering script-only pages** ([`engine/web.py`](engine/web.py)): `web_search` can also use Gemini with Google Search grounding (`GEMINI_API_KEY`), Grok (`XAI_API_KEY`), Kimi (`MOONSHOT_API_KEY` or `KIMI_API_KEY`) and Firecrawl (`FIRECRAWL_API_KEY`), with OpenClaw's requests and order. Those keys are often already there for the models, so these four are only used when named (`"web": {"search": {"provider": "gemini"}}`) or when `"search": {"more": true}` lets them join the automatic pick (brave → gemini → grok → kimi → perplexity → firecrawl → exa → tavily → searxng); otherwise nothing changes. Gemini and Grok answer with sources (the answer comes first, then the links); each of the four logs one row per query in `engine_media_usage` (count only; no price checked). `"web": {"fetch": {"render": true}}` makes `web_fetch` hand an HTML page with almost no text (a script-only shell) to the Agent's sandbox browser once (online only through Doorman) and read what it renders; Agents without a sandbox browser get the page as before.
- **Many tools on demand** ([`engine/toolsearch.py`](engine/toolsearch.py)): `"tools": {"search": true}` (or `{"threshold": 20}`; default threshold 30) means that when an Agent's MCP and connector tools come to more than the threshold in a turn, they aren't handed to the model one by one: it gets `tool_search` (find by name or description; the full directory, sorted by name and up to 18,000 characters, is in its description), `tool_describe` (one tool's description and parameters) and `tool_call` (run one: `name` + `arguments`). `tool_call` takes the called tool's own classification, so read-only ones run right away and the ones that need your OK send the same card as calling them directly would (approving it runs that tool once, the same way). The engine's own tools, hands and memory are still given directly. The set is fixed when the turn starts, so it doesn't change mid-turn and the prompt cache holds; tools turned off (`engine.tools.levels`, or in Settings → Connectors) aren't in it, and `tool_call` checks the arguments against the tool's own schema first. Off by default: every tool is handed over as before.
- **Structured sub-tasks** ([`engine/llm_task.py`](engine/llm_task.py)): `"tools": {"llm_task": true}` (or `{"model": "deepseek/deepseek-flash", "models": [...], "timeout": 60, "max_tokens": 4000}`) gives Agents `llm_task`: one call to a model with **no tools** that works on `input` (any JSON, outside text included) following `prompt` and returns JSON, checked against `schema` (a JSON Schema: types, required, properties / additionalProperties, items, enum / const, lengths and ranges, pattern, anyOf / oneOf / allOf / not / if, local `$ref`; unknown keywords are skipped) and asked again once with what didn't match. It goes through the engine's one-shot path (`engine/oneshot.py`; not saved as a session, logged with its usage like other one-shots). Model: the call's `model` only if it's in `models` (default: the models you can switch to in the app), else `model`, else `engine.use.json`, else the chat's model, else `engine.model`. Your own plan (`claude-code/…`, `chatgpt/…`) is used only where it may be (`models.may_spend`: your own turns); otherwise a pay-as-you-go model is picked. `timeout` is the default wait (a call may ask for up to 300 s); `max_tokens` is the default and the cap. Not available in scheduled runs, heartbeats or background tasks. Off by default.
- **Diffs** ([`engine/difftool.py`](engine/difftool.py)): `"tools": {"diff": true}` gives Agents `diff`: `before` + `after` (two texts, up to 512 KB each; `path` is then only the name shown), or `path` alone (a workspace file, same path guard as `read_file`) compared with an old version kept before a change (`version`, default the most recent; `to` compares two old versions). It returns a unified diff (`context` lines around each change, default 3); long ones keep the start and the end. Binary files only say their sizes and hashes. `page: true` also publishes it as a page (green and red lines) under the reply, named `name` (default `diff-<file>`): publishing the same name again makes a new version. Comparing is `read`; with `page` it's `undo`. Off by default.
- **Code that calls your tools** ([`engine/codeexec.py`](engine/codeexec.py), after Hermes's `execute_code`): `"tools": {"execute_code": true}` (or `{"tools": ["write_file"], "timeout": 300, "max_calls": 50}`) gives Agents that have a sandbox `execute_code`: a Python script runs in the Agent's own sandbox (online only through Doorman, like `sandbox_exec`) and calls the Agent's tools as functions (`read_file(path=…)`, `web_search(query=…)`, `call_tool(name, **args)`; `tools()` lists them), so a chain of steps takes one call and only what it prints comes back (long output keeps the start and the end; the whole of it stays in the sandbox under `/tmp/.mousse-code/`). The calls travel over the `docker exec` process's own standard input and output (no network or extra mount needed) with a token made for that one run and revoked when it ends, stops or times out; each call goes through the same checks as a normal call. Inside the code only read-only calls run, unless you list a tool under `tools`; calls that need your OK still send their card (the script stops there with `NeedsApproval`), and tools turned off stay off. At most `max_calls` calls (default 50) and `timeout` seconds (default 300, at most 900) per run. The tool itself is classified like `sandbox_exec` (`undo`; `ask` with a card showing the whole code when the sandbox can write your workspace). Not available in scheduled runs, heartbeats or background tasks, nor to sandbox-only Agents. Off by default.
- **Media purposes, keys and costs** ([`engine/media.py`](engine/media.py)): `engine.use.vision`, `pdf`, `video`, `stt`, `tts`, `image`, `video_gen` and `music` take `provider/model` or an object with options; your own plans (`claude-code/…`, `chatgpt/…`) aren't accepted here (these are pay-as-you-go), except your Grok subscription (`grok/…`) for `image`, `video_gen` and `tts` (see "Your Grok subscription"). Keys are read like the models' (environment, keys saved in the app, `env_file`) and scrubbed from errors. Every call is logged in `engine_media_usage` (`mousse.db`) with its cost where the price is on the official page (sources and dates in `media.PRICES`; chat models fall back to `engine/models.py` prices); `GET /api/setup/usage` has a `media` column. `GET /api/setup/purposes` lists them under `media`; `PUT /api/setup/purposes` takes `{"vision" / "pdf" / "video" / "stt" / "tts" / "image" / "video_gen" / "music": "provider/model" | {…} | null}`. None of these tools exist in scheduled runs, heartbeats or background tasks. The provider catalog's `caps` now also say `pdf`, `video` and `audio` where the official docs do (`null` otherwise).

## Skill requirements and settings (built-in engine)

Skills written for OpenClaw or Hermes work as they are ([`engine/skill_gate.py`](engine/skill_gate.py)). A skill whose requirements aren't met is left out everywhere the Agent sees skills (the skill list at the start of a session, the `skill` tool, the per-message search, helpers over `/mcp`); the settings API still lists it and says what's missing.

- OpenClaw's frontmatter: `metadata: {"openclaw": {"requires": {"bins": [...], "anyBins": [...], "env": [...], "config": [...]}, "os": [...], "always": true, "primaryEnv": "FOO_API_KEY"}}` (one line of JSON or nested YAML). `bins` must all be on `PATH`, one of `anyBins` is enough, `env` must be in the environment, the app's saved keys (`secrets.env`), `env_file` or the skill's `entries.<name>.env`, `config` paths in `server.json` must be truthy, and `os` is `darwin` / `linux` / `win32` (`macos` and `windows` work too). `always: true` skips `requires` but not `os`. Old ClawHub skills' `metadata.clawdbot` is read too, and `metadata.openmousse` takes the same keys.
- Hermes' frontmatter: `platforms: [macos, linux, windows]`; `metadata.hermes.requires_tools` / `requires_toolsets` (hidden when the Agent doesn't have them) and `fallback_for_tools` / `fallback_for_toolsets` (hidden when it does). `required_environment_variables` (and `setup.collect_secrets`, `prerequisites.env_vars`) don't hide the skill: it's listed as `(setup needed)` and its text ends with a `[Skill setup note: …]` telling the model to have you add the key in settings, never in the chat.
- Per-skill settings in `server.json`, `engine.skills.entries.<name>` (all optional; nothing changes for existing setups):
  - `enabled: false` turns the skill off.
  - `env: {"FOO_API_KEY": "${FOO_API_KEY}"}`: variables for this skill. Names that look like secrets must be written as `${VARIABLE}`; the value comes from the environment, `secrets.env` or `env_file`. `apiKey: "${VARIABLE}"` is short for the `primaryEnv` one.
  - `config: {"units": "metric"}`: non-secret settings. They're appended when the skill's full text is read, as `[Skill config (from server.json engine.skills.entries.<name>.config): …]`, with the defaults the skill declares in `metadata.hermes.config` for anything not filled in.
- Who gets the real values: commands on the host (`host_exec`) get the variables the skill declares (`requires.env`, `primaryEnv`, `required_environment_variables`) and the non-secret ones in `entries.<name>.env`, only while that Agent has the skill (on its list, requirements met, not turned off). `PATH`, `LD_*`, `PYTHONPATH`, proxy and CA variables and the like are never passed. The sandbox keeps getting placeholders only; real values never go into a container.
- Settings API (your own devices only; `server.json` is backed up before every write): `GET /api/setup/skills/{agent}` gives each skill a `gate` (`eligible`, `enabled`, `missing` like `needs ffmpeg` / `needs FOO_API_KEY`, `setupNeeded`, `env`). `GET /api/setup/skills/config/{name}` shows a skill's switch, variables (whether set, where from, last four characters; never the value), settings and requirements. `PUT /api/setup/skills/config/{name}` takes `{"enabled"?, "env"?: {"FOO_API_KEY": "value" | null}, "config"?: {…} | null}`: values go only into `secrets.env`, `server.json` only gets `${FOO_API_KEY}`, and `null` removes the variable (and its `secrets.env` line, when no other skill uses it).
- Skills as slash commands: `/<skill> <what you want>` (or `/skill <name> <what you want>`) hands the model the skill's full text, its settings and missing-variable notes, the other files in its folder, and then what you typed after it, the way Hermes does. Names match without regard to case or `-` / `_`. Built-in commands win, a skill with `user-invocable: false` in its frontmatter (OpenClaw's key) isn't a command, and neither is one the Agent can't use (not on its list, requirements not met, turned off). The matching is `slash_skill` in [`engine/agent_skills.py`](engine/agent_skills.py); chat starts calling it when the built-in command framework lands, so that its commands are checked first.

## Skills every Agent shares (built-in engine)

Besides each Agent's own `skills/` and the bundled `packs/core/skills`, there is one more folder every Agent sees: `skills/` under the data directory (`<data_dir>/skills`, by default `~/.openmousse/data/skills`; like OpenClaw's `<state-dir>/skills` and Hermes' `~/.hermes/skills`). When two have the same name, the Agent's workspace wins over this folder, which wins over core. Skills from the skill market go here (or into one Agent's workspace if you ask), and you can put your own in by hand. Agents can't write to it: `skill_manage` only writes the Agent's own workspace (a skill there with the same name hides the shared one; a link to the shared folder is replaced by a copy before any change). Requirements and settings (above) apply the same way.

## Skill market: search and install (built-in engine)

Search several places at once and install skills after a scan and your OK ([`engine/skill_market.py`](engine/skill_market.py)). Publishing isn't part of it.

- Sources: **ClawHub** (`clawhub:@owner/slug`; search, its trust verdict checked before every install, download), **GitHub** (`github:owner/repo[/path][@ref]`; the ref is turned into a 40-character commit and the lock records it; search covers the repositories in `repos`, plus GitHub code search when `GITHUB_TOKEN` is set), **skills.sh** (search only; installs come from the GitHub repository it points to, pinned the same way), **sites that publish skills in the agentskills.io format** (`/.well-known/agent-skills/index.json` with digests, or `/.well-known/skills/index.json`; the `sites` list is searched, any other site can be installed from), and a **direct link** to a `SKILL.md`. agentskills.io itself is the format specification: it has no public catalog or search API (checked 2026-10-19), so the market accepts any site that follows its discovery format instead of treating it as one source.
- Search asks every source at once, each with a time limit; a source that fails or times out is skipped and named in `failed`. Results are merged, deduplicated (the same GitHub folder found through two sources counts once) and ranked by how well the name and description match.
- Install: download into memory with hard limits (zip up to 25 MB, at most 100 files, 1 MB per file, 10 MB in all). Paths that escape the folder (zip-slip), symlinks and hard links, and executable binaries reject the whole package. It goes into a quarantine folder (`<data_dir>/skills-market/quarantine/`, no executable bits) and is scanned with Hermes' skills guard (data exfiltration, prompt injection, destructive commands, changes to agent config, invisible Unicode…) as untrusted community content, whatever the source. `dangerous` is never installed, not even from the command line, and neither is anything ClawHub blocked or flagged as malicious (if ClawHub's verdict can't be fetched, it isn't installed either). Otherwise the Agent gets an approval card with the source, version or commit, scan verdict and findings, the start of `SKILL.md` and where it will go. Only when you approve is the quarantined copy checked against the card's fingerprint, scanned again and moved into the shared skills folder (or the Agent's workspace, `agent`). An existing skill with the same name is never overwritten.
- `<data_dir>/skills-market/lock.json` records each install: source, identifier, version or commit, content fingerprint, scan verdict and findings, when.
- Update: fetches the same identifier again (GitHub follows the original branch to its new commit) and compares fingerprints. Unchanged means up to date; a skill you changed locally is skipped; a changed upstream goes through quarantine, the scan and a card again, and the old copy is kept first (`engine/versions.py`). Remove keeps a copy, then deletes. Only market installs (in the lock) are touched.
- The Agent's `skill_market` tool (off until `engine.skills.market.enabled` is `true`, since it goes online): `search` and `list` are read-only; `install`, `update` and `remove` make a card. Like OpenClaw's clawhub skill, the Agent is told to search before saying it can't do something, and that finding a skill isn't permission to install it.
- Settings API (your own devices): `GET /api/setup/skills/market/search?q=`, `POST /api/setup/skills/market/preview {"id", "agent"?}` (download, quarantine, scan; returns the verdict and a `staged` id, `installable: false` for dangerous ones), `POST /api/setup/skills/market/install {"staged"}`, `GET /api/setup/skills/market/installed`, `POST /api/setup/skills/market/update {"name", "agent"?}`, `DELETE /api/setup/skills/market/installed/{name}?agent=`.
- Command line, on your own machine: `mousse skills search <words>`, `mousse skills install <id> [--agent <id>] [--yes]` (installs directly after the scan; `caution` needs `--yes` or a typed `y`; `dangerous` never), `mousse skills update [<name> | --all] [--force]`, `mousse skills list`, `mousse skills remove <name>`.
- Settings, `engine.skills.market` in `server.json` (all optional): `{"enabled": false, "sources": ["clawhub", "skills.sh", "github", "well-known"], "clawhub": "https://clawhub.ai", "github_api": "https://api.github.com", "github_raw": "https://raw.githubusercontent.com", "skills_sh": "https://skills.sh", "repos": ["anthropics/skills"], "sites": [], "timeout": 8}`. Links the Agent supplies (direct `SKILL.md` links, sites not in `sites`) only reach public addresses.

## Your own hooks (built-in engine)

Run your own script when something happens in the engine ([`engine/user_hooks.py`](engine/user_hooks.py)). Only scripts: your Python never runs inside the server (that's what code plugins are for, further down). Nothing runs until you've written a hook and approved it.

- Events: `startup`, `session:start`, `session:end` (a chat's day session starts, and the previous day's ends), `message:received` (you said something in the app; it can stop the message), `reply:sent`, `tool:before` (before a tool call; it can stop the call or change its arguments), `tool:after`, `compact:before`, `compact:after`. The two that can stop something wait for the scripts; the rest run in the background.
- In `server.json`, `engine.hooks.<event>` is a list of `{"command": ["python3", "/home/me/hooks/guard.py"], "matcher": "host_exec|demo__*", "timeout": 30, "fail_closed": false, "cwd"?}`. `command` is an argv list and never goes through a shell; `matcher` (tool events only) is a tool name with `*` / `?` wildcards, several separated by `|`; `timeout` defaults to 30 seconds, at most 300.
- Hooks in an Agent's workspace, OpenClaw style, are read only with `"workspace": true`: `hooks/<name>/HOOK.md` with `events` (or `metadata.openclaw.events`; OpenClaw's names like `gateway:startup` and `command:new` are mapped), `requires` / `os` like skills, and a script handler: `command` in the frontmatter, or `handler.py` / `handler.sh` / an executable `handler` next to it. They only see that Agent's events.
- The protocol is the one Claude Code and Hermes use. The script gets the event as JSON on stdin (`event`, `hook_event_name`, `agent`, `conversation`, `at`, plus `tool_name` / `tool_input`, `text` / `from` / `trusted`, …). On stdout, `{"decision": "block", "reason": "…"}` stops it (Hermes' `{"action": "block", "message"}` and Claude Code's `permissionDecision: "deny"` work too) and `{"decision": "modify", "tool_input": {…}}` changes a tool call's arguments (`tool:before` only; also `{"action": "modify", "args"}` and `updatedInput`). Exit code 2 stops it with stderr as the reason. Other exit codes, timeouts and output that isn't JSON let things go ahead, unless `fail_closed` is `true`.
- A stopped tool call returns the reason to the model; a stopped message gets a short reply saying a hook stopped it. Changed arguments are checked against the tool's schema and must stay the same kind of call (the approval level can't get stricter, and a command-line tool keeps its subcommand), then go through the approval gate again. Nothing a script prints ever goes into the model's context.
- Approval, as in Hermes: before a hook's first run you approve it. Its fingerprint (event, command, working directory and the contents of the script it runs) goes on `<data_dir>/hooks/allowlist.json`, and changing the command or the script needs a new OK. An unapproved hook doesn't run, not even a `fail_closed` one, and gets an approval card instead; `mousse hooks approve` does the same from a terminal.
- Scripts get a minimal environment (`PATH`, `HOME`, locale and so on, plus `MOUSSE_HOOK_EVENT`), never the server's API keys. Each runs in its own process group and is killed at its time limit.
- Two bundled hooks, off until turned on in `engine.hooks.bundled`: `"boot-md": true` runs each Agent workspace's non-empty `BOOT.md` once at startup as one of your own turns, in a fresh session that isn't posted to any chat, with the heartbeat's choice of model (never your plan); `"command-logger": true` writes one JSON line per session start and end and per slash command to `<data_dir>/logs/commands.jsonl`.
- `GET /api/engine/hooks` shows every hook, whether it's approved and its last few runs. Command line: `mousse hooks list`, `mousse hooks approve <fingerprint prefix> | --all`, `mousse hooks revoke <fingerprint prefix>`, `mousse hooks test <event> [--tool <name>] [--payload <json>]`.

## Your MCP servers: prompts, sampling and managing them (built-in engine)

The MCP servers you add under `mcp_servers` in `server.json` ([`engine/mcp_client.py`](engine/mcp_client.py)) get three more things. Nothing changes for existing setups: prompts only appear for servers that have some, and sampling is off until you turn it on per server.

- Prompts: when a server says it has prompts and actually lists at least one, the Agent gets two read-only tools, `<server>__prompts_list` (names, descriptions, arguments; `*` = required) and `<server>__prompts_get` (`{"name", "arguments": {"…": "…"}}`). What comes back is wrapped as outside data, not instructions. `"prompts": false` on a server hides them.
- Sampling, off by default: a server can ask the client's model to write something (MCP's `sampling/createMessage`). Without a `sampling` entry the engine says no, as the MCP spec describes ("Sampling not supported"). With `"sampling": {"model": "deepseek/deepseek-flash", "max_tokens": 1024, "max_rpm": 10}` (each key optional: `model` defaults to the default model, `max_tokens` caps each answer whatever the server asks for, `max_rpm` is answers per minute, then an error) it answers, always as an outsider turn with no tools (the server's system prompt and messages are its only input; no memory, no chat, nothing else), never with your own Claude Code or ChatGPT plan (a plan model is refused; with no `model` and a plan as the default model, the first pay-as-you-go model in `engine.models` is used), and counted in usage (purpose "other", conversation `mcp-sampling:<server>`). The server's `includeContext`, `modelPreferences` and `tools` are ignored. Local (stdio) servers only for now: remote servers open a short session per call, which has no way to answer. Give a server that samples a `timeout` long enough for the model to answer.
- Managing them from a terminal: `mousse mcp list [--json]`, `mousse mcp add <name> --command <cmd> [--arg …] [--env K=V …] [--cwd …]` or `--url <url> [--type http|sse] [--header K=V …]`, plus `[--agent <id> …] [--tool <tool>=auto|ask|off …] [--disabled]`, then `mousse mcp remove | enable | disable <name>` and `mousse mcp probe <name> [--json]`. `add` connects once first and lists the tools; one that can't connect isn't saved (`--save-anyway` saves it turned off; `--no-probe` skips the check). Secrets in `env` and headers must be `${VARIABLE}`, as before.
- Settings API (your own devices only): `GET /api/setup/mcp`, `GET /api/setup/mcp/{name}` (the entry as written, secret-looking literal values masked, plus its status), `PUT /api/setup/mcp/{name}` (the entry as the body; checked like `server.json`, a plan model for sampling is refused), `DELETE /api/setup/mcp/{name}` (also stops its process), `POST /api/setup/mcp/{name}/probe` (one real connection: starts it or connects, initializes, lists tools, resources and prompts, and closes; a running copy isn't touched). `server.json` is backed up before every write, by the API and the command line alike; the engine reads it fresh, so changes apply from the next turn.
- Elicitation (a server asking you a question mid-call) isn't supported yet; servers get the spec's refusal.

## Remember when… (built-in engine)

"Next time I mention my passport, remind me to renew it": prospective memory, after OpenClaw's standing intents ([`engine/intents.py`](engine/intents.py)). Off until `engine.intents.enabled` is `true`.

- The Agent gets a `remember_when` tool in your own turns only: `create` with `triggers` (words or short phrases) and a `reminder`, optionally `max_fires`, `cooldown_hours` and `expires`; `list`; `cancel` (which is also how a create is undone, so it needs no card).
- Each message you send is checked without a model: lowercased and split into words, and a trigger matches when all its words are in the message (Chinese, Japanese, Korean and Thai, which don't put spaces between words, match as substrings). Messages the server writes itself (inbox notices, scheduled scripts, background results) aren't checked, and other people's messages never are.
- On a match, one line goes into that turn right after your message, in the same note as the manuals found for it (or on its own): "Reminder the user asked you to keep (set 2026-10-19; their message mentions "passport"): …". At most 3 per message and 1,200 characters. Each reminder fires at most `max_fires` times (default 3), at least `cooldown_hours` apart (default 24), until `expires` (default 90 days), then stops by itself. Each firing is noted with what the turn used (`engine/used.py`, kind `intent`).
- In the memory gate it counts as experience, like `HEARTBEAT.md`: a dated, self-expiring note of something you asked for, not a fact (leaf) or a standing way of working (procedure). So creating and cancelling are direct writes in your turns, recorded in the gate's log; Cyber and outsider turns can't.
- `GET /api/engine/intents?agent=main[&all=1]` lists them; `DELETE /api/engine/intents/{id}` cancels one.
- Settings, `engine.intents` in `server.json`: `{"enabled": false, "max_fires": 3, "cooldown_hours": 24, "expiry_days": 90}` (the last three are the defaults for `create`).

## Code plugins (built-in engine, off by default)

Python plugins that add tools, hooks, skills and MCP servers to the engine ([`engine/plugins.py`](engine/plugins.py)), after Hermes' plugins (a manifest plus `register(ctx)`).

**A plugin's Python runs inside the server process, with no sandbox.** It can do anything the server can: read `server.json`, `secrets.env` and every provider key, use the network, start processes, change files. As OpenClaw puts it for its native plugins, a loaded plugin "has the same process-level trust boundary as core code". The rules below cover what a plugin says it will do and what you agreed to; they can't stop a plugin written to do harm. Only install plugins you trust.

- Nothing loads unless `engine.plugins.enabled` in `server.json` lists it (`{"enabled": ["weather"], "load_timeout": 10, "entries": {"weather": {"agents": ["main"]}}}`), it's installed, and you've agreed to its capabilities.
- A plugin is a folder in `<data_dir>/plugins/<name>/` with `openmousse.plugin.json` (`name`, `version`, `description`, `capabilities`: `tools` (`[{"name", "undoable"}]`), `hooks` (event names), `skills` (a folder), `mcp` (server names)) and `plugin.py` with a plain `register(ctx)`.
- `ctx` offers only what the manifest declares: `ctx.tool(name, fn, description=, schema=, undoable=False)` (named `<plugin>__<tool>`, your own turns only, for the Agents in `entries.<plugin>.agents`, default `main`; undoable tools run directly, the rest send a card every time); `ctx.hook(event, fn, matcher=, timeout=)` (the same events and `block` / `modify` answers as script hooks); `ctx.skills_dir("skills")` (seen by every Agent, after the shared folder and before core, still subject to requirements and lists); `ctx.mcp_server(name, entry)` (checked like `mcp_servers`; an entry with the same name in `server.json` wins). Anything undeclared fails the whole plugin.
- Your agreement covers its capability list (`tool:x`, `undoable:x`, `hook:<event>`, `skills`, `mcp:x`), kept in `<data_dir>/plugins/plugins.json`. Installing from the command line (after typing `y`) or the settings API counts. An enabled plugin you haven't agreed to, or that asks for more after an update, doesn't load and sends an approval card; fewer capabilities need no new OK.
- Install from a local folder, or a git address plus a full 40-character commit (branches, tags and short hashes are refused; HEAD is checked after the checkout). Files go through the skill market's limits (no paths escaping the folder, no links, no executable binaries), Hermes' skills guard, and Python checks (dynamic code, shell commands, native libraries, environment variables, network, secret files…). Those findings are warnings only: they're shown, not enforced.
- Loading happens at server start, before the `startup` hooks: each plugin imports and registers in a thread with a time limit (`load_timeout`, default 10 seconds, at most 120). A plugin that times out or fails isn't loaded, nothing it registered is kept, and the others load anyway. Changes need a server restart (Python can't unload a module).
- Command line: `mousse plugins list`, `mousse plugins install <folder | git address> [--commit <sha>] [--yes] [--enable] [--replace]`, `mousse plugins enable | disable | approve | remove <name>` (remove keeps a copy in `<data_dir>/plugins/.removed/`). Settings API (your own devices): `GET /api/setup/plugins`, `POST /api/setup/plugins/preview {"source", "commit"?}`, `POST /api/setup/plugins/install {"staged"}`, `POST /api/setup/plugins/{name}/approve`, `PUT /api/setup/plugins/{name} {"enabled"}`, `DELETE /api/setup/plugins/{name}`. `server.json` is backed up before every write.

## Brakes and outside triggers (built-in engine)

Everything here is off on an existing install until you turn it on; the emergency stop is always there but does nothing until you use it.

### Emergency stop

One switch pauses every automatic thing ([`engine/estop.py`](engine/estop.py), after Hermes's `hermes pause`). It's a small file, `<data_dir>/ESTOP`, so it survives a restart and never touches `server.json`.

```bash
mousse pause --reason "Away this weekend"      # new automatic work stops
mousse pause --stop-running                    # also stop what's running now
mousse resume
```

- While paused: scheduled jobs and heartbeats skip their time (the run log gets an `estop` row; it isn't a failure and doesn't count toward five-in-a-row; a one-off job due then is marked missed). Webhooks answer `503` with `Retry-After`, mail and watch triggers don't fetch, new background tasks aren't started (the `tasks` tool says why), flows don't advance, and write-back, skill reviews and embedding backfill wait. An Agent can't run a job by hand through `cron`; you still can in the app.
- Chatting in the app works as usual, and so does approving cards.
- What's already running finishes, unless you pause with `--stop-running` (`"stop_running": true`): then running jobs, heartbeats, background tasks, flow steps, video and music generation that went to the background, and the automatic turns in chats (`origin auto`) are stopped as if you had pressed stop. They're logged as interrupted, not failed. Your own turn in the app is never stopped.
- A file that is empty or broken still counts as paused (touching it is enough). The command line writes the file directly, so it works with the server down; the server checks it every time and applies `--stop-running` within 30 seconds.
- API, from your own devices only (the app's token or one of your Tailscale devices, like the setup pages): `GET /api/engine/pause`, `POST /api/engine/pause {"reason"?, "stop_running"?}`, `POST /api/engine/resume`. `/api/engine/status` has `paused`.

### Spend caps

How many dollars the engine may spend in a day or in one turn ([`engine/spend.py`](engine/spend.py)). Without `engine.spend` there is no cap, as before.

```json
"engine": {"spend": {"day": 5, "turn": 1, "warn": 0.8,
                     "agents": {"g-study": {"day": 1}},
                     "purposes": {"background": {"day": 2}, "outsider": {"day": 1}}}}
```

- `day`: pay-as-you-go dollars per calendar day in `server.json`'s time zone (the usage page's days). `turn`: per turn (one message in until the model finishes, however many model calls that takes). `agents.<id>` and `purposes.<purpose>` take their own `day` / `turn`; purposes are the usage page's: `chat` (your own chats), `background` (jobs, heartbeats, background tasks, write-back), `outsider` (card agent, Doorman, the one tool-free read of an outside trigger), `api`, `cyber`. `0` means nothing pay-as-you-go may run for it. `warn` (default 0.8) sends one silent push per cap per day at that share, and one more when the cap is reached.
- What counts: models with a known price (`PRICES` in [`engine/models.py`](engine/models.py)), the same money the usage page shows, plus embeddings (indexing counts as background) and media with a known price (image, video and music generation, image reading, speech…), which count toward the day and the Agent but not a purpose. Image, video and music generation check the caps before they start; local ones (ComfyUI, local commands) are never stopped. Your own plans (`claude-code/…`, `chatgpt/…`, and media on your Grok subscription) cost nothing here and are never stopped; Claude Code signed in with an API key does count (its own estimate). Models without a price can't be costed: their tokens are logged, `GET /api/engine/spend` lists them under `unpriced`, and they aren't stopped, since a local Ollama or a brand-new model would otherwise just break without saying why. Give them a price, or no key, to control them.
- When a cap is reached: the check runs before every model call, so a turn that crosses it stops at its next call, with no retry and no backup model. Your own turn in the app ends with one line saying what was spent, the cap and which key to change. Jobs, heartbeats and background tasks check before they start: they skip and log `limit`, which isn't a failure. Claude Code with an API key checks the day total before each turn; embedding backfill checks the day total and `background`.
- Not covered: the card agent's direct `card.llm` and OpenClaw's `llm-task`, which don't go through the engine.
- `GET /api/engine/spend` shows today's spending per cap, what's left, what's blocked, and the unpriced and plan turns. `PUT /api/engine/spend {"day"?, "turn"?, "warn"?, "agents"?, "purposes"?}` changes the caps (`null` removes one; `{"spend": null}` removes them all), from your own devices only, backing up `server.json` first.

### Retries

What a scheduled job that runs the model does when a run fails, once you turn it on with `"retry": true` in `engine.jobs` ([`engine/jobs.py`](engine/jobs.py), after OpenClaw's cron backoff and Hermes's quota hold). It's off by default: a retry is another model run, so it spends plan quota or pay-as-you-go money. Off, a failed run just waits for the next normal one, as before.

- A passing problem (the provider can't be reached, 429 or overloaded, a 5xx, a timeout) before the model wrote anything or used a tool: the same run is tried again after 30 s, 1 min, 5 min, 15 min and 60 min, never past the job's next normal run (that run just happens). A one-off job is retried at most three times. Retries don't count as runs or toward five failures in a row, and the chat only hears about it when the last retry fails too. When the provider says how long to wait ("try again in 20s"), it waits at least that long.
- The provider's usage window is closed and it says when it reopens ("resets 3pm", "retry after 7200s"): the job waits instead of failing at every run. The runs inside the window fold into one at the first scheduled time after it; a sparse job (once a day) gets one catch-up run right after the window. The chat hears about it once, with the times. Without a reopening time, or more than a week away, it's treated as permanent.
- Anything else is permanent and isn't retried: not allowed, not configured, signed out, the command won't start, a spend cap, the emergency stop, a refusal, or a run that already wrote something or used a tool (running it again could repeat what it did).
- Jobs that post into the chat (`"session": "chat"`) aren't retried after a passing problem: the failed run has already left its "Auto-triggered" line and the missing reply in the chat, and a retry would add a second pair. The usage-window wait still applies.
- Jobs that only run a command are retried only with `"retry"` in `command` (whatever `engine.jobs.retry` says); heartbeats aren't (the next beat comes anyway), and neither are runs you start by hand.
- `engine.jobs.retry`: `true` uses the ladder `[30, "1m", "5m", "15m", "1h"]`, a list sets your own, and leaving it out or `false` turns retries off.

### Webhooks

Another service POSTs to `/webhooks/<name>` and the engine tells you about it, hands it to an Agent after you approve, or (for your own signed scripts) wakes the Agent directly ([`engine/webhooks.py`](engine/webhooks.py), [`engine/triggers.py`](engine/triggers.py); verification, filters and coalescing after Hermes's webhook gateway). Nothing is on until you add one, and only with the built-in engine.

```json
"engine": {"triggers": {"webhooks": {
  "github": {"verify": "github", "secret": "${GITHUB_HOOK_SECRET}", "label": "GitHub",
             "events": ["pull_request"], "filters": [{"field": "action", "in": ["opened", "reopened"]}],
             "coalesce": {"key": "pull_request.number"},
             "action": "card", "say": "Only mention PRs that need my review.",
             "task": "Read the PR and write me a short review summary."},
  "backup": {"verify": "hmac", "secret": "${BACKUP_HOOK_SECRET}", "action": "agent", "trust": "owner",
             "task": "If the nightly backup failed, find out why and tell me."}}}}
```

- What comes in is someone else's text. With `notify` (the default) or `card`, the body goes only into one tool-free read (the card agent's kind of call: no tools, never your Claude or ChatGPT plan; model `engine.use.trigger`, or the first pay-as-you-go model) that writes a one- or two-sentence notice, following your `say`. `notify` posts it in the chat as a grey ⚙ line and pushes it (`level`, default quiet). `card` puts an inbox card up instead; only when you approve does the Agent get a turn, doing your `task`, with what came in handed over as data (a note you add when approving counts as yours). The copy the model sees later is always wrapped as data.
- `agent` (wake the Agent with your `task`) and `job` (start a scheduled job now, `"job": "job-…"`) skip the read. They're only allowed for a signed hook (`github` or `hmac`) that you marked `"trust": "owner"`: your own scripts and devices.
- Verification, required: `github` (`X-Hub-Signature-256`), `hmac` (`X-Webhook-Timestamp` in Unix seconds and `X-Webhook-Signature: sha256=<hex HMAC-SHA256 of "<timestamp>.<body>">`; more than 5 minutes off is refused), or `bearer` (`Authorization: Bearer <secret>`, for small devices that can't sign; never `trust: owner`). The secret is always `${NAME}`, with the value in `secrets.env` (or the environment).
- Answers: unknown name or bad signature → `404` / `401` with no detail; body over `max_bytes` (1 MB) → `413`; more than `limit` (60) an hour → `429`; emergency stop → `503` with `Retry-After`; accepted → `202`, handled in the background. The same delivery (`X-GitHub-Delivery`, the same signed body, or the same timestamped signature) is handled once; one that failed is tried again when the sender redelivers it. `events` and `filters` (`exists`, `equals`, `not_equals`, `contains`, `in`, `regex`, combined with `all` / `any` / `not`; `field` is dotted, or `event`) drop what you don't want; `coalesce` keeps only the latest of a burst on the same `key` (quiet `window` 30 s, at most `max_wait` 300 s).
- Reaching it: `/webhooks/<name>` sits on the main server, outside `/api`, so your own devices and Tailscale can call it. A hook with `"public": true` is also served by the small public server (`share.public_port`, the one Funnel or a reverse proxy points at). The server never opens Funnel or a port by itself.
- `GET /api/engine/triggers` lists the hooks (the secret only as its variable name and whether it's set) and recent events, with what happened to each. `PUT /api/engine/triggers/webhooks/<name>` with the fields above (and optionally `secretValue`, saved into `secrets.env`) and `DELETE` change `server.json`, from your own devices only, backing it up first.

### Watching for changes, checking first

A scheduled job that runs the model can look at something before it calls the model ([`engine/watch.py`](engine/watch.py), after Hermes's cron monitor and wake gate). Without these fields a job runs exactly as before.

```json
{"agent": "g-garden", "when": "every 30m", "task": "Tell the user what changed in the plant stock.",
 "watch": {"board": {"from": "plants"}}}
{"agent": "main", "when": "every 15m", "task": "Tell me when appointment slots open.",
 "watch": {"url": "https://clinic.example/booking", "match": "slots", "action": "notify"}}
{"agent": "main", "when": "every 10m", "task": "Summarise the new orders.",
 "pre": {"script": "/home/me/scripts/new_orders.py"}}
```

- `watch` takes one of `command` (a command-line tool or an allowlisted script, as in command jobs), `board` (one of the Agent's board tables: `from`, optional `where` / `sort` / `limit`) or `url`. Each time it looks first and compares with what it saw last time (the exact output's fingerprint, so a source should print stable output; `match` keeps only the lines of a page matching a regex). The first look is only remembered; when nothing changed the run is logged as `unchanged`, calls no model and doesn't count toward `engine.jobs.daily_limit`.
- A change in a `command` or `board` (your own things) wakes the Agent for that run with the diff and how it looks now, handed over as data. A change in a web page (someone else's text) only goes to the tool-free read, following the job's `task`, which posts a notice or, with `"action": "card"`, puts up an inbox card; it never starts the Agent's turn by itself. Pages are fetched only from the public internet, like the `web_fetch` tool.
- What it saw is only replaced once the woken run succeeds, so a failed run sees the change again next time. A source that can't be read is a failed run (retries and five-in-a-row as usual).
- `pre` runs a command first: if the last line it prints is `{"wake": false}` (Hermes's `{"wakeAgent": false}` works too) the run is logged as `gated` and no model is called; otherwise its output is passed to the model as data.
- You can add them in the app (`POST` / `PATCH /api/engine/jobs`, `false` removes one). An Agent can propose them through its `cron` tool; like every new job it stays off until you approve, and the card says what is watched and what a change does.

### Mail

The engine can watch an IMAP mailbox and tell you about new mail ([`engine/mailwatch.py`](engine/mailwatch.py), Python's own `imaplib`, nothing to install). Nothing is watched until you add a mailbox.

```json
"engine": {"triggers": {"mail": {
  "home": {"host": "imap.example.com", "user": "me@example.com", "password": "${HOME_MAIL_PASSWORD}",
           "known": ["boss@work.example", "@school.example"], "authserv_id": "mx.example.com",
           "action": "notify", "say": "Tell me who wrote and whether it needs an answer today."}}}}
```

- It only reads: the folder is opened with `EXAMINE`, messages are fetched with `BODY.PEEK`, so nothing is marked read, moved, deleted or sent. It remembers where it is by `UIDVALIDITY` and UID; the first look (and a rebuilt mailbox) only remembers where the mailbox is, so old mail is never read. It looks every `interval` seconds (300 by default, at least 60) over `ssl` (port 993) or `starttls`; unencrypted connections aren't allowed.
- Mail is someone else's text: each new message (headers, the text body, attachment names) goes only into the tool-free read and becomes a notice, or with `"action": "card"` an inbox card that hands it to the Agent only when you approve. A mail trigger never wakes an Agent by itself.
- `known` limits it to senders you know: a full address or `@domain`, and only when the topmost `Authentication-Results` header written by your own mail server (`authserv_id`) says `dmarc=pass` for the sender's domain, so a forged `From` doesn't count. Unknown senders follow `others` (`ignore` by default, or `notify`). Without `known`, every new message is handled.
- At most 20 messages are read at a time (after a long outage only the newest; the rest are noted as skipped), and at most `limit` (30) an hour. A message held back by a spend cap is read again on the next round. While the emergency stop is on it doesn't connect. If the same mailbox is also set up as an email chat (`channels.email` with the same IMAP host, user and folder), this trigger doesn't run, and `GET /api/engine/triggers` says why.
- `PUT /api/engine/triggers/mail/<name>` (with optional `passwordValue`, saved into `secrets.env`) and `DELETE` change `server.json` from your own devices, backing it up first; the listing shows the password only as its variable name and whether it's set.

### Heartbeats: in the chat, answering with a tool, checking first

Three additions to `engine.heartbeat.<agent>` ([`engine/heartbeat.py`](engine/heartbeat.py)); a heartbeat without them runs as before.

```json
"engine": {"heartbeat": {"main": {"every": "30m", "prompt": "Check whether anything needs me today.",
                                  "session": "chat", "pre": {"script": "/home/me/scripts/anything_new.py"}}}}
```

- `"session": "chat"` runs the check-in inside the Agent's chat for today, so it sees what was said (the default, `isolated`, is a fresh session without the chat history). When there's nothing to say, both lines are removed again, as before.
- `heartbeat_respond` (after OpenClaw's): every turn of an Agent with a heartbeat has this tool, so its tool list doesn't change, but only a heartbeat turn accepts it, once. `notify: false` with a one-line `summary` sends nothing, and the summary is shown to the next check-in as its own note; `notify: true` with `text` sends that text. Without the tool, `NO_REPLY` works as before.
- `pre` runs a command first (a command-line tool, or a script listed in `engine.jobs.scripts`): if its last line is `{"wake": false}` the check-in is logged as `gated` and no model is called; otherwise its output is added as data after the checklist.

### Run this in the background

`POST /api/engine/bg {"thread", "text", "label"?, "minutes"?, "model"?}` ([`engine/bg.py`](engine/bg.py)) hands one message to a background task, the same way the `tasks` tool does: it shows on the task page, can be revised there, and its result comes back into that chat as a new turn while you keep chatting. Since you asked for it yourself there's no "one more background task" card for the daily allowance; `tasks.max_minutes` still caps how long it runs, and the emergency stop and spend caps still refuse it (answered with `409` and why). From your own devices only. The `/bg <what to do>` slash command calls the same thing for the chat you're in.

### Workflows

A few steps you write once in `server.json` and start when you like, or from a scheduled job ([`engine/flows.py`](engine/flows.py)). It's deliberately small: steps run in order, one at a time.

```json
"engine": {"flows": {"weekly-review": {"agent": "main", "steps": [
  {"run": {"tool": "board", "args": ["rows", "query", "tasks"]}},
  {"do": "Summarise what got done this week from the rows above."},
  {"ask": "Post the summary to the family chat?"},
  {"do": "Post the summary to the family chat."}]}}}
```

- `do` is an instruction you wrote: the Agent gets one turn for it in its chat (the earlier steps' results are in the conversation; outputs of `run` steps are added as data). `run` runs a command-line tool or an allowlisted script (as in command jobs); a non-zero exit stops the workflow and says so in the chat. `ask` puts up an inbox card: approve to carry on (a note you add goes to the next step), decline to stop.
- Progress is kept in the database after every step. After a restart, a workflow between steps or waiting for your OK carries on; a step that was cut off halfway isn't redone by itself (it may already have done something): it shows as `interrupted` until you resume it. The emergency stop holds workflows before their next step; `--stop-running` interrupts the step in progress.
- A scheduled job can start one: `{"when": "every monday 9am", "flow": "weekly-review"}` instead of `task` (if the last run is still going, that time is logged as `busy`).
- `GET /api/engine/flows` (definitions, problems, recent runs), `POST /api/engine/flows/<name>/start`, `GET /api/engine/flows/runs/<id>`, `POST …/runs/<id>/stop` and `…/resume`, from your own devices only.

### Standing orders

When you hand an Agent a piece of work for good ("the Friday report is yours from now on", "whenever a new order comes in, tidy it up and tell me"), the `standing-orders` skill ([`packs/core/skills/standing-orders`](../packs/core/skills/standing-orders/SKILL.md), after OpenClaw's standing orders) tells it what to do:

- Write the order down first, in a fixed shape: what it may do, when, what still needs your OK, when to stop and ask, and what it never does. It shows you the text; nothing counts until you approve. It's kept where every later turn finds it: a world-tree manual proposed through `manual_manage` (a card), or a `## Standing orders` section in the Agent's own workspace `AGENTS.md` (the template isn't changed).
- Then make it happen: a scheduled job whose task names the order, a `watch` or `pre` check, a line in the heartbeat checklist, or (set up by you) a webhook, mail trigger or workflow. An order without a trigger is only a sentence.
- Each run is do, verify, report. An order grants no extra rights: things that can't be undone or reach other people still come to you as cards, the emergency stop and spend caps still apply, and text from outside never counts as an order.
- Ask "what are you looking after for me?" for the list; changing or removing an order goes through you the same way, and removing one also removes its job or heartbeat line.

## Model aliases and remembered cooldowns (built-in engine)

- **Aliases** (`engine.aliases`, off until you write it; [`engine/models.py`](engine/models.py)): `{"fast": "deepseek/deepseek-flash", "smart": "moonshot/kimi-k3"}`. An alias is a name without a slash; it points at one real `provider/model` (one level, no alias of an alias). Every place that reads a model reference resolves it first (`engine.model`, `engine.models`, `engine.fallbacks`, `engine.use.*`, `/v1`, the app's model switch, `mousse agent --model`), so changing the alias moves everything that uses it. Aliases that point at pay-as-you-go models also appear in the app's model list. The check for spending your own plan (`may_spend`) always looks at what the alias resolves to: an alias for `claude-code/…` or `chatgpt/…` is a plan like the real reference, other people's turns and the external API never spend it, scheduled jobs and heartbeats don't take plan aliases (write the real reference there), and plan aliases aren't offered in the app.
- **Cooldowns survive a restart** ([`engine/fallback.py`](engine/fallback.py)): rate limits, billing and key errors and missing models were remembered only in memory; now they're also kept in `<data_dir>/engine/cooldowns.json` (0600, written atomically) and read back the first time they're needed, with expired ones dropped. It holds key fingerprints (variable name + short hash), labels, reasons, counts and times, never a key.

## Your Codex or Copilot login as the chat model (built-in engine)

Off by default. With OpenAI's Codex CLI or GitHub's Copilot CLI installed on the server and signed in by you, set `engine.codex` / `engine.copilot` and `codex/default` (Codex's own default model), `codex/<model>`, `copilot/auto` (Copilot picks) or `copilot/<model>` appear in the app's model list and can be the chat model ([`engine/provider_cli.py`](engine/provider_cli.py)). Like Claude Code, only the official command runs, with its own stored login: OpenMousse never reads, stores or passes on its tokens, nor borrows one CLI's login for another, and key-like environment variables (`OPENAI_API_KEY`, `GH_TOKEN`, `GITHUB_TOKEN`…) are removed, along with the ones that point it at another endpoint (`OPENAI_BASE_URL`, `COPILOT_PROVIDER_*`…), so it can't fall back to a key. Each reply is one run of the command in an empty `<data_dir>/<codex|copilot>/<agent>/` folder: the conversation goes in on stdin, the command's own shell, file, web, plugin and hook features are off, and the Agent's tools come only through OpenMousse's MCP with a token for that one reply, behind the same approval rules. Not signed in, or the plan's limit is reached: the reply moves to the fallback chain. Other people's turns, the external API and fallback chains never use them. Compacting a long session on one of these needs `engine.use.compact` set to a pay-as-you-go model.

- **Codex** (`codex exec --json --ephemeral`, read-only sandbox, your `config.toml` and execpolicy rules ignored; checked against codex-cli 0.163.0): signed in with ChatGPT it spends your ChatGPT plan, so it follows that plan's rule: your own turns can use it, background ones only after you allow the plan in the background. It's listed only while `codex login status` says you're signed in.
- **Copilot** (`copilot --output-format json`; checked against Copilot CLI 1.0.100): each reply spends AI credits (premium requests on the older billing) from your Copilot plan. It sees only OpenMousse's tools (`--available-tools`); its shell, write, read, URL and memory permissions are denied; custom instructions, the built-in GitHub MCP, auto-update and exporting the session to GitHub are off; and the folder's `.github/copilot/settings.json` sets `disableAllHooks`, so your own Copilot hooks and plugin hooks don't run (an administrator's policy hooks still do). Copilot saves every run under `~/.copilot/session-state/`, so OpenMousse gives each run its own session id and deletes that one folder afterwards. Copilot has no "am I signed in" command, so it's listed as soon as it's installed and turned on; if you're signed out, the first reply fails over to the fallback chain.
- **`engine.codex`** (optional, default off): `true`, or `{"models": ["codex/default", "codex/<model>"], "max_concurrent": 2}` to choose which models to offer and how many may run at once (the rest wait).
- **`engine.copilot`** (optional, default off): `true`, or `{"models": ["copilot/auto", "copilot/<model>"], "max_concurrent": 2, "background": false, "max_ai_credits": 30, "bin": "/path/to/copilot"}`. `background: true` lets scheduled jobs and other background turns spend it too; `max_ai_credits` (at least 30) caps what one reply may spend; `bin` is needed when `copilot` isn't on the server's `PATH`.
- **Not added**: the Gemini CLI signed in with a Google account (Google's terms for it, dated Apr 10 2026, call using its OAuth through other software a violation and name OpenClaw as the example; add a Gemini API key as an ordinary provider instead). Cursor, Qwen Code and Kimi CLI aren't added either: no terms were found that allow it, or the login has been discontinued.

## A cheaper model for simple lines (built-in engine)

Off by default. With `engine.auto` set, a short, plain line you send yourself ("thanks!", "what time is it in Lisbon?") is answered by a cheaper model, and everything else by the main one ([`engine/auto.py`](engine/auto.py)). A line is simple when it's at most `max_chars` characters and `max_words` words, has at most one line break, and contains no code (a backtick), no link, no picture and none of the words that usually mean real work (debug, implement, analyse, compare, write an essay, 分析, 为什么, 代码 and so on, plus your own `keywords`). It only applies to your own turns (what you type in the app or relay to an Agent; scheduled jobs, the inbox, the external API and ACP are left alone), when the conversation is on the default `engine.model` and that model isn't one of your plans (a flat-rate plan would only cost more). The choice is made at the turn's first model call and holds for the whole turn, through tool calls. If the cheap model fails before it has written anything, it gets the usual cooldown, and the main model answers that line and the rest of the turn. The reply is recorded and priced as the model that really answered, and the app marks it the way it marks a fallback.
- **`engine.auto`** (optional, default off): `{"cheap": "deepseek/deepseek-flash", "max_chars": 160, "max_words": 28, "keywords": ["invoice"]}`. `cheap` must be a pay-as-you-go model that has its key (a plan doesn't count); without it, or with `"enabled": false`, nothing changes.

## Keeping Claude's prompt cache warm (built-in engine)

Off by default. Your own chats on Claude (the Anthropic API) cache the start of the conversation for an hour; come back later and the whole prefix is written again, at twice the input price. With `engine.cache_warming` set, the server resends the conversation's last request shortly before that hour is up, with `max_tokens` 1 and everything else unchanged (system prompt, history, tools, cache and thinking settings), so the cache is read once (a tenth of the input price) and kept for another hour ([`engine/warming.py`](engine/warming.py)). It warms only your own turns in the app (not scheduled jobs, the inbox, other people's turns or the external API), only on Claude with the hour-long cache, and for at most `hours` after you last said something. A warm that fails stops warming that conversation until you speak again; an emergency stop skips warms while it's on; a restart forgets them all. Each warm is recorded as its own turn (conversation `warm:<conversation>`, origin `warming`) with its real tokens and cost, under the `warming` purpose in usage.
- **`engine.cache_warming`** (optional, default off): `true`, or `{"hours": 2, "every_minutes": 55}` (`hours` 0.1–24; `every_minutes` 5–59, so it lands before the hour runs out).

## Enterprise clouds: Azure OpenAI and Amazon Bedrock (built-in engine)

Both are in the model catalog ([`engine/catalog.py`](engine/catalog.py), official pages checked 2026-10-19) and are set up like any cloud provider, with your own address. Neither can list its models, so you type the model name.
- **Azure OpenAI** (`azure`, key in `AZURE_OPENAI_API_KEY`): the v1 API at `https://<your-resource>.openai.azure.com/openai/v1` (or `.services.ai.azure.com/openai/v1`), with no `api-version`. It has no default address: put your resource's address in when you save the key (`python3 setup_ctl.py add azure --url https://<your-resource>.openai.azure.com/openai/v1`); a key without an address isn't saved and doesn't count as connected, and use your deployment's name as the model: `azure/<deployment name>`.
- **Amazon Bedrock** (`bedrock`, key in `AWS_BEARER_TOKEN_BEDROCK`): the OpenAI-compatible Chat Completions on `https://bedrock-runtime.<region>.amazonaws.com/openai/v1` (US East and US West to pick from; any other Region by editing the address). Use a long-term Bedrock API key from the Region it was made in (short-term keys expire within 12 hours and aren't renewed here), and a Bedrock model ID as the model: `bedrock/openai.gpt-oss-120b-1:0`.
- Their prices aren't in the price list, so usage shows their tokens without a cost. Google's Vertex AI isn't added: its OpenAI-compatible API takes a one-hour OAuth access token rather than a key that can be stored.

## More of the external API (built-in engine)

These add to the OpenAI-compatible `/v1` ([`engine/openai_api.py`](engine/openai_api.py)). Each is off by default and needs `engine.api` on first; the tokens (`api`, `api-<agent id>`), Agents, inbox cards and sessions are the same as for `/v1/chat/completions`.

- **`/v1/responses`** (`engine.api.responses: true`; default off, and every route below is a 404 until then): OpenAI's Responses API, for programs that only speak that. `POST /v1/responses` runs one turn: `input` is text or a list of messages (`input_text` / `input_image` parts; other item types are a 400), `instructions` apply to this turn only, `previous_response_id` carries on the same session, and `store: false` keeps nothing. `stream: true` sends the Responses events (`response.created` … `response.output_text.delta` … `response.completed`, or `response.incomplete` / `response.failed`). Usage comes back as `input_tokens` / `output_tokens` / `total_tokens`. `GET` and `DELETE /v1/responses/{id}` fetch or delete a stored reply, only for the token that made it. Replies are kept in `mousse.db` (`engine_api_responses`, created on first use), the last 100 per token, and survive restarts. The caller's `tools`, `temperature` and so on are ignored: the Agent uses its own tools and settings.
- **Session history and ACP `session/load`**: `GET /v1/openmousse/history?id=<session key>[&agent=<id>][&limit=200]` returns what was said in one of this token's own sessions, oldest first and across days (user messages, replies, thinking summaries, tool calls with the start of their results); another token's session or an unknown key is a 404, and more than `limit` (at most 1000) gives the latest ones with `truncated: true`. The ACP adapter ([`engine/acp.py`](engine/acp.py)) now advertises `loadSession`: `session/load` replays the latest 500 items as `session/update` notifications (`user_message_chunk`, `agent_message_chunk`, `agent_thought_chunk`, `tool_call`) before it answers, then the session carries on like `session/resume`.
- **A2A for your own agents** (`engine.api.a2a: true`; default off, and every route below is a 404 until then): each Agent is an A2A 1.0 agent (JSON-RPC binding) for your own other agents and A2A clients, with the same `api` / `api-<agent id>` tokens ([`engine/a2a_api.py`](engine/a2a_api.py)). This is separate from the friends-facing A2A at `/f/a2a`. `GET /v1/a2a` lists the Agents this token can use. `GET /v1/a2a/<agent>/agent-card.json` is that Agent's card (it needs the token; the endpoint URL follows `X-Forwarded-Proto` / `-Host` behind a proxy). `POST /v1/a2a/<agent>` takes `SendMessage`, `GetTask`, `ListTasks` and `CancelTask`. Streaming, push notifications and the extended card return UnsupportedOperation, and 0.3 method names return VersionNotSupported. A message is one turn, like `/v1/chat/completions`: its text parts (and raw PNG / JPEG / WebP / GIF images) are the line, `contextId` is the session (keep sending it to carry on), and a repeated `messageId` returns the first task. The reply is always a task. `TASK_STATE_COMPLETED` carries the reply in `status.message` and an artifact. `TASK_STATE_AUTH_REQUIRED` means an approval card is waiting in your inbox, and the task turns `COMPLETED` on a later `GetTask` once you've decided. `TASK_STATE_FAILED` gives the error. `configuration.returnImmediately: true` answers with `TASK_STATE_WORKING` straight away, for `GetTask` to poll. Tasks are kept in `mousse.db` (`engine_a2a_tasks`, created on first use), the latest 200 per token.

## Agents

"New Agent" in the app = a separate agent in your OpenClaw: its own workspace (AGENTS.md / IDENTITY.md / MEMORY.md), skill allowlist, routing. See [`agents.py`](agents.py). With the built-in engine (or another claw) nothing goes into `openclaw.json`: an Agent is a row in OpenMousse's database and a conversation of its own with the same engine, which knows the Agent's name and role. From the command line:

```bash
python3 agent_ctl.py list
python3 agent_ctl.py create --name Sleep --purpose "Interpret last night's sleep every morning." --icon moon --color purple
python3 agent_ctl.py update g-xxxxxxxx --name "Sleep & recovery" --color default   # only the fields you give change
python3 agent_ctl.py delete g-xxxxxxxx      # workspace archived to ~/.openclaw/archive/, never deleted
```

With `packs/core/skills/agent-builder` installed on the main agent (the installer does this) you can create Agents from chat.

| Endpoint | What it does |
|---|---|
| `GET /api/groups` | Every Agent: `{id, name, icon, color, purpose, modelId, dashboard, lastLine}`. `color` is null when unset (the app's default color) |
| `POST /api/groups` | `{name, purpose?, icon?, color?, model, skills?}` → `{ok, id}`: builds the OpenClaw agent, then the row; if a step fails nothing is left behind |
| `PATCH /api/groups/{id}` | `{name?, icon?, color?, purpose?, model?}` → `{ok, group}` (`group` has the same shape as in GET). Only fields you send that actually differ change; `color: null` = back to the default |
| `DELETE /api/groups/{id}` | Removes the OpenClaw entry and the routing; the workspace moves to `archive/` |

The first extra Agent turns a one-agent OpenClaw into a multi-agent one. OpenClaw then requires `agents.ownership: "explicit"` in `openclaw.json` and stops falling back to "the only agent", so in the same write the server does what OpenClaw's own `openclaw agents add` does: the agent you already had (normally `main`) is written down as the owner of what it handled implicitly: a channel-wide binding for each channel configured in `openclaw.json`, the heartbeat, system work (`agents.defaults.systemAgent`) and Talk. Channels turned on only by environment variables or a login aren't in the file: bind those yourself (`openclaw agents bind --agent main --bind <channel>:*`); `openclaw doctor` lists them.

POST and PATCH check the same things: the name can't be empty (400) or the same as another Agent's, ignoring case (409); `icon` is an icon key, lowercase letters and hyphens, at most 24 characters (the app ships moon, dumbbell, utensils, book, wallet, briefcase, heart, plane, coffee, music, camera, code, cart, home, car, paw, leaf, gamepad, palette, globe, graduation, lightbulb, trophy, pill); `color` is one of cyan, gold, green, purple, pink, orange (400 otherwise).

What a PATCH touches besides the database:

- **icon, color**: nothing else.
- **name or purpose**: the Agent's `IDENTITY.md`, so the agent knows. Only the block between `<!-- mousse:role -->` and `<!-- /mousse:role -->` is replaced: a "Role (set in the app; this wins)" section with the name and the purpose. Everything outside the markers, hand-written or written by the agent, stays byte-for-byte as it was. No block yet → it's appended at the end (the file is created if missing); new Agents get it from the start. The old file is copied to `backup_dir` first.
- **model**: the Agent's default model in `openclaw.json` (`agents.entries.<id>.model`, nothing else in the file), with the same steps as creating an Agent: back up, write, `openclaw config validate`, restore on failure. An existing `{primary, fallbacks}` keeps its fallbacks; an Agent that followed the default model gets the default fallback chain copied, so it keeps falling back. An id without its own entry (such as main) → 400. The app's thread for this Agent switches to the new model too.
- Everything is checked before anything is written. If the model can't be written (502), `IDENTITY.md` is put back and the database is unchanged.

## Cybers (built-in engine, off by default)

Two kinds of Agent: functional Agents do things (the Agents above: one area each, they can act); Cybers think with you: a name, an avatar, a personality, a model and a memory of their own, and they only talk. See [`cybers.py`](cybers.py). A Cyber isn't a row in `groups` and never becomes an OpenClaw agent: it has its own table and the engine runs its cyber turn ([`engine/cyber.py`](engine/cyber.py)).

- **Off by default.** `"cybers": true` in `server.json` (with the built-in engine) turns it on; without it every `/api/cybers…` answers 404 and the app shows no entry for it. Installs that already exist stay off until you turn it on.
- **What's stored** (table `cybers` in mousse.db): id `cy-<8 hex>` (also the thread of its one-to-one chat), a number (`No. 07`, never reused), name, tag (shown after the name in contacts and group chats), kind (`pro` / `friend` / `machine` / `blank`), avatar, three personality lines (`identity`, `tone`, `rules`), voice, model (`provider/model`; empty = `engine.use.cyber`, then `engine.model`; your own Claude Code / ChatGPT plans can't be picked for a Cyber yet) and when it was created. Deleting a Cyber keeps the row and its chat, moves its memory to the archive and takes it off every list.
- **Avatar**: a half-length figure built from parts `{hair, hairColor, beard, collar, clothes, skin, bg, accColor, acc: {glasses, phones, earring, hat}}`, a picture you uploaded first through `/api/chat/upload` (`{"upload": <attachment id>}`, kept only on this server), or for the machine kind a line icon `{"machine": "timer" | "sides" | "rewind"}`.

| Endpoint | What it does |
|---|---|
| `GET /api/cybers` | `{cybers}`: the ones not deleted, most recent conversation first |
| `POST /api/cybers` | `{name, tag?, kind?, template?, avatar?, identity?, tone?, rules?, voice?, model?, loadout?}` → `{ok, cyber}`. Same name as another Cyber (ignoring case) → 409, so an @ in a group can't be mistaken; `loadout` follows the loadout rules below |
| `GET /api/cybers/{id}` | One Cyber: number, created, `days` together, model in use (`modelInUse`, `modelName`), last line |
| `PATCH /api/cybers/{id}` | Only the fields you send that actually differ; `model: null` = back to the default |
| `DELETE /api/cybers/{id}` | Delete: its memory moves to the archive, nothing is erased |

- **Two default Cybers**: once Cybers are on, the server creates Iris (host: follows up one question at a time, never draws your conclusions, sums up at the end) and Zhe (the layman: says so when lost, asks for examples), in the server's language, at start-up or the first time the app lists Cybers or contacts. Only once: delete one and it stays deleted; if you already have a Cyber with that name it isn't created. Podcast prep will use them as host and layman. Installs without Cybers on see nothing.
- **Talking one to one**: a Cyber's chat is the thread with its id. `/api/chat/send` there runs a cyber turn instead of an owner turn (`chat.engine_stream` hands it to `cybers.respond` → `engine/cyber.chat`: its own session for the day, `cyber:<id>:<day>`, with its personality lines and your card). The stream events, the `messages` rows, unread and pins are the same as any chat, so the app's chat page draws it unchanged. The reply's `modelId` is the Cyber's model. Cyber turns never spend your Claude Code or ChatGPT plan: when the Cyber's default (`engine.use.cyber`) is a plan, a model with an API key is used instead.
- **Memory, three kinds**: the card (every Cyber knows it: what your card agent shows the "friend" tier, such as your name and what you're working on), what it kept (notes it grows itself, only from your talks, each one kept only once you approve; you can see, delete or clear them) and its knowledge base (material you gave it, or reports it read, each with where it came from). The most recent notes and the latest knowledge go at the end of its opening; older notes and passages related to what you just said follow your message as data. Health, diet and sleep are never given to a Cyber, and it doesn't keep notes about them. Endpoints: `GET /api/cybers/{id}/memory` (the profile's Memory card), `GET /api/cybers/{id}/notes`, `DELETE /api/cybers/{id}/notes/{note}`, `DELETE /api/cybers/{id}/notes` (clear), `GET` / `POST /api/cybers/{id}/knowledge` (`{title, text}` or `{file: <attachment id>}` for an uploaded document), `DELETE /api/cybers/{id}/knowledge/{item}`.
- **Changing it**: every change shows the result first (before → after) and is written only when you approve; each one is a version you can undo. Three ways in, one interface. **Said in the chat** ("from now on, recommend five"): the cyber turn has a propose-only tool, `propose_change` ([`engine/cyber_tools.py`](engine/cyber_tools.py), only in cyber turns, at most 3 per reply), for its identity, tone, rules, tag or a note to keep. **Proposed by the Cyber itself** (review, daily read). Both become an inbox card (kind `tool`, the `cyber:change` call through [`engine/calls.py`](engine/calls.py)) in that Cyber's chat; approve runs it once. **A row on the profile page**: `POST /api/cybers/{id}/changes` with `{field, value}` (the new line as written), `{field, tweak}` (`stricter` / `gentler` / `shorter` / `english` / `examples`) or `{field, ask}` (a sentence saying how), or just `{ask}` from the box at the bottom of the profile (the model picks at most two items, a note included); tweak and ask are rewritten with one tool-free call of your own (`llmjson.ask`). It answers with the result (`changes`, before → after) and no card; apply or drop it with `POST /api/cybers/{id}/changes/{change}` `{action: apply | drop}` (which also withdraws a card for the same change). `GET /api/cybers/{id}/changes` lists what's waiting (cards you declined or withdrew drop out) and the recent versions (with the card's `inbox` id when one came from a card); `POST /api/cybers/{id}/undo` `{version?}` puts back the previous value (only the latest change to an item; undoing a note deletes it). Direct edits with `PATCH` are versioned the same way.
- **Growing on its own (off by default)**: `"cybers": {"review": true}` (every 6 turns; `{"review": {"every": n}}`) makes it look back over the recent talk now and then with one tool-free call on its own model: what's worth keeping, and whether its tone or rules should change after something you said. Each idea becomes a before → after card; nothing changes until you approve. It's a new background cost, so it stays off until you turn it on, and it doesn't run during an emergency stop.
- **Loadout: the personality belongs to the Cyber, the skills to functional Agents.** Load a functional Agent on a Cyber and it can use it; unload it and the link is gone; the data always stays with the functional Agent, and one Agent can serve several Cybers. In the chat the Cyber gets one tool, `ask_agent` ([`engine/cyber_tools.py`](engine/cyber_tools.py), only in cyber turns), whose target can only be an Agent on its loadout. That Agent answers in a read-only turn of its own (its usual tools without handoff or reading your other sessions, told that the question comes from a Cyber on another company's model so it answers only what's needed); read-only results come back to the chat, and anything that would change your data (board, schedule, goals, journal…) becomes an inbox card in the Cyber's chat that only you can approve; approving runs exactly that call once. The Agent's turn never spends your Claude Code or ChatGPT plan, the Cyber can ask at most 3 times per reply, and the Agent can't hand it on, so there's one hop. Both sides keep a record: the Agent's chat gets a grey line "The Cyber … asked (read-only)" and its answer (not unread, not reordering). Health Agents can't be loaded: an Agent with the built-in `diet` or `fitness` dashboard, the icon `heart`, `pill`, `utensils` or `dumbbell`, health, diet or sleep words in its name or purpose, or listed in `cybers.health_agents` (you can add, not remove). Endpoints: `GET /api/cybers/{id}/loadout` (`loaded`, `available` with `health` / `why`, `daily`), `POST /api/cybers/{id}/loadout` `{agent}` (health → 400, at most 6), `DELETE /api/cybers/{id}/loadout/{agent}`.
- **Daily read (per Cyber, off by default)**: `POST /api/cybers/{id}/daily` `{on}`. Once a day after `cybers.daily_at` (default `09:00`), a Cyber with it on reads what its loaded Agents produced that day (output cards and replies their scheduled jobs posted), stores it in its knowledge base with the source ("GitHub radar · 10/20 report") and starts a turn in its own chat to talk about it. One Cyber turn per day each, so it's a new scheduled cost; it doesn't run during an emergency stop.
- **New from one sentence** (Cybers and functional Agents, the same path; [`agentnew.py`](agentnew.py), behind the same `cybers` switch): one sentence or a template → two or three multiple-choice questions (skippable) → a draft with everything filled in → for a Cyber, a one-line trial → create. The questions and the draft are one tool-free JSON call each (`llmjson.ask`, as your own call: your description); the trial is one tool-free call on the Cyber's own model (never your plan). If the model doesn't answer, the questions and the draft fall back to the template and your answers (`fallback: true`). Templates: pro (Rachel the case interviewer, Victor the early investor, "Socrates" the skeptic, Dr. Lin the thesis advisor), friends (Kobayashi the Japanese partner, Zhe the layman, Sam the listener), machines (Quizzer, Contrarian, Retro), and Start blank. A Cyber's draft has name (a number is added if it's taken), tag, kind, the three lines, three avatar presets, a recommended model with one line why ([`cybermodels.py`](cybermodels.py): open-weight first; pro roles get a stronger one, the rest a cheaper one) and up to two Agents to load (never a health one); create it with `POST /api/cybers`. A functional Agent's draft has name and icon (one of the 24), purpose, one table, the first board blocks (picked from latest rows / this week / to-dos / add a row / a note; the queries are built here and drawn once with `boards.plan_board`), reminders and the main chat's model; `POST /api/new/agent` creates it like a nightly proposal does (`data.create_group`, the table, the board) and every reminder becomes a scheduled-job card that stays off until you turn it on. Endpoints: `GET /api/new/templates`, `POST /api/new/questions` `{kind: cyber | agent, text, template?}`, `POST /api/new/draft` `{kind, text, template?, answers?: [{q, a}]}`, `POST /api/new/trial` `{name, identity, tone, rules, model?, tweak?: stricter | gentler | shorter | english | examples, previous?}` → `{line, tone, rules}`, `POST /api/new/agent` `{name, icon, color?, purpose, model?, table?, board?, reminders?}`.
- **Choosing a Cyber's model** ([`cybermodels.py`](cybermodels.py), same switch): `GET /api/cyber-models?cyber=<id>` (or `?class=pro | friend | machine | blank` while creating one; `probe=1` checks local servers again) reads what the model settings already know (`engine/setup_api.connected`: every provider you connected, local servers found, signed-in plans; plus the models the app can switch to and the ones other Cybers use) and ranks it: open-weight first (local ones count as open and cheapest; a closed model gets the note that what it reads goes to that vendor), then the cost tier this kind of Cyber prefers (pro roles a stronger one, the rest a cheaper one; tiers from the price list's output price: under $2 per million tokens low, under $8 mid, otherwise high). Each row has vendor, one line of use, `billing` (`metered` / `local` / `plan`) and `cost`; `recommended` is the top three with one line why (the same pick a new Cyber's draft gets), `local` the models on your computer, and `channels` the four ways to add more (OpenRouter, local models, a vendor's API key, the ChatGPT plan). Your own plans are listed but greyed ("Cybers can't use subscription plans yet"); whether to allow them is a launch question, and `may_spend` is unchanged. Picking one is `PATCH /api/cybers/{id}` `{model}`.
- **Contacts** ([`contacts.py`](contacts.py), same switch): `GET /api/contacts?q=&filter=all | cyber | agent | friend` gives the whole page at once: the butler on top (until the butler arrives this is your card agent, and tapping it opens the card agent page), then Cybers (most recent conversation first, with tag and model), functional Agents (with their purpose, in Agent bar order) and friends (most recent first; a friend whose card has an Agent gets a "Mia's butler" line under them). `q` matches names, tags, models and purposes, ignoring case; every item also carries `keywords` so the app can filter while you type, and `filters` has the four chips with their counts. Read only.
- **In the chat list**: `GET /api/chats?with=cyber` adds a row (`kind: "cyber"`, with `tag`, `model`, `avatar`) for every Cyber you have talked with, ordered like the other rows. Older apps don't know this kind, so without `with=cyber` there is none. Deleting a Cyber goes through `DELETE /api/cybers/{id}`, not `/api/chats`.

## Group chats (built-in engine, off by default)

A meeting is for deciding (minutes and to-dos, see [`../docs/meetings.md`](../docs/meetings.md)); a group chat is for bouncing ideas off your own Agents and getting different views. They are two entries under +. A group chat has you plus your own Cybers and functional Agents (friends come with the butler, later). See [`groupchat.py`](groupchat.py).

- **Off by default.** `"groupchat": true` in `server.json` (with the built-in engine) turns it on; without it every `/api/groupchats…` answers 404 and the app shows no "New group chat". Installs that already exist stay off until you turn it on. Cyber members also need `cybers` on.
- **Stored like a meeting**: a group is the thread `gc-<8 hex>`; its messages are `messages` rows with `speaker` and `meta` (yours `user`, members' `grava` (the internal value for the assistant's side) with `origin = group`: unread, never pushed; system lines `auto`). Table `groupchats` holds the name, optional topic, members in speaking order (Cyber `cy-…` and Agent ids, 1–8) and from which message each one joined, the host (`main` = the assistant, a Cyber's id, or empty = none), how members speak (`mention` / `host`), the source (an idea or a podcast episode) and the round. `/api/chat/send` refuses group threads (400).
- **Who speaks**: you, any time; an Agent only when @-mentioned. @ one (or a few) and they answer in that order. **@All Agents = one round**, the meeting's round (`meetings.run_round`, shared through `MeetingRoom` / `GroupRoom`): everyone once, in order; an @ inside a reply goes one hop. A group created with a topic starts with one round. With **"Host decides"** (`mode: host`, needs a host), after a message of yours with no @ the host decides whether one member should answer (one at a time; at most 3 per message of yours, and not someone who just spoke). With no host there is only @.
- **The host** is the assistant in this group's own context (a tool-free `llmjson.ask` call that only sees this group, never the main chat's), one Cyber (a tool-free call on its own model; never your plan) or nobody. It only picks the next speaker (in "Host decides") and writes the summary after a round.
- **Each member speaks in its own turn**: a Cyber in a cyber turn ([`engine/cyber.py`](engine/cyber.py) `speak`: never your plan; its loadout tool `ask_agent` included; conversation `group:<group>:<cyber>`), a functional Agent with its own opening (who it is, its workspace files, your profile, its branches of the memory tree, its diary and last digest) and no tools, on the model picked in its chat. Each time it reads only this group's settings (name, topic, who's in, the host, the rules), the pinned summary, the latest 20 messages (none from before it joined) and the message that @-mentioned it.
- **Only ideas in the group.** Anything to do (add to the schedule, change a board, set a goal, message someone) a member writes on its own line starting `【要做】` / `[To do]`; the server turns it into an inbox card only you see (kind `other`, "From X · for Y"): a functional Agent's line goes to that Agent, "hand to <Agent>: …" goes to that Agent, everything else to the main chat. Approving hands it over the usual inbox way (the Agent does it in its own chat and reports done). A Cyber's `ask_agent` changes stay cards in its one-to-one chat and are listed in the group too. Health, diet and sleep Agents can't share a group with a Cyber (or a Cyber host): the Cyber's model reads every message.
- **Group content goes on hold, not into the tree**: once a stretch has been quiet for 30 minutes (or the group ends), the same tool-free, plan-free call as the write-back for the card agent ([`engine/writeback.py`](engine/writeback.py)) picks what might be worth remembering, and the server keeps only items that pass the three tests and whose quote really is in the group; they go to `memhold.hold(channel="group")` with who said it and the quote, for you to approve one by one. A member's guess about you doesn't count as something you said. Off when `engine.writeback` is false.
- **Summaries go into the group's memory**: after a full round with a host, the host writes that round's summary (the assistant: a tool-free `llmjson.ask` call written like meeting minutes; a Cyber host: its own model). It doesn't overwrite the last one: it goes into the group's memory (`group_memory`): decided (with round, day and "you agreed" when you said so), still disputed (one line per side; a point settled later is put away) and what each member kept. The latest summary is pinned on top, and every later turn (the next round, or tomorrow) reads it. What a Cyber kept is proposed to its own memory the usual way (a before → after card in its one-to-one chat, `via: group`); nothing is kept until you approve. A summary goes back to where the topic came from: for a group opened from an idea, the idea's note gets one block (between `%% mousse:group <id> %%` and `%% /mousse:group %%`, an Obsidian comment, hidden in reading view) that is replaced with the latest memory each round. With no host there is no summary and nothing is written back.
- **Three actions under a summary**: write back to the idea (no source idea → the summary becomes a new Zen thought and the group writes back to it from then on), start a meeting (topic = what's still disputed, members = the ones in the group that can join a meeting, started by you) and make it a podcast (a new episode with that summary as material). Each is recorded on the summary (`actions`), so the app shows "Written back", the meeting or the episode.
- **When a group ends** the main chat gets one line ("The group chat … is over; the summary is in its memory:") with one summary card under it (`/api/chat/cards`, a `minutes` card with `group: true`: decided and still disputed; tapping opens the group). A group with no summary tells the main chat nothing. Deleting the group removes that line too.
- **Usage per group per day** (`group_usage`): Agent messages, model calls and tokens (estimated from the text when a call doesn't report usage, marked "about").
- **In the chat list**: `GET /api/chats?with=group` adds a row per group that hasn't ended (`kind: "group"`, `members`, `faces` = the first four members, the latest line, `state` working while someone speaks or waiting while a card waits for you); ended ones are in `?archived=1&with=group`, and `endedGroups` counts them. Pin and mute work as usual; `DELETE /api/chats/{thread}` deletes the group. Unread counts in `/api/unread`.

## The butler (built-in engine, off by default)

The butler is the card agent, upgraded: you still have one outside identity. It talks the same way (an outsider turn with no tools, only what the tier releases, every reply checked by Doorman before it goes out, a card for anything you have to decide); [`butler.py`](butler.py) wraps [`cardagent.py`](cardagent.py) and adds a profile, example answers instead of the tier table, Cybers it may consult, and what it said.

- **Off by default.** `"butler": true` in `server.json` (built-in engine) turns it on; without it every `/api/butler…` answers 404, the contacts page keeps the Card agent row and the app keeps the My card agent page. Installs that already exist stay off until you turn it on.
- **Profile**: the name (yours, or "<your name>'s butler" until you pick one; friends see it), the look (ring and dot by default, or one you build like a Cyber's), the model (the `card` use in model settings; read here, changed there), and how many lines it said this week and Doorman held.
- **Example answers**: for each tier it tries a few common questions ("Are you busy this week?", "What have you been up to lately?", "Where do you live?") the same way a real reply goes (the tier's material, the model, the server's checks), but without Doorman, cards, sending or logging; answers are cached until the tier or the material changes. "Change this line" picks another level for that kind of question (plans: share the plans / only busy or free / don't say), shows the new answer first, and writes `social.tier_scopes` only when you apply it; every change is recorded and can be undone.
- **Fixed rules** (no switches): making plans, promising things, money and requests for your details always become a card only you see; health, diet and sleep are never said and never seen.
- **Consulting Cybers**: only the Cybers you list. The server first turns the question into its gist with a no-tool call (names and the original wording removed, then checked again: a gist that still copies most of the question is dropped), then runs that Cyber's turn (`engine/cyber.speak`: kind cyber, never a plan, no tools, a conversation of its own) and labels the answer "Victor's view: …". Health, diet and sleep questions are never taken to a Cyber. Each consultation is recorded for you only (`butler_consults`).
- **What it said**: every line it sent out in the last days (`card_log`), held ones included with the original and the reasons; Release / Keep go through the existing review card (`POST /api/inbox/{id}`, hook `cardagent.release`).

### Friend groups (with the butler)

You and a few friends in one group: messages are end-to-end encrypted, and your side has only your butler speaking for you ([`friendgroup.py`](friendgroup.py); the protocol is in [docs/social-protocol.md](../docs/social-protocol.md) 7.1).

## Chat: queueing, stopping, quoting

- A conversation has one reply running at a time. What you send while it's replying (`/api/chat/send`) no longer gets a 409: it's stored right away (status `queued`, shown as "Queued" in the app), the SSE answers with a `queued` event and the connection waits. When the reply ends (or is stopped), the queued messages go to the model as one turn (numbered, after a note asking it to start each separate answer with its own line `> 「their words」`; the app draws that as a quote that jumps back to the message), and every waiting connection attaches to that turn. On startup, messages still queued from before a restart are sent if they're under 30 minutes old, older ones are marked as not sent. Timers and other system triggers (`/api/chat/trigger`) still get a 409 when the thread is busy; relays queue instead (below).
- `POST /api/chat/stop` `{thread}` stops the reply in progress by closing the connection to the Gateway, which aborts the turn. What was already said stays, with "(Stopped)" appended, status `stopped`, no push. Queued messages go out next.
- Long-press → Quote: `/api/chat/send` carries `replyTo` (`db<id>`). The model gets the quoted line as context, the message stores `reply_to`, and `/api/chat/history` returns `replyTo {id, role, text}` for the app to show above the bubble.
- With the Gateway's WebSocket chat channel (server.json `chat.transport: "ws"`, see `gateway_ws.py`), what you send mid-reply is not queued but **cut in**: `chat.send` with `queueMode: steer` hands it to the model at the turn's next step, and it stays one reply (the message is stored as `steered`, shown as "Cut in"). If the Gateway couldn't steer it and ran it as its own turn, the server adopts that turn as this message's reply. Stop uses `chat.abort`. Turns run to completion inside the Gateway: a reply still running when the server restarts is adopted or recovered from `chat.history` on startup. Messages with images still go over HTTP (and queue). The first connection pairs automatically on loopback; the device identity lives in `<data_dir>/gateway-device.json`.
- **The built-in engine** cuts in the same way (`steered`, read after the current batch of tool calls). A cut-in the turn ends before reading is not lost: it goes to the front of the queue and becomes the next turn, and since 2026-10-20 the turn's own stream (the connection of the message being answered, and of any cut-in that made it) says so first with `event: steer_missed` `{userIds: ["db<id>", …]}`, so the app changes "Cut in" to "Missed this turn" for those messages at once. Their own connections stay open and attach to that next turn as before. Older apps ignore the event.
- **Progress while it works** (WebSocket channel only, 2026-10-05): the Gateway's `agent` events on the same connection carry the turn's preparation phase (`run_status`), each tool step (`item`, its model-written title and status) and the model's thinking summaries (`thinking`). The server folds them into one snapshot and sends it on the reply's SSE stream as `event: progress` `{since, phase, steps: [{id, tool, detail, status: running | done | failed}], thought}` (the last 6 steps, the last 600 characters of thinking; a re-attaching client gets the current snapshot first). Command arguments and output are never forwarded. Over HTTP there is no progress; the app still animates while it waits.
- **With the built-in engine** the same `progress` event comes from the engine's own events (`chat.note_engine`), and since 2026-10-20 each step also carries `label` (the step in plain words, "Check the schedule"), `doing` ("Checking the schedule", for the title line while it runs), `note` (what the label doesn't say: a file name, a site's domain, a skill name, a device, an app's tool, or the title of a background task or a plan; `""` when there's nothing; never the command, search words, a prompt or text to read aloud) and `wait: true` once the step became an approval card ([`engine/steps.py`](engine/steps.py)). These are only added: `detail` still carries the tool's title (with "· awaiting your approval" after it for an approval card), so older apps draw the step as before.
- **Model switches while it works** (built-in engine, 2026-10-20): when the fallback chain moves to another model mid-turn ([`engine/fallback.py`](engine/fallback.py); a different key for the same model doesn't count), the reply's stream gets `event: model_switch` `{from, to, reason}` right away (reason as in `fallback.py`: `rate_limit`, `overloaded`, `server`, `timeout`, `network`, `auth`, `billing`, `model_not_found`, `context_overflow`, `cooldown`; `quota` / `broken` / `auth` when your own Claude Code is swapped out, [`engine/owner.py`](engine/owner.py)), and a re-attaching client gets the latest one again. `done` then has `fallbackReason` (why the requested model wasn't used, the first switch's reason) next to `fallbackFrom`; it is only in that event, not stored, so a re-read history has `fallbackFrom` alone. Older apps ignore both.
- **When a background task finishes** (see [`settle.py`](settle.py)): OpenClaw runs one more turn in the conversation that started the task so the model can report back (run id `announce:v1:<sub-session>:<run>`, or `announce:requester-settle:…` when the starting turn yielded or several tasks settle together). Its reply is delivered to the channel the task came from, which for the app used to mean only the Gateway's own web UI. Now, for tasks started from the app (`requesterOrigin.channel` = webchat) in a thread the app knows, the chat gets a grey line "Background task finished: <title>" (role `auto`) followed by that turn's reply. Over the WebSocket channel the server adopts the turn live (the reply streams like any other, cards from that turn hang under it); on both transports a catch-up pass every 30 s reads `chat.history` for tasks delivered in the last 30 minutes and fills in any it missed (HTTP transport, restarts, dropped connections). `settle_replies` in mousse.db records which turns were handled, so nothing is written twice. A task that finishes while the turn that started it is still running is folded into that turn by OpenClaw, and there's nothing extra to add. Tasks started from Telegram are answered there. No extra push: the quiet "task done" push already covers it; the reply counts as unread.
- `GET /api/chat/busy` → `{running, queued, idle}`. To restart the server use `python3 safe_restart.py --unit <service>`: it waits until no reply is running and nothing is queued (up to 10 minutes), since a restart cuts off replies in progress.
- **Talk mode** (phone app, 2026-10-19; feature `talk`): a talk button in the main chat's header opens a full-screen page that listens, ends a sentence after a 1.5 s pause, transcribes it with `POST /api/chat/transcribe` (the same paid call as voice input), sends it to the conversation as your own message and reads the reply aloud sentence by sentence as it streams (the phone's built-in voice; code blocks and tables are skipped with a note), then listens again. Tapping, or starting to speak, interrupts the reading; the reply is still written out in the chat. `GET /api/chat/transcribe` → `{ready, why}` tells the app whether transcription is set up (it only checks that `OPENAI_API_KEY` is there; nothing is sent out). Nothing runs in the background: leaving the app pauses it.

## Handoff and task cards

When the main chat hands a question to an Agent (`scripts/ask_agent.py` → `/api/chat/relay`) or starts a background task (OpenClaw `sessions_spawn`), the chat shows a card. See [`cards.py`](cards.py).

- **Handoff card**: appears as soon as the question goes out ("asking Diet…", with the question as sent), turns into "handed to Diet · 34 s" when the answer is back, and sits under the reply that asked. Tap it to open the Agent's chat at that question. The relay run itself is recorded in `handoffs` (mousse.db); the reply that asked is the one mid-reply when the relay arrives (the script can't tell which session called it; main-agent threads win, then the newest). With the built-in engine the script does know (`source` in the relay, see [Other sessions…](#other-sessions-handing-over-between-agents-and-mousse-agent-built-in-engine)), so the card records that conversation, Agents can hand over too, and the Agent-side line says which Agent it came from. Since 2026-10-05 a relay to a busy Agent waits for it instead of failing: the card shows "busy · queued" (`queued`), the question goes in as soon as the Agent is free (after any messages you queued there yourself), and the whole wait counts toward the relay's `timeout`. If it's still waiting when that runs out, the relay returns 200 with `status: queued` and keeps waiting in the background for up to 15 minutes; the answer lands in the Agent's chat and the card follows. Waiting relays count in `/api/chat/busy`, so `safe_restart` waits for them. Older records may still say `busy` (refused with 409 before this change).
- **Task card**: read from OpenClaw's task ledger (`<openclaw_home>/state/openclaw.sqlite`, tables `task_runs` / `subagent_runs`, read-only, a few ms per read instead of a 2-second `tasks.list`). While a reply is running the server looks every 2 s for tasks that session started and sends them over the same SSE stream (`event: card`), so the card shows up mid-reply; when the reply ends they are attached to it (`task_links`). Running: the step it's on ("reading L2.pdf", from the sub-session's transcript, read at most every 20 s). Done: the start of the result. "Revise" sends notes to the same sub-session (`POST /api/tasks/{id}/revise`); rounds, notes and each round's result come from the `task:<id>` thread.
- **Allowance**: `server.json` → `tasks: {daily_limit: 10, max_minutes: 30, notify_done: true}`. It's a number for the Agents to check (`tasks_ctl.py quota`, exit code 3 when used up); what actually stops a long task is OpenClaw's `agents.defaults.subagents.runTimeoutSeconds`.

```bash
python3 tasks_ctl.py quota   # started today, the limit, how many are left
python3 tasks_ctl.py list
```

## Meetings

Several Agents take turns on one topic while the main chat's agent hosts and writes the minutes; confirmed to-dos go into the schedule and each Agent's dashboard. Start one in the app (+ → New meeting) or from the main chat (`ask_agent.py --meet`). Each member speaks in its own OpenClaw session `agent:<id>:grava:grp-<id>` (`grava` there is an internal value in the session key, kept so older sessions are found again); at most one turn per Agent per round, @ goes one hop, and a round costs at most one reply per member + 1 for the minutes. See [`meetings.py`](meetings.py); rules, data and the API (`/api/meetings…`, chat cards `meeting` / `minutes`) are in [`docs/meetings.md`](../docs/meetings.md). Since 10/21 (built-in engine) Cybers can attend, "tell me when it's settled" (`auto`, for meetings you start in the app, with `by_origin` below on) runs a meeting to the end by itself, and `GET /api/meetings/records` lists and searches every meeting. `"meetings": {"by_origin": true}` (off by default; existing installs keep the old behaviour until you turn it on) decides where a meeting lives by who started it: yours stay in the chat list, the assistant's and fully automatic ones leave it when they're done (the main chat's row says "In a meeting" while one runs, and keeps the minutes card).

## Schedule and "To remember"

One timeline per day and one list of things to remember, both editable. See [`schedule.py`](schedule.py).

- **Schedule** = the timetable (the optional `calendar` source, read-only) + a layer the server keeps itself (`schedule_items` in mousse.db: the user's own plans and the ones Agents put in) + deadlines due that day, each with a tick. The timetable can't change, but this layer can mark a class "not going" (`series` = every week), move its place, add a note. Past days record what actually happened: went / didn't, done / didn't, actual times (a workout planned with key `<agent>:training:<date>` gets its actual time from the workouts source).
- **To remember** = coursework deadlines (`study.deadlines_cmd`) + things pulled out of email (`remember.mail`, below) + application deadlines (`applications`) + the user's own deadlines. Each thing shows up once: the day it's due it moves into that day's timeline. Groups: `security` (pinned), `overdue`, `tomorrow`, `week`, `later`, `nodate`, `news` (undated money / status mail).
- **Tick** = done or not needed (`schedule_marks.done_at`): gone from the list, and scripts that remind (a reminder script in your workspace can read `schedule_marks` too) stop mentioning it. Ticking a mail item also runs `remember.mail.cmd --done <id>` (untick: `--undo`); fixing one (`/api/remember/edit`) runs `--edit <id> --json …`.
- **Changes by Agents** (via `schedule_ctl.py`, which calls this API with `source`): while an Agent is replying, a `schedule` card goes out on its SSE stream; when the reply ends the change is attached to it (`schedule_log.message_id`). Every change can be undone (`/api/schedule/undo/{id}`). An Agent re-adding with the same `key` updates that item, but never overrides a time the user moved himself.
- **iPhone calendar**: `GET /cal/<token>.ics` is outside `/api` and needs no token header; the token in the link is the password (rotate it in the app). Four switches: classes (off by default, so a timetable already on the phone isn't doubled), yours and the Agents', deadlines, email events.

```bash
python3 schedule_ctl.py day [--date tomorrow] [--days 3]
python3 schedule_ctl.py remember
python3 schedule_ctl.py add --title "Workout · Push A" --date today --start 17:30 --end 18:30 --key fitness:training:2026-09-28
python3 schedule_ctl.py skip "ics:2026-09-28T13:00|Office Hours" --every-week
python3 schedule_ctl.py done "mail:1a0d…:todo"
python3 schedule_ctl.py undo 42
```

## The Today page

`GET /api/today?day=` sorts one day into three blocks and the app only draws them (2026-10-13; `/api/health` lists the feature `today`, and older servers keep the app's previous page). Each block follows one rule, so a thing shows up in one place only; see [`today.py`](today.py):

- **To do** (needs you to act): items waiting for your OK (the inbox), suspicious security alerts, to-dos and deadlines due within 7 days (overdue ones you haven't ticked stay for 3 days), most urgent first: approvals → security → overdue → by date. Each row has a `chip` (Today / Tomorrow / Wed / Due Fri / Security / Overdue) and a `tone` (bad / warn / gold / neutral). Undated to-dos come separately (`nodate`). Swipe-to-postpone writes `today_snooze`; the item comes back on that day. It only affects this page (pushes and the morning report are unchanged).
- **Schedule** (needs you there): classes, what you and Agents scheduled, and timed events from email (tickets, registrations). Entries on the same day at the same time with similar titles (more than half the words shared, or every name in one title appearing in the other's title or text) or the same link merge into one; `refs` lists the merged entries and their states become `tags` ("Ticket"). An email that gives only the start but says "17:00–19:00" in its text gets that end. Past entries with an actual time sit at that time (`slotStart` / `slotEnd`; `moved` = differs from the plan). Training plan and review cards (`training_plan`, `training_review`) attach to that day's entry with key `<agent>:training:<date>` (`cards`).
- **Reports** (to read): Agent cards not attached to the schedule, plus an email digest. The sleep card carries `sleep` (that day's recovery score, time asleep, the last 6 days and the lowest), the meal card `meal` (which meal, what to eat, the totals, how many items were logged that day). The email digest counts money and status items (dated that day; today also the undated ones) by category: bookings, tickets, accounts, charges, refunds, other.
- Other days: To do lists only what was due that day (done or not), without inbox, security alerts or postponing. Scheduled jobs and background tasks aren't on this page.

| Route | What it does |
|---|---|
| `GET /api/today?day=` | `{day, today, weekday, now (today only), pending: {items, nodate}, schedule: {items, allDay, calendar}, reports, errors}`; no `day` = today (in server.json's timezone) |
| `GET /api/today/range?from=&days=` | Week / month views (1–42 days): `{date, type: event / deadline / todo, title, sub, start, end, allDay, done, skip, …}` per entry, events merged the same way; no actual times |
| `POST /api/today/snooze` | `{ref, until}` postpones to `until` (YYYY-MM-DD); `until: null` cancels |

### Categories and to-dos (2026-10-15, optional)

Turn it on with `"today": {"categories": true}` in `server.json` (without it Today works as above; the feature `today.categories` in `/api/health` only says the server knows it):

- **Three categories**: every to-do, deadline and schedule entry has a `category` (`study` / `life` / `work`, see [`todocat.py`](todocat.py)); the app colours circles, schedule blocks and week/month marks by it and can filter by one. Who decides: your own change in the app (`schedule_marks.category`) > what the writer gave (`schedule_items.category`, a mail item's `category`) > the source (timetable and coursework → study; school applications → study, other applications → work; an Agent's items follow its dashboard: fitness, diet, sleep → life) > the wording (bills, returns, appointments, travel visas → life; jobs, interviews, work visas → work; coursework, exams, recommendation letters → study) > life.
- **Undated to-dos**: with `schedule_items.kind = todo` the `date` may be empty; they fold into "No date" at the end of To do (`schedule_ctl.py add --todo --category life --title …`).
- **Overdue items stay**: they no longer disappear after 3 days. 1–7 days overdue stay in To do (`chip` "N days overdue", `overdueDays`), older ones come in `pending.stale` (the app folds them into "Overdue, not handled · N") until you tick them done or dismiss them. Mail items are dropped by their source after the due date; a snapshot (`todo_keep`) keeps them listed, with `kept: true`.
- **Dismiss**: `POST /api/remember/done {ref, how: "dismissed"}`, recorded apart from done (`schedule_marks.resolved`); anything reading `done_at` still treats it as handled. Change a category: `POST /api/remember/category {ref, category}` (`null` = back to automatic). Both can be undone.
- `/api/today` adds `categories: {on, list}` and `pending.stale`, and each row `category` / `categoryAuto` / `categorySet` / `overdueDays` / `kept` / `canDismiss`; `/api/today/range` adds `category`; `/api/remember` has one more `group`, `stale`, and `schedule_ctl.py remember --by-category` prints the three categories apart.

### Engineering board (2026-10-15, optional)

`"today": {"engineering": {"todos": "path to the handoff file", "archive": "glob of archived files (optional)"}}` syncs Claude Code's handoff file (markdown: each `## ` section is a line of work, each `- [ ]` / `- [x]` a task) into `eng_lines` / `eng_items`, read only ([`engboard.py`](engboard.py)), re-reading only when the file changes (no timer). Today's reports get an engineering card (`type: eng`: done this week / not started / waiting on you, and the main line), which opens the board page. Unticked tasks that need you (waiting on you, you decide, sign-off …) count as waiting; ones marked "→ moved to …" or dropped don't count; tasks done in a section that was later moved out still count.

Or read a GitHub Projects board instead (2026-10-19): `"today": {"engineering": {"source": "github", "owner": "user or org", "number": 1, "mainline": "path to a main-line JSON (optional)"}}`. The server runs `gh api graphql` with the machine's own `gh` login (no token passes through it), keeps a read for 5 minutes (1 on the board page), and falls back to the last read (also kept in `eng_gh`) when gh fails, saying when it was from. A line is an option of the board's line field, a task is an item. Waiting → waiting; In progress and Ready to ship → shown as doing (ready-to-ship titles start with "Ready to ship · "); Queued → queued; these three are "not started" in the three numbers. Later is left out of that number, gets its own column, and a line with only later items folds into earlier lines. Field and option names default to the Chinese ones (`fields` / `statuses` override them; GitHub's default Todo / In Progress / Done are understood).

| Route | What it does |
|---|---|
| `GET /api/today/eng` | `{weekDone, todo, wait, main, mainCells, mainNote, lines, older, columns}`: the main line's steps, each line (done / total, status doing / waiting / queued / done) and three columns (not started / waiting / done this week) |
| `GET /api/today/eng/line/{id}` | One line's tasks: not started, waiting, done |

## Projects

Things with an end: they run for days or weeks and have a goal and deadlines (a group assignment, a job-hunt sprint). A project is a chat thread (the old "side chat", id `sc-…`) with a **project card** on top: goal, deadlines, next steps, decisions, progress, the tasks started inside it, and a summary once it's archived. See [`projects.py`](projects.py).

- **Deadlines live in the schedule layer**: your own are `schedule_items` rows (kind deadline, key `project:<id>:…`); existing ones (coursework, mail items, applications, other deadlines) are linked by their ref. Ticking, reminders and "To remember" all work the same, and `/api/remember` / `/api/schedule` entries carry `project: {id, title}`.
- **Carried across the daily reset**: on the first message of the day in a project, and after the card changes, `chat.start_run` puts the card in front of the message (the model sees it, the chat doesn't show it; `side_chats.fed_rev` / `fed_at`). The daily digest script sends each project "【自动触发】日结（项目）" so the Agent updates progress and next steps.
- **Changes by Agents** (`project_ctl.py`, which calls this API with `source`): a `project` card goes out on the reply's SSE stream and is attached to the reply at the end (`project_log.message_id`), undoable via `/api/projects/undo/{id}`. Deadline changes are schedule changes and show `schedule` cards.
- **Opening**: the app or an Agent asked by the user (`POST /api/projects`, optional `brief` handed over into the new project like a handoff). An Agent's own idea goes through the inbox (`POST /api/projects/propose` → kind `project`); approving it opens the project on the server and hands the brief over.
- **Archiving**: `POST /api/projects/{id}/archive {summarize}` moves it to Archived right away and, with `summarize`, sends "【自动触发】项目归档" into the project so the Agent writes the summary (`/conclude`) and its memory entries. `POST /api/projects/review` (called by the daily digest) asks once, through the inbox, to archive projects whose last deadline passed 3+ days ago.

```bash
python3 project_ctl.py done sc-1a2b3c4d pi-5e6f7a8b
python3 project_ctl.py ask sc-1a2b3c4d "What's left before Friday?"

```

## Goals

Long-term goals by area (health / study / career / finance: the category values are the Chinese words 健康 / 学业 / 职业 / 财务, the app translates them), editable by the user in the app and by the Agents from the command line. See [`goals.py`](goals.py).

- **A goal** = a row in `goals`: title, note, due (`YYYY-MM-DD`, `YYYY-MM` or words like "spring 2027"), an optional number target (`targetLow` / `targetHigh` / `unit`, one end is enough), an optional `metric` the server reads by itself (`bodyfat`, `weight`), the Agent that keeps an eye on it (`groupId`), and `status`: active / done / dropped. Nothing is ever deleted: "drop it" is `dropped`, folded at the bottom of the page.
- **Readings**: the body data source (`xunji.py`, one cached query for weight and body fat over 400 days, shared by `/api/goals` and the trend) comes first; Apple Health's daily averages (`health_metrics` BodyMass / BodyFatPercentage) are the cross-check. The current value is the latest of the two (the body source wins on the same day). Body fat is never calculated, only read. Progress runs from the start (the reading on or before the day the goal was set) to the target range, down or up; inside the range is 100 %. A reading older than 30 days is `stale`.
- **Every change** writes a `goal_log` row (who, before / after) and an activity line. Undo restores only the fields that change touched and nobody changed since (`kept` lists the rest; all of them changed since = 409); undoing an add hides the goal. Changes by Agents in the last 24 hours that the user hasn't dismissed come back as `recent`: the app shows them at the top of the Goals page with Undo.
- **Agents** use `goals_ctl.py` (`list`, `trend`, `log`, `add`, `update`, `done`, `drop`, `reopen`, `undo`; `--source` = who is changing it). The skill (`packs/core/skills/goals`): a change the user asked for is made at once; the Agent's own idea goes through the inbox first; no goals the user never stated.

```bash
python3 goals_ctl.py list [--all]
python3 goals_ctl.py add --title "Down to 65 kg" --category health --metric weight --low 60 --high 65 --due 2026-12-31 --agent fitness
python3 goals_ctl.py update goal-1a2b3c --low 18 --high 22
python3 goals_ctl.py drop goal-1a2b3c
python3 goals_ctl.py trend --metric weight
python3 goals_ctl.py undo 12
```

## Meal log

What you eat is logged in the server's own database (since 2026-10-13; it used to be read from Xunji). See [`diet.py`](diet.py) and [`nutrition.py`](nutrition.py); Agents use [`diet_ctl.py`](diet_ctl.py) (or the MCP `diet` tool without a shell), with usage in [`../packs/diet/GUIDE.en.md`](../packs/diet/GUIDE.en.md).

- **Three tables**: `diet_foods`, the personal food library (per 100 g, drinks per 100 ml; usual portions like "1 egg (shelled) = 65 g"; source xunji / off / cofid / usda / label / manual / estimate and where exactly it came from); `diet_entries`, one row per item eaten (date, meal, time, amount, this item's nutrition plus a per-100 g snapshot from when it was logged, `source` = plan / chat / photo / manual / xunji, `estimated`, and a `batch` shared by one write); `diet_targets`, nutrition targets by effective date (a day's target is the latest row on or before it). Deletes are soft.
- **Lookup order** (`/api/diet/lookup`): the food library → packaged food on Open Food Facts (API v3 by barcode, Search-a-licious by name, UK products first; or the user's photo of the label) → the UK's CoFID 2021 (2,887 generic foods, imported from the GOV.UK spreadsheet on first use) → USDA FoodData Central (only with `USDA_FDC_API_KEY` in `.env`); otherwise the Agent estimates and marks it. External results are cached in `<data_dir>/nutrition.db` (safe to delete). Open Food Facts data is ODbL: lookups are cached on this machine only, the library records the source, and the merged library is never shared (shares, the card agent and A2A never include it); the User-Agent carries only the project name and URL.
- **Log this meal in one tap** (`POST /api/diet/log-plan`): logs a meal plan card's `data.meals` (`feed_items` of kind `meal_plan`); `meals` picks which, `scale` scales the whole meal, `items` changes single amounts; the same meal from the same card is never logged twice (409). For older cards whose items only have calories and protein, the meal's carbs and fat are split across items by the ratios of similar foods in the library (never more than the item weighs), so the meal totals match the card.
- **Source**: `diet.source` in `server.json` is `local` (default) or `xunji` (still read from Xunji, until you migrate). `/api/diet/day` has the same shape either way (boards and Today are unchanged); writes always go to these tables. History from Xunji comes in once through [`diet_import.py`](diet_import.py): a read-only export → import (Xunji's `record_id` is the food id and not unique, so the key is date:meal:record_id#occurrence) → a day-by-day check of totals → a migration report.

```bash
python3 diet_ctl.py day
python3 diet_ctl.py lookup banana --en "bananas flesh only"
python3 diet_ctl.py food-save --from cofid:14-318 --name Banana --portion "1 banana=120"
python3 diet_ctl.py add --meal breakfast --item "Banana=120" --item "Egg:1 egg (shelled)×2" --commit
python3 diet_ctl.py log-plan --meal dinner --set 0.1=100 --commit
python3 diet_import.py export && python3 diet_import.py import --file <export> --commit
python3 nutrition.py cofid-import [--file local.xlsx]
```

## Boards, feature packs and reminders

Each Agent has its own tables and a dashboard of blocks it lays out itself; the app draws seven block types from the server-computed data and never computes. See [`boards.py`](boards.py), [`packs.py`](packs.py), [`alerts.py`](alerts.py); Agents use [`board_ctl.py`](board_ctl.py).

**Collections** (block type `collection`, 2026-10-13, [`views.py`](views.py)): after Notion's "same data, many views", one table gets several views, switched by a bar at the top in the app: table (columns, sorting, filters), board (columns by a choice, bool or text field; dragging a card to another column changes that field), calendar (rows placed by a date field, dots coloured by `group`), timeline (bars from a start to a date; the window and ticks come from the server) and chart (`charts` holds 1–6: number, bar, hbar, line, donut). Views reuse the query vocabulary: `where` / `sort` / `group` / `date` / `field` / `agg` (`group_by` / `filter` / `date_field` / `value_field` are accepted too); cards are templates `card {title, meta, tags}`. Views live in the board config, so versions, proposals with previews, undo and history work as before; Agents use `board_ctl.py view list / show / add / update / remove / default` (`--check`, `--propose`). The app shows "needs a newer app" for a view type it doesn't know.

## Pages (web pages written by Agents)

For what blocks can't draw (interactive views you drag or that recompute, custom charts, one-off analysis pages) an Agent writes one web page and the app shows it in a sandbox (2026-10-13, [`pages.py`](pages.py); Agents use [`page_ctl.py`](page_ctl.py) or the MCP tool `page`, see [`packs/core/skills/page`](../packs/core/skills/page/SKILL.md)). Same idea as Claude Artifacts and OpenClaw's `show_widget`, wired to OpenMousse's own data and UI:

- **Versions**: publishing the same `name` again from the same Agent makes a new version with the same id; nothing new is stored when neither the HTML nor the data it reads changed.
- **Sandbox**: the server wraps the document: a CSP first (`connect-src 'none'`, no frames, no form submission, scripts and styles only from jsDelivr / cdnjs / unpkg, fonts from Google Fonts), then theme colors (CSS variables following the app's light or dark mode) and the bridge. The web app puts it in a `sandbox="allow-scripts"` iframe (srcdoc, opaque origin): the page can't read the app's token, sign-in or other data and can't call `/api`; the web shell's `frame-src 'none'` stops it from navigating away with data, and the app stops a page that tries. The phone app (1.0.6 and later, server feature `pages.native`) uses a WebView instead: the document loads as `about:blank` in an incognito WebView without file access, cookies or DOM storage, every navigation to anything other than `about:blank` / `about:srcdoc` is refused and stops the page, and the bridge also removes camera, microphone, location and dialogs there (the web iframe doesn't have them either).
- **Bridge**: inside the page `mousse.data(name)` reads data, `mousse.prompt(text)` puts a line into that Agent's chat composer (you press send), `mousse.page` describes the page (id, title, version, today's date). Messages go through postMessage (in the phone app through `window.ReactNativeWebView`, with results dispatched back as a `message` event); the app accepts them only from that iframe or WebView, rate-limits them and calls the server with its own token.
- **Data and consent**: what a page may read is declared at publish time in `caps.data`: name → a board query Q (`from` / `where` / `sort` / `limit`, at most 1000 rows) over that Agent's own tables and the read-only system sources `health:*`, read-only. The first time you open a page that declares data, the app asks you (which tables and fields); the decision is bound to that version's digest (a hash of HTML + caps), so a changed page asks again. Declining still shows the page; its reads get `not_granted`.
- **Chat cards and boards**: the version an Agent published during a reply hangs under that reply (kind `page` in `/api/chat/cards`); Pin to board on the page adds a block of type `page` at the end of that Agent's board (logged and undoable like any board change).

| Endpoint | What it does |
|---|---|
| `POST /api/pages` | An Agent publishes `{agent, name, title, summary?, html, caps?, note?, check?}`: size (256 KB), external URLs, inline script syntax (`node --check`) and data queries are checked first; `check: true` checks without saving |
| `GET /api/pages?agent=`, `GET /api/pages/{id}` | Page list, one page (version, `needs` = tables and fields it reads, `grant` = your decision) |
| `GET /api/pages/{id}/doc?theme=dark\|light` | The document shown in the sandbox (`raw=1` returns the Agent's original, used by `page_ctl get`) |
| `POST /api/pages/{id}/grant` | `{digest, decision: allow / deny}`: current version only; 409 `stale` if the page just changed |
| `POST /api/pages/{id}/data` | `{name, digest}`: one dataset the page asked for through the bridge; 403 `not_granted` without your OK, 409 `stale` on a version mismatch |
| `GET /api/pages/{id}/preview-data?name=` | What an Agent's declared data returns now (`page_ctl data`; no user grant involved, the app never calls it) |
| `POST /api/pages/{id}/pin`, `DELETE /api/pages/{id}` | Pin to the board (returns `undoTo`; undo = `POST /api/boards/{agent}/revert`); delete (chat cards and the board block then say it was deleted) |

## Nightly proposals

After the nightly digest the main chat looks back over the week and turns what keeps coming up into a proposal: **add a skill** (a way of doing something, given to the Agents that need it) or, rarely, **create an Agent**. It lands in the inbox; nothing changes until the user approves. See [`proposals.py`](proposals.py); the main chat uses [`proposals_ctl.py`](proposals_ctl.py) and the `proposals` skill, and `packs/core/scripts/daily_close.py` sends the nightly trigger.

| Endpoint | What it does |
|---|---|
| `GET /api/proposals/context?days=7` | The material to look back at: what the user said in every chat (with the start of each reply), existing skills and who has them, Agents, past proposals with the reasons they were declined, today's quota |
| `POST /api/proposals` | `{kind: skill / agent, slug, title, why, evidence: [{date, thread, quote}], changes?, skill: {name, agents, markdown} / agent: {name, purpose, icon, color, board}}` → an inbox card of kind `skill` / `agent`. ## Notifications

Three levels: **ring** (sound, interruptionLevel active), **quiet** (no sound, goes to Notification Center, passive), **none** (not sent). During `push.quiet_hours` in `server.json` (default `["23:00", "07:30"]`, in `timezone`; `[]` turns it off) ring is downgraded to quiet.

| When | Level |
|---|---|
| A reply to something you sent | ring |
| The main chat handing a question to an Agent (relay), the study desk | none |
| System triggers (`/api/chat/trigger`) | the request's `level`; only `notify: false` = none; neither = quiet |
| A new (or resubmitted) inbox item | the item's level (task / write / send / spend / calendar default to ring, the rest to quiet) |
| An inbox item done / failed | quiet |
| A background task started from the app finished, failed or hit its time limit; a revision round finished (`tasks.notify_done`) | quiet (tasks started on Telegram are answered there by OpenClaw; cancelled ones aren't pushed) |
| `/api/push/send` (wake-up report, deadline reminders, …) | the request's `level`, default ring |
| Anything above during focus time | held (the response says `held: true`) and handed over in the focus summary |

If the reply wrote a card (a new `feed_items` row whose group_id is this thread; for main, cards without an Agent), the card is pushed (subtitle = the card type, body = "card title · first point"); otherwise the start of the reply (Markdown stripped, cut at a sentence boundary). `data` carries `thread` (all older app builds read), `target` (`{type: thread | card | inbox | today, …}`), `level` (the level actually used after quiet hours) and `kind` (reply / card / inbox / done / report). The badge is inbox items waiting for you plus unread replies to your own messages. `/api/push/send` takes `{title, body, thread?, thread_id?, subtitle?, level?, category?, collapse?, target?}`.

Card and inbox pushes also carry `data.card`, which the app's notification content extension (1.0.5) draws when you long-press the notification: `k` type label, `t` title, `s` up to three `[label, value]` numbers, `r` `[value, max, label]` for a ring, `l` up to five lines, `f` a footnote, `c` a color (an Agent color name or `#RRGGBB`). Keys are short because the whole push is limited to 4 KB; `rich_card` in `push.py` builds it from meal and training cards and falls back to the first lines of the card body.

## Widgets and Live Activities

`GET /api/widget` (`widget.py`) is the small payload behind the iOS widgets (app 1.0.5): today's recovery (only once last night's sleep is in), the next meal from today's latest `meal_plan` card, today's and tomorrow's upcoming schedule items (`start` / `end` in Unix seconds so the widget can roll "next" forward on its own, a `time` label, `title`, `place`, `kind` class / training / deadline / event, at most 8) and the "To remember" count for the next week. Everything is formatted in the request's language; each part fails on its own; cached 60 s per language.

Live Activities (`live.py`): `GET /api/live` lists what should be on the Lock Screen / Dynamic Island right now as `{key, kind, state, staleAt}` (`state` is the Swift `ContentState`: `title`, `subtitle`, `icon` (SF Symbol), `accent`, `startAt` / `endAt` (Unix seconds), `progress`, `lines`, `done`). Built in: focus time (`focus:<id>`, from `think_focus`) and the post-workout meal countdown (`meal:post`: a reply that writes a `meal_plan` card with an upcoming 练后 / post-workout meal starts it, counting down to that meal; a card without one ends it). Anything else: `POST /api/live {key, kind, state, staleAt?, endsAt?, minutes?}` and `POST /api/live/{key}/end {state?}`. The app starts / updates / ends activities to match while it is in the foreground; it posts push-to-start and per-activity tokens to `POST /api/live/token {type: start | activity, token, key?, id?}` and a swipe-away to `POST /api/live/dismissed {key}` (that one isn't reopened until a new one with the same key starts). With `apns` in `server.json` (`{key_file, key_id, team_id, topic: <bundle id>, sandbox?}`, an APNs `.p8` key; the Expo push service doesn't relay Live Activities) the server also pushes start / update / end straight to Apple over HTTP/2 (`curl --http2`), so they appear without opening the app.

## Unread

`GET /api/unread` → `{threads: {<thread>: {n, mine, last: {id, text, ts, origin}}}, feedNew: [card ids], inbox, badge}`. Only threads with something unread are listed (main, every Agent, projects that aren't archived); n = assistant replies after the read mark, mine = those answering something you sent (`messages.origin = user`; timer- and inbox-triggered ones don't count); inbox = items waiting for you (exec approvals included); badge = inbox + the sum of mine. `POST /api/unread/read {thread, upto?}` moves the read mark forward (never back) and returns the same summary. New cards on the Today page: every item of `GET /api/feed` has `seen`; `POST /api/feed/seen {ids}` marks them seen.

Chat list (2026-10-13, `chats.py`, feature `chats.list`): `GET /api/chats` → `{agents, rows, ended, archived}` for the Chat tab. `agents` = every Agent `{id, name, icon, color, purpose, line, lineRole, at, unread, pinned, muted, state}`; `rows` = the main chat (always first, always pinned, can't be deleted), meetings and Agent groups (kinds `meeting` / `room`, from an optional `meetings` module: `chat_rows()` and `delete_meeting(id)`) and projects that aren't archived; `ended` / `archived` count ended meetings and archived projects (`GET /api/chats?archived=1` lists them). Order and unread count only your own messages and the replies to them (`role=user`, or `role=grava`, the internal value for the assistant's messages, with `origin=user`): timer, inbox and relay replies don't move a row or add unread. `state` is `working` (a reply running or a background task the thread started) or `waiting` (an inbox item with that thread or source). `PATCH /api/chats/{thread} {pinned?, muted?}` stores pins and mutes in `chat_prefs`; a muted thread gets no push and its replies leave the app badge (`/api/unread` marks it `muted`). `DELETE /api/chats/{thread}` deletes a project or a meeting (Agents go through `DELETE /api/groups/{id}`). Friends: `POST /api/friends/{id}/clear` hides the whole chat on your server only (feature `friends.clear`).

## Study desk

`/study` is a wide-screen page for a computer: courses and modules on the left, study notes / slides (PDF) / flashcards / quiz in the middle, and a chat on the right that answers from this session's materials. Configure it with `study` in `server.json` (see [`study.py`](study.py)):

- `materials`: one folder per course, one subfolder per module (week / session), files inside. A module-by-module download of a learning platform (e.g. Canvas) has exactly this shape.
- `pages`: study notes, one folder per course, Markdown with YAML front matter (`session`, `title`, `sources` = material paths relative to the course folder). Notes attach to the module of their first source; videos go in `<course>/media/` named `S03 ….mp4`.
- `courses` (optional): which course folders to show, in order. `deadlines_cmd` (optional): a command that prints a JSON array of `{due, course, title, url}` shown along the top.
- `readings` (optional): a folder with one `<course>.json` reading list per course: `{"items": [{title, kind, required, instructions, sessions, file, status, url}]}`, `file` relative to the course's materials folder. Each session gets a "Readings" tab; if a required reading is missing, generating a study path / flashcards / quiz asks you to supply it first.
- `recordings` (optional): lecture captions, `<course>/index.json` listing recordings (`id, name, start, duration, sessions, file`), each `file` holding `{viewer_url, segments: [{t, text}]}`. Each session gets a "Lectures" tab (captions with timestamps that open the recording at that moment), and the captions go into the chat context. Keep captions private if your institution's recording policy says so.
- `video_cmd` (optional): a render command (argv list; `{script}` = the Manim script the assistant wrote, `{media_dir}` = a work folder). When set, each session gets "make a video": the assistant writes the script, the server renders it and hands any error back once for a fix. This runs code the assistant wrote on your machine, so only turn it on where you already trust the assistant to run code.

Originals of materials and study notes (`GET /api/study/file?course=&path=&where=materials|pages`) go to the browser inline and unchanged, always with `X-Content-Type-Options: nosniff`. They come from a learning platform, the web or an Agent, so HTML, SVG and XML also get `Content-Security-Policy: sandbox` (no `allow-scripts`): opened directly, they load in an opaque origin with scripts off and can't reach the web app's tokens or `/api`, while SVGs embedded with `<img>` in study notes show as before. Chat attachment originals follow the same rule (`files.untrusted_headers`).

Every study page opens on its **study path**: 5–8 steps (what to do, which slide pages / note section / reading / recording time, roughly how long), generated from all of the session's materials, with a tick box per step; progress is saved on the server and shown in the course tree.

**Review**: what a podcast's Feynman check found wrong or missed can be added to the course with one tap (`POST /api/study/review {course, page?, items, …}`, stored in `pages/<course>/.gen/review.json`, attached to that session); opening the session on the study desk shows a Review box at the top, and "Reviewed" ticks an item off (`POST /api/study/review/done`). `GET /api/study/review?course=&page=&all=`.

Questions go through the same chat channel as the app, one thread per study page. The first question of each day carries the notes, the full text of the materials, the lecture captions and the readings (as much as fits; the rest by file path), plus the study-path step you're on. Flashcards, quizzes and study paths are saved next to the notes; when OpenClaw has llm-task on they are generated in a tool-free call (the course text never enters a turn with tools), otherwise in the session's generation thread.

Without `materials` and `pages` in the config they default to the data directory (`<data_dir>/study/materials`, `pages`); the installer creates those folders.

### Adding a course (course profiles)

"+ Add a course" on the left of the desk is a five-step wizard with the **study Agent**'s chat open on the right (`study.agent`; the same thread as that Agent's Chat in the app): tell it what's wrong and it fixes it with `study_ctl.py`, highlighted and undoable. Each course gets `pages/<course>/course.json` (see [`coursefile.py`](coursefile.py)):

1. **About the course**: name, term, how it's assessed, how you like to learn, anything else (every study page uses it).
2. **What you have**: a syllabus (file, web link or chat attachment), course files (files or a zip), a Canvas personal token, or nothing yet; where to find each follows the course site you pick. The model reads the syllabus (tool-free llm-task) into sessions with dates, topics and readings, plus assignments and exams, and lists what's unclear as questions.
3. **Check the sessions**: click a cell or tell the Agent; confirming creates each session's folder and sends assignments and exams to Today, To remember, the top bar and the study Agent's deadline table.
4. **Add materials**: files are filed by name (Session / Lecture N → that session; Week N → that week, asking when a week has several sessions or the topic disagrees; a match on the reading list becomes that reading), zips are unpacked; each session shows its files, readings in hand and caption files (drop a `.vtt` / `.srt` into the session); missing items can be added or skipped openly.
5. **Generate**: only complete sessions, one at a time: the study page (fixed sections, including the self-test in `**Q1.**` + `<details>` form that the Self-test tab parses), then the study path, flashcards and quiz (and a video). The study Agent's chat gets a line when each is done.

An existing materials folder (a synced course site, say) can become a course: sessions come from the module names and existing notes attach by `session`. Courses without a profile work as before.

## Memory tree

Me → Memory tree in the app. The memory your AI apps share (Claude, ChatGPT, Gemini, Claude Code and your own Agents): the trunk is the profile, branches are areas of life and one per Agent, leaves are memories. It is either the workspace script `memory_tree.py` or the open-source tree the installer sets up (`openmousse_tree` in [`../tree/`](../tree/), wrapped by [`treelib.py`](treelib.py)); [`sources.py`](sources.py) picks one, and the `tree` tool and Zen's "done thinking" use the same one. That tree owns the index, the writes and the forgetting; this server only reads it and passes the actions through (optional source `tree`: without either both endpoints answer `ok=false` + `missing_source: tree`). See [`memtree.py`](memtree.py).

With the open-source tree, a new Agent gets a small branch of its own (its id in `agents`, so the engine shows that Agent the leaves on its branches), and older Agents get theirs when the server starts. **Weekly pruning** ([`treeprune.py`](treeprune.py), builtin engine only): a scheduled job of the main chat, every Sunday at 19:00 by default, follows the `tree-prune` skill: `tree prune-context`, then a plan through `tree prune-plan`, which becomes a quiet inbox card (kind `tree`, one per week, expires after a week). Approving it prunes exactly as planned on the server and marks the card done; declining discards the plan. `server.json` `"tree": {"prune": {"when": "every sunday 19:00"}}` moves it, `"tree": {"prune": false}` turns it off.

**Manuals** (tree 0.6, builtin engine): a procedure you want followed the same way everywhere (how you write documents, log a workout, prepare a meeting) is kept once as a manual next to the tree (`mousse-tree manual …`, see [`../tree/README.md`](../tree/README.md)); every other place keeps a four-line pointer (`mousse-tree manual pointers`). Before each of your turns the engine searches your manuals and the Agent's skills for what you just said (plus your previous message) and adds only the matching bodies after your message ([`engine/manuals.py`](engine/manuals.py)); the skills list at the top of the conversation keeps only names. Each turn records what it actually read (manuals, skills, memory leaves; [`engine/used.py`](engine/used.py)): the reply carries `used` and a line such as "Following the "Writing documents" manual · used 2 leaves ›". An Agent that wants to change a manual uses `manual_manage` ([`engine/manual_write.py`](engine/manual_write.py)): manuals are "how things are done" in the memory gate, so the change becomes an approval card first and the old version is kept; through the `tree` tool they are read-only. The weekly pruning card gets a "Not used this month" section: manuals and your own skills nobody used, each left as is by default; approve = reword (a second card with everyday wording), or revise the item with "disable". `"engine": {"manuals": false}` brings back the old behaviour; the other settings are in `engine/models.py`.

| Route | What |

## Connections

Me → Connections: everything the assistant is connected to, and how it's doing. `GET /api/connectors[?fresh=1]` → `{groups: [{id, title, items}], counts: {ok, warn, off}, checkedAt}`; each item is `{id, name, icon, status: ok | warn | off, line, facts: [{label, value}], uses, fix, open}` (`open` = a screen in the app to jump to). The result is cached for 60 s per language (`fresh=1` skips it) and the chat channels' status (`openclaw channels status`) for 2 minutes. Every check is best effort and never returns a secret: only whether key names exist, file times, counts and systemd unit states. Checks for things your machine doesn't have (a script, a unit, a folder) are left out; built-ins you don't use yet (Apple Health, the calendar feed, push) show as not connected. Unit names and one path can be changed in `server.json` (2026-10-20, read on every request): `"connectors": {"units": {"browser", "mail", "obsidian", "tree"}, "canvas_courses"}`. The defaults are `mousse-browser.service` (the browser on the server that signs in to Canvas), `mousse-mail.timer` (the mail digest), `obsidian-sync.service` and `mousse-tree.service` (what the installer sets up); a name without a suffix counts as `.service`. `canvas_courses` is the JSON file of tracked courses (`{course id: name}`, default `<openclaw_home>/canvas/tracked.json`).

Only timers listed in `titles` are shown (`repeat` defaults to daily), and one-off reminders (`systemd-run --unit=<prefix>…`, titled by their Description) only when `reminder_prefix` is set. By default no timer is listed and cron jobs keep their own names.

## Connectors (apps over MCP)

Settings → Connectors: third-party apps connected to this server over MCP (Notion, Linear… or any remote MCP address). Your claw uses their tools through `/mcp`; the tokens stay on this server. See [`apps.py`](apps.py).

- **Connecting** follows the MCP authorization spec: the server finds the app's authorization server (the 401's `WWW-Authenticate` → protected-resource metadata → authorization-server metadata; a server without resource metadata is looked up the older way, on the MCP address's own host), gets a client (the `apps.client_id_url` document when the server supports client ID metadata documents, otherwise dynamic client registration, cached per authorization server and callback address) and gives the app an authorization URL (PKCE S256, `state`, `resource` = the MCP address, `scope` as advertised). The phone signs in, the provider sends it to `<app scheme>://oauth/callback?code&state`, the app hands that to `/api/apps/oauth/callback`, and the server exchanges the code and lists the tools. An authorization has 10 minutes and works once; starting again while one is unfinished registers a new client (the provider may have forgotten the old one). Tokens are refreshed shortly before they expire and once after a 401; if refreshing fails the app shows as needing to be reconnected. Removing an app revokes its tokens at the provider when it can.
- **Using**: each connected app's tools appear on `/mcp` as `<app id>__<tool>` (with an optional `agent` argument, `mousse_agent` when the tool has its own `agent`). Each tool is `auto` (runs), `ask` (every call becomes an inbox card of kind `app` that rings; approving runs exactly that call and posts the result into the Agent's chat; asking for a change makes the Agent call again with new arguments) or `off`. Defaults: read tools auto, write tools ask (the tool's `readOnlyHint`, otherwise its name: get / list / search / read / fetch / find / query / view / describe / show / lookup are reads). Which Agents may use an app is set per app (main by default); the caller is the Agent an `mcp-<id>` token is bound to, else the `agent` argument, else main. Claws that keep a tool list per session see changes when they reconnect.
- Calls: one short MCP session each (streamable HTTP, or SSE for servers that only have that), 60 s at most, 4 at a time; text is capped at 30,000 characters, images and other binary content become a one-line note.
- In `server.json` only (no settings screen yet): `apps.<app id>.disabled_tools` / `enabled_tools` (lists of tool names; an empty `enabled_tools` turns them all off) hide tools from `/mcp` and the engine, and calling one says which key turned it off. With the built-in engine, tool descriptions are cut at `apps.desc_max` characters (600) and an `ask` card lapses after `apps.ask_ttl_hours` (24; approving it then gets 409); with OpenClaw or another claw descriptions keep 8,000 characters and cards wait until answered.
- Safety: addresses learned from a server (metadata, endpoints) must be https and resolve to public addresses, unless they're on the MCP address's own origin; a custom MCP address is https, or plain http only for this machine or a Tailscale address. Tokens are never returned or logged. An `app` card edited after it was sent is not run.

## Thinking space and Saved

The Think tab in the app (labelled **Zen** since 2026-09-28; the code and API still say think): drop a thought the moment it comes (a sentence, a few `#keywords`, a voice note, a photo, a file, a link, a long piece of writing) and nothing answers. The model only joins when you pick a few thoughts and tap **Talk** or **Done thinking**. **Saved** keeps things from other apps (links, files, screenshots) for later, also without calling a model. **Focus time** holds every notification until it ends. See [`think.py`](think.py) and [`saves.py`](saves.py).

- **A thought is a Markdown note.** With `think.vault` in `server.json` (e.g. `"think": {"vault": "~/vault", "obsidian_vault": "Vault name"}`) it goes into the vault's inbox folder, so Obsidian sees it and edits made there come back; without it, into `<data_dir>/think/`. Folder names default by language (zh: 收件箱 / 收件箱/已想完 / 收件箱/附件 / 笔记 / 写作; override with `think.inbox_dir`, `done_dir`, `attach_dir`, `notes_dir`, `writing_dir`). Properties: `id, kind, created_at, source, keywords, tags, topics, note, files, url`; attachments are embedded at the end as `![[…]]`. Notes you create in Obsidian show up too. Files are re-read only when their mtime or size changes, anything modified in the last second waits for the next read (sync clients don't write atomically), and every write is a temp file + rename. Deleting moves the note into the vault's `.trash/`; finished thoughts move to the done folder, never deleted.
- **Keywords** = the `keywords` property plus `#words` in the text (after CJK text too). The keyword page lists every thought and saved item with it, the topics that used it and the words that often come with it.
- **Topics** (`think_topics`, id `tp-…`, which is also the chat thread and the OpenClaw session `agent:main:grava:tp-…`; `grava` is an internal value in the session key): **Talk** sends "【自动触发】聊聊" so the model asks before it concludes; on the first message of each day, and whenever the topic's thoughts change, `chat.start_run` puts the thoughts and the "think with them" rules in front of the message (not shown in the chat). **Just note** in a topic saves a thought the model doesn't see (`note: true`, a dashed line in the chat, never sent to the Gateway); it is used when you finish. **Done thinking** drafts a note in the background in a separate session (title, one line, points with the thoughts they came from, still open, next steps, keywords, one line for the memory tree), you edit it, and **save** writes it into the notes or writing folder, moves the thoughts to the done folder and, if you keep it, adds a memory-tree leaf through the workspace's `memory_tree.py`.
- **Saved** (`think_saves`, originals in `<data_dir>/saves/`, `think.saves_dir` to change): the originals stay out of the vault. The text is extracted once when saved (web pages in the background, WeChat articles included, so a deleted article survives; PDF / Word / spreadsheets); when a page can't be fetched the reason is kept next to the link. From there you choose: ask the main chat about it (`save` on `/api/chat/send` gives the model the text), hand it to an Agent (a quiet round in its thread), turn it into a thought, distil it into a note, or delete it (soft, restorable).
- **Zen home** (2026-10-13): the app splits Zen into **Thoughts | Podcast**. The Thoughts side no longer separates thoughts from saved items: `GET /api/think/home` returns the open topics (with `stage` for the four-step progress, a one-line `state`, and `waiting` when it's your turn) and the noted items (unfinished thoughts and saved items together, newest first; thoughts inside a topic and saved items turned into thoughts aren't listed twice). Every item has a way out that calls no model: **Done** (`POST /api/think/done`: a thought moves to the done folder with `status: done` and `done_at`; a saved item gets `done_at`; `undo` restores), and the finished list is ordered by when they were finished (a written-up topic is one row).
- **Take it to discuss** (2026-10-21, [`ideatalk.py`](ideatalk.py)): long-press a thought → one sheet (`GET /api/think/ideas/{id}/discuss`: where it's being discussed now, Cybers you talked with most recently first, Agents, friends, recent episodes, and which of these this server can do). One-to-one with a Cyber (`POST …/cyber {cyber}`: its chat gets "Let's talk about this thought", the full text goes in only as context it reads, not as a message), a new group chat (`POST …/group {members, host?, mode?}`: the thought is the source and the topic, one round starts, summaries are written back into the thought's note, and when the group ends the thought moves to Done thinking), into a podcast (`POST …/podcast {episode?}`: a material; no episode given = a new one), to a functional Agent for things to do (`POST …/agent {agent, note?}`: a message in its chat quoting the thought; it acts under its usual approvals) or to a friend as key points only (`POST …/points` → `{points}`, made with one tool-free call that counts as your own ask: your tap in the app can use your plan when `engine.use.json` is one, a request through /mcp can't; the app shows them and sends what you approve through `/api/friends/{id}/messages`, never the original wording). One thing, one home: the note's `talk` property (and `group` once a summary is written back) records where it went, and every thought carries `discussion: {kind, id}` so Zen shows "Discussing" and opens that place. All of it needs Cybers or group chats on (both need the built-in engine); otherwise every route is a 404 and the app keeps the old "discuss with the assistant". The group and Cyber routes need `groupchat` / `cybers` themselves.
- **Search** is literal and in memory over thoughts, saved items, talked topics and saved notes (two CJK characters are enough), with highlighted parts; no model call. **History** counts thoughts and saved items per day; the search page's heat calendar uses `GET /api/think/heat` (items noted per day over the last few weeks).
- **Focus time** (`think_focus`, 25 / 45 / 90 minutes or open-ended = 3 hours): before it starts the app shows what's scheduled in that window; while it runs `push.send_push` sends nothing and records what it would have sent (`think_focus_held`); when it ends (tapped or timed out) the summary merges them by where they lead (one per chat thread, the latest), plus what's waiting in the inbox and what's next on the schedule. A summary nobody has seen comes back on the next `GET /api/think/focus`.

## Podcast

The third part of Think (Zen): say it out loud, and afterwards it turns it into a note. It is the voice version of Talk and ends the same way: a note in your own words → saved to Notes / Writing / Study → anything worth remembering long term is offered to the memory tree, and nothing is added unless you tap. Audio and transcripts stay on the server (`<data_dir>/podcast/<episode>/`, `podcast.dir`), never in the vault. See [`podcast.py`](podcast.py).

- **Talk about today**: the model picks 4 from your unfinished Zen topics, the "still open" lines in your vault notes, recent study-desk sessions, deadlines in the next 6 days and the memory tree, writes each as a concrete question and says where it came from; cached per day, "Others" picks again.
- **Four modes**: solo (it just listens) / with a host (it asks one follow-up when you pause; skip or rephrase) / Feynman (it plays a smart layperson, then checks your explanation against the session's slides, notes and lecture captions: right, wrong, missed, with sources; the standard view when there are no materials) / with friends (one phone in the room, voices told apart afterwards, you name who's who the first time; only your words go into the note, everyone gets minutes).
- **Talk it through first**: it asks for your first reaction, you answer (type or speak), and it drafts a 3–5 point outline card from your words that stays on screen while you record. An outline, never a script.
- **Take by take**: every pause uploads a take and the server transcribes it at once: `gpt-transcribe` for the words (vocabulary keywords, per-token confidence → unclear words are marked), `whisper-1` for sentence timing, aligned character by character, so every sentence plays on tap. Vocabulary = words you corrected + `transcribe_prompt` terms + course, Agent and project names + tree branches (profile names and addresses stay out). Fixing a sentence adds the changed words.
- **Organizing** (in the background; the app polls): proofread names and misheard words → title, one line, your own words with timestamps, still open, keywords (suggestions only when tapped), an optional tree line → compare with earlier notes (did your view change) → the Feynman check.
- **Models** go through [`llmjson.py`](llmjson.py): OpenClaw's `llm-task` (no tools, no chat; a host question takes 2–3 s), or a throwaway session when it's off. Transcription needs `OPENAI_API_KEY` (same as voice input): about $0.0045/min for `gpt-transcribe` and $0.006/min for `whisper-1`.
- **Materials**: an episode can take things you already have: messages from any chat (long-press → Add to a podcast, or pick them inside the episode), chats with friends (both sides), files (PDF, Word, Excel, PowerPoint, text; recordings are transcribed), Zen thoughts and topics, saved items. The text is taken when you add it (up to 12,000 characters each, 40 per episode), and the prep chat, the host's questions, organizing (newest first, 8k / 6k / 24k characters), comparing with earlier notes (only your own words) and the Feynman check (files count as course materials) use it. A friend's words stay in that episode: never quoted, never in the title or the tree; the saved note's Drew on section only says "Drew on a chat with Sam". If `llm-task` isn't available and a call falls back to a normal chat turn (which has tools), friends' words are left out of it (`fallback_input` in `llmjson.ask`). See [`podmaterials.py`](podmaterials.py).
- **A prep group per episode** (built-in engine, with `groupchat` and `cybers` on; [`podprep.py`](podprep.py)): "Start discussing" (`POST /api/podcast/episodes/{id}/discuss` `{mode?, guests?, friends?}`) opens a group chat for this episode (`prep_group` on the episode; the group's source is the episode). Who asks you depends on the mode: Iris for solo (she only helps with the outline; nobody hosts the recording) and host, Zhe for Feynman (the layman: says when lost, asks for an example); with friends (`friends: [friend ids]`, butler on) the prep group is a friend group you own and your butler hosts: it opens with a fixed line, and when someone proposes a time it answers by the card agent's rules, so the time comes to you as a card first; Iris still helps with the outline, seeing only what you said there (never a friend's words or names), and the outline line stays on your side. Without friends Iris helps as before. Guests are more Cybers. The host speaks first, then answers each of your messages. `POST /api/podcast/episodes/{id}/outline` `{note?}` has the host draft or change the outline from what was said (tool-free; the assistant through `llmjson.ask`, a Cyber on its own model): it's saved as the episode's outline (the card on screen while recording), pinned on top of the group, and the group gets a line "Iris updated outline items 2, 4". A summary of a full round goes into the episode's materials. **Put in** cards: `POST /api/podcast/episodes/{id}/offers` `{agent}` takes a functional Agent's latest report (the last 7 days) as a card only you see; `POST /api/podcast/offers/{offer}` `{action: put | skip}`. A normal one becomes a material; a health, diet or sleep Agent's (like last week's sleep report) never does: it goes only to the group's host Cyber, only once (its next turn reads it, then it's marked used). The older prep chat (`/prep`, `pod_turns`) still works and stays readable; nothing is moved or deleted. Deleting an episode deletes its prep group (a friend group is only unlinked: it's shared with your friends).
- **In-progress rows** (`GET /api/podcast` episodes, and each episode): `participants` (faces, host first), `booked` (the recording time you set: `PATCH /api/podcast/episodes/{id}` `{bookedAt: "YYYY-MM-DDTHH:MM" | ""}` puts it in the schedule under key `podcast:<episode>:rec`; in a friend group your butler tells everyone; a time a friend proposes there lands on the same item only after you approve its card), `latest` (the newest line in the prep group, or the next step: "Outline ready · 4 items"), `steps` (discuss → outline → record → organize), `waiting` and `prepGroup`.
- **Friend notes** (with friends): pick who's here before recording; when naming voices, match each voice to a person (someone you recorded with before, a friend, or a new name; or just a name and no notes). After organizing, each matched person gets 3–8 notes (views / up to / cares about / ask next time), each resting on one of their sentences (tap to hear it). The same thing again isn't written twice, a change replaces the old note (kept as history), and an "ask next time" that got its answer is marked asked. Re-organizing or deleting an episode takes back the notes it wrote (ones you edited stay). Only you see them: the host and the prep chat can pick up a thread ("Last time Sam said…") and Talk about today can suggest catching up with someone; nothing else reads them — not the card agent at any tier, not the main chat or Agents, not the vault or the memory tree. Friends are told: the recording screen says notes are kept, and each person's minutes end with a line saying so. With friends, the title, one line and keywords come only from what you said, since they can end up in the vault. Notes are only written through `llm-task` (no tools; the whole input is someone else's words): without it the done page says no notes were kept this time. A fallback chat turn never carries friend notes, and with friends it carries only your own sentences. See [`people.py`](people.py).
- **Recording together remotely isn't built; the interface is reserved**: later (possibly a call inside the app) each person becomes one track, uploaded to the same episode with a `track` (who) and the time since recording started (to line tracks up), so organizing splits people by track instead of guessing voices. Today's takes are one timeline, one after another.

## Sharing

Share a reply or a Done-thinking note as a link page or a clean image card: long-press a message → Share, or Zen → Done thinking → Share; Me → Shared lists what went out. See [`share.py`](share.py).

- **A share is a snapshot.** The text is copied into `shares` when you share; editing the original later doesn't change what went out.
- **Private bits are hidden first.** Addresses and the names of your partner and family found in the profile (`USER.md`), emails, phone numbers, body numbers (weight, body fat, heart rate, sleep…) and the words in `share.private_words` start hidden, and you show them one by one. Hidden text never leaves the server: the link page and the cards draw a grey bar instead, titles included.
- **Two looks.** *With link*: `/s/<token>` is a plain page anyone can open without the app, and `/s/<token>/card.png` is the preview image chat apps show. *Clean*: a 3:4 image with no URL, QR code or app name, for platforms that don't allow links. Cards are drawn on the server with Pillow; Chinese needs a CJK font (Noto Sans CJK is found automatically, `share.font` / `share.font_bold` pick another).
- **Reaching the link from outside.** Set `share.public_port` and `run.py` also starts a small app on `127.0.0.1:<port>` that serves only `/s/` ([`public.py`](public.py): no `/api`, no tokens, no trusted devices). Point Tailscale Funnel or a reverse proxy at it (`tailscale funnel --bg --set-path /s http://127.0.0.1:<port>/s`) and set `share.public_url` to the address people see. Without `public_url` the app offers the clean card only. The main server serves `/s/` too, for your own devices; views are counted only through the public app, link-preview bots excluded.
- **Withdraw** empties the snapshot (the hidden-bits title stays in your list) and the link says it was withdrawn. Drafts nobody published are deleted after 7 days. No model is called.

| Route | What |
|---|---|
| `POST /api/shares` | `{kind: message, thread, id}` / `{kind: note, topic or path}` / `{kind: text, title?, text}` → a draft with `masks` (label, the hidden text and a few words around it, released) and `segments`; sharing the same message again returns the same share |
| `GET /api/shares` | Published and withdrawn shares; `canLink` = a public address is configured |
| `GET` / `PATCH /api/shares/{id}` | `{release?: [mask ids], hide?: [...], quote?, title?, withQuestion?}` (`""` = back to the default; `withQuestion` takes the snapshot again) |
| `POST /api/shares/{id}/publish` | The link starts working (`url` when `public_url` is set) |
| `DELETE /api/shares/{id}` | Withdraw (a draft is simply deleted) |
| `GET /api/shares/{id}/card?style=clean\|link` | The card as a data URI; `/card.png` for the image itself |
| `GET /s/{token}`, `/s/{token}/card.png` | Public: the link page and its preview image |

## Forwarding

Long-press any message, in an Agent chat or a friend chat, for **Forward**, **Select this conversation** (the model checks the messages around it on the same topic and writes a one-line title), **Select messages**, or **Add to basket** (collect messages from several chats and send them together later). See [`forward.py`](forward.py).

- **To friends** the bundle becomes a share of `kind: thread` (above): private bits are hidden first, the friend can ask about it (the card agent answers from that bundle only), and withdrawing it clears their copy. A bundle with someone else's words in it (a friend, their card agent) can't take questions, and each line says who said it.
- **To your own Agent** it is a message from you in that Agent's chat, with an intent (remember / handle / read only) and an optional note; the app draws the bundle above it. A busy Agent gets it queued. **A friend's words never enter a tool-capable turn**: they are condensed into points by a model without tools (`llm-task`, or `card.llm`), and the Agent only sees the points; with neither, it's told how many lines it didn't get.
- Bundles with a friend's words can go into a podcast but not into Saved (a saved item can be handed to an Agent).

| Route | What |
|---|---|
| `POST /api/forward/preview` | `{refs, gist?}` → the lines, a one-line title, which chats, whose words |
| `POST /api/forward/segment` | `{ref}` → the messages on the same topic around it, and a title |
| `POST /api/forward/share` | `{refs, gist}` → a draft `thread` share (then the share routes: masks, `/send`) |
| `POST /api/forward/agent` | `{refs, gist, agent, intent, note?}` → posts it into that Agent's chat |
| `POST /api/forward/save` | `{refs, gist}` → one saved item |
| `GET` / `POST` / `DELETE /api/forward/basket` | The basket (`DELETE` without refs empties it) |
| `GET /api/forward/{id}` | A bundle sent to an Agent, in full |

Refs are `chat:<thread>:<message id>` or `friend:<friend id>:<row id>`.

## Friends

Chat → Friends in the app. Your server and a friend's server talk directly: identity is an Ed25519 key per server (not the address), you become friends through a one-time invite, and every request between the two servers is signed. The protocol is [`../docs/social-protocol.md`](../docs/social-protocol.md); the code is [`social.py`](social.py) (identity, card, signatures, tables, tiers) and [`friends.py`](friends.py) (invites, chat, delivery, shares to friends, follow-up questions).

- **How friends reach you.** Through the small public app ([`public.py`](public.py)) under `/f`: either directly (point Tailscale Funnel or a reverse proxy at it, `tailscale funnel --bg --set-path /f http://127.0.0.1:<share.public_port>/f`, and set `share.public_url`) or, by default when there's no usable public address, through the OpenMousse relay (below). Without `user_name` the app asks for one before you can add friends. A reverse proxy must keep the `/f` prefix as it is (the path is signed).
- **Invites.** An invite is a link `<your address>/f/i/<token>/<your public key>`: it works once, lasts 7 days by default, and only its hash is stored. Opening it in a browser shows a landing page (with a QR code for phones and an "Open in the app" link); the app pastes it, checks the other server's card against the key in the link and redeems it with a signed `POST /f/hello`. Fingerprints (10 characters) let two people compare on a call.
- **Chat.** Each message is one signed `POST /f/msg`. Outgoing messages queue in `friend_messages` and a delivery loop sends them in order per friend, retrying for up to 3 days; edits, withdrawals, a changed name or address, and removing a friend travel as messages too. Blocking drops their messages silently.
- **Sharing to friends.** On the Share page, pick friends: they get the snapshot with the same hidden bits (`▇▇▇`; the original never leaves the server). Without a link, the share's status is `friends` and `/s/` stays closed. Withdrawing a share withdraws every copy.
- **Follow-up questions and your card agent.** Friends can ask about something you shared; when the share allows it and their tier's `shares` is `ask`, your card agent (`cardagent.py`, never the claw, no tools) answers within that tier and says what it used. You see every answer with Fine / Rewrite / Withdraw. Without a card agent, questions just wait for you. Tiers (close / friend / classmate / stranger) and your status line are set in Chat → Friends → My card agent (`/api/card`); health and the memory tree are never on offer. Everything the card agent says first goes through **Doorman** (`sentinel.py`, step 9 of the security base): rules plus a separate, independent model review; anything off is held for you to send, rewrite or drop, and a line that can't be reviewed becomes a fixed one (details in `docs/a2a.md` 2.4.1).
- **Push** for friends is a new kind of notification: off until `social.push` in `server.json` turns it on (`{"message": "ring", "answered": "quiet", "friend": "quiet"}`; `agents`, when what your card agent asked a friend's agent comes back decided, follows `answered` unless set). Friends' messages count as unread and in the badge either way.
- **Relay and end-to-end envelopes** (2026-10-05, [`relay.py`](relay.py), [`../relay/`](../relay/)): a server without a usable public address connects out to the OpenMousse relay (default `https://relay.openmousse.ai`) and friends reach it at `https://relay.openmousse.ai/u/<kid>`, so adding friends works on a fresh install with no Funnel. Cards now carry an X25519 key (`enc`): messages, the invite handshake and A2A between current servers go sealed through `POST /f/sealed`, so the relay sees only ciphertext. `"relay": false` in server.json turns it off. Protocol: [`../docs/social-protocol.md`](../docs/social-protocol.md) 6.1.
- **Your name and whether you can be reached** (2026-10-05). The name on your card is `user_name`; the app sets it with `PATCH /api/card {name}` (also written to the profile, like `settings_ctl.py user-name`), and asks for it right after the first connect. `GET /api/friends` reports `unreachable` when `share.public_url` is a `*.ts.net` address but `tailscale funnel status` shows `/f` isn't public, or when the last friend's server that tried to reach you couldn't (`publicFix` is the command to run). When someone redeems your invite, your server tries to fetch their card before answering and returns `reach: true | false`, which their server stores and shows; any message that later arrives from a friend clears it. A message that couldn't be delivered yet carries `error` and `nextTry` while it's still retrying, and `…/retry` on it tries again at once.
- `social.allow_http: true` is for test servers on one machine (`http://127.0.0.1:<port>` addresses); never set it on a real server.

## Errand agent and Doorman egress (preview)

## Data sources are optional

The boards need workouts / meals / body / calendar / derived health metrics, each provided by one script in the `scripts` directory named in `server.json` (default `<workspace>/scripts`): `xunji.py` (workouts / body; meals only when `diet.source` is `xunji`, otherwise they live in the server's own meal log, see Meal log), `calendar_ics.py` (calendar), `apple_health.py` (recovery score, energy balance, fitness trend, and whether you are up yet: `/api/health/wake` reads the raw sleep segments the phone pushes to `/api/health/sleep` and the wake signals posted to `/api/health/signal`). `memory_tree.py` provides the memory tree (Me → Memory tree). A script that is present gets loaded; a missing one means "not connected": `/api/health` reports `sources` so the app knows, the affected endpoints answer `ok=false` + `missing_source`, boards show an empty state, everything else works. See [`sources.py`](sources.py).

Today these three scripts are written for particular sources (the Xunji training app, an ICS calendar, Apple Health). They are being split into optional packs (`packs/`): each pack declares the data types it needs and you map the sources.
