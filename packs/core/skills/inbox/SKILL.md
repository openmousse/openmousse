# 收件箱：先问再做

你交上来的事会变成一张带按钮的卡：在对话里就显示在你这条回复下面，同时出现在 app「今天 → 等你点头」里。用户点**同意**，或者引用这张卡回复你说要怎么改，或者**拒绝**。同意之后系统会在你的线程里发一句「【收件箱】已同意…」，那时你再动手。

**在对话里要用户点头时，不要让他打「确认」**：交一条收件箱，回复里只说你想做什么、按钮就在下面。

```bash
I=~/.openmousse/repo/server/inbox_ctl.py
python3 $I add --kind send --source <你的 id> --dedupe "<你的 id>:reply-hr:2026-09-26" \
  --title "给 HR 回邮件，确认周三 14:00 面试" \
  --why "HR 昨天问你周三还是周四，你刚才说周三下午可以" \
  --change "发给 hr@example.com：确认周三 14:00，附上 CV" \
  --detail-file draft.md --approve-label "发出去"         # 打印 id，比如 ib-1a2b3c4d
python3 $I done ib-1a2b3c4d --result "发了，HR 回复收到"
python3 $I fail ib-1a2b3c4d --result "邮箱授权过期了，要重新登录"
python3 $I update ib-1a2b3c4d --change "改成周四 10:00"     # 用户要改之后，同一个 id
python3 $I get ib-1a2b3c4d                               # 看自己交过的全部内容
python3 $I withdraw ib-1a2b3c4d                          # 不需要了
python3 $I list                                          # 还在等的；--status recent 看最近定下来的
```

- `--kind`：task 任务 / write 写进外部系统 / send 发给别人 / spend 花钱 / schedule 新定时任务 / push 新推送 / calendar 外部日历 / skill 新技能 / agent 新 Agent / block 看板 / code 改代码、配置、凭证 / other。
- `--source`：你是主对话就写 `main`，是某个 Agent 就写自己的 id（同意之后消息发回这个线程）。
- 细节长（邮件全文、改动清单）就写进文件，用 `--detail-file 文件`（Markdown，`-` 是标准输入）。
- 有时效的加 `--expires 2026-09-26T18:00`：过了还没点头就作废。
- 要先预览再确认的写入（比如会覆盖原有记录的更新）：把预览的要点一行一个写进 `--change`，`--approve-label 确认提交`。

## 直接做，还是先问

看两件事：**是不是用户明确让你做的**，**做了能不能撤回**。

**直接做**：

- 只读的事从不进收件箱：查资料、读文件、跑只读的命令、转给某个 Agent 问。
- 用户明确让你做、而且能撤回的：做完在对话里说做了什么、怎么撤回。比如他说「记一下，中午吃了鸡胸沙拉」，就把这一餐记上，回一句"记了：午餐鸡胸沙拉 350 g，要撤回跟我说"。写草稿、记日志、改目标都一样。

**先交收件箱，等他点头**：

- **你自己的主意**（提议）：新技能、新 Agent、看板加一块、改一处代码；也包括他没开口的补记录，比如"发现你早餐没记，按平常的补上？"。
- **会发给别人、或者撤不回的**：发送任何东西（邮件、消息、评论、申请材料）（`send`）；花钱（`spend`）；超出每天的后台任务额度，默认每天 10 个、每个 30 分钟以内（`task`）。
- **新建定时任务、新的推送**（`schedule` / `push`）。
- **改代码、配置、凭证，或者 OTA 更新**（`code`）。

## 提议怎么交

- 新技能、新 Agent、看板、代码用 `skill` / `agent` / `block` / `code`，默认就是静默推送；补记录这类用 `write` 时加 `--level quiet`。你自己的主意都别响铃。
- 一天最多一两条：攒着，挑最有用的交。
- `why` 里写证据，比如「这周你让我翻译 PDF 三次：9/22、9/24、9/26」。拿不出证据的想法先别提。

## 规则

1. **永远不替自己点同意**，也不要让用户在对话里说一句"同意"来绕过收件箱。
2. **一条一个决定**：不相干的几件事分几条交。
3. **`--dedupe` 用固定的键**（比如 `<你的 id>:<做什么>:<日期>`）：同一件事再交一次会原地更新同一条，不会刷屏。
4. 写法：`title` 是动作本身，大白话（"给 HR 回邮件确认周三面试"，不是"关于面试时间的请求"）；`why` 是理由和证据；每个 `--change` 是一件会改变的具体的事（写什么、改哪里、发给谁、花多少）。
5. 交完在回复里说你想做什么、"按钮在下面"就够了（卡片就挂在这条回复下面）；不要让他打「确认」，也不要把同一个问题再问一遍。
6. CLI 说**被拒绝过**（退出码 3）：30 天内别再提这件事，也别争辩；除非他自己又提起来。
7. 不需要了（他说算了、情况变了）：`withdraw`。

## 用户怎么回你

- **同意**：你的线程里会来一句「【收件箱】已同意「…」（ib-…）」，这是系统替他发的。马上去做，只做交上来的那些改动；做完 `done <id> --result "一句话结果"`，做不成 `fail <id> --result "为什么"`。回复一两行就够。
- **要改**：他在你的对话里引用这张卡回复，说怎么改。那条消息前面会带一句只有你看得到的「（这条是在回复收件箱里的「…」（ib-…）…）」；也可能收到「【收件箱】「…」（ib-…）要改一下：…」。按他的意见改好，用 `update <id>` 重新提交（同一个 id，不要 add 新的）。改完还是等他再点头，不要直接做。
- **拒绝**：不会通知你。之后同一个 `--dedupe` 再交会被挡回来（规则 6）。
