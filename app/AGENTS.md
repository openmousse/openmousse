## OpenMousse app conventions

What this is: the iOS / Android / Web client of OpenMousse — a shell for a personal agent that runs on your own OpenClaw. All data comes from your own server ([`../server/`](../server/)); there is no sample data. When the server is unreachable every page shows "not connected" and sending fails loudly (`OfflineApi`) instead of faking a reply.

### Identity and build

- **Per-instance identity stays out of git**: `app.local.json` (name, slug, bundle ids, EAS project id, owner, icon directory; template in `app.local.example.json`) plus the icons in `assets/local/`. `app.json` is the generic template (OpenMousse); `app.config.js` overlays the identity file. Permission strings use `{name}` and get the assistant's name.
- The environment variable `MOUSSE_LOCAL` selects a different identity file (`none` = pure template). This is how one codebase builds two apps under one Apple account: `eas.json`'s `production` profile uses `app.local.json`, `production-openmousse` uses `app.local.openmousse.json`. Pass the same variable when running `eas update` for that app.
- **`.easignore` must live at the git repository root** (`../.easignore`). When it exists EAS ignores `.gitignore`, which is what lets the untracked identity files and icons travel with the build. Check what would be uploaded with `npx eas-cli build:inspect --platform ios --profile production --stage archive --output <dir>`.
- `eas init` writes `extra.eas.projectId` into `app.json`; move it into the identity file afterwards. The template must not carry anyone's project id.
- `runtimeVersion` follows `appVersion`. JS-only changes ship with `eas update --channel production --environment production`; anything native (new module, permissions, entitlements) needs a new build and a bumped `version` first, so old binaries never receive a bundle that references a module they do not have. Never OTA a bundle that imports a native module absent from the installed binary; keep the last known-good update group id for `eas update:republish`.
- `eas update` exports into `dist/` by default, the same folder `../server` serves as the web version, and leaves it without the home-screen tags `scripts/build-web.mjs` adds. Run `npm run web:build` again after every `eas update`.

### Architecture

- **Navigation is React Navigation, not Expo Router**, on purpose: `NavigationContainer` has no `linking`, so the single-file web preview works from any path. Do not migrate.
- **Icons only from `src/components/icons.ts`**. Importing from `lucide-react-native` directly pulls thousands of icons into the bundle. Add a line there for a new icon.
- **Bottom sheets use `src/components/Sheet.tsx`**, not React Native's `Modal` (which escapes the phone frame on web). Inside a native modal screen wrap the page in its own `SheetProvider`. `open` dismisses the keyboard first and the sheet slides in as it goes down; a sheet with its own inputs lifts above the keyboard by itself. Sheets render outside the `NavigationContainer`, so content inside a sheet can't call `useNavigation` (it throws); navigate with `navigationRef` from `src/navigation.tsx`.
- **Keyboard: react-native-keyboard-controller (native since 1.0.5, `KeyboardProvider` in `App.tsx`), never RN's `KeyboardAvoidingView` with a hard-coded `keyboardVerticalOffset`** (it compares a parent-relative layout with screen coordinates; the old `90` left a 90pt gap). `useBottomInset(ref?)` in `src/components/keyboard.ts` measures the view in the window and returns `style` (an animated `paddingBottom` for a `Reanimated.View`: the keyboard height frame by frame, or the home-indicator inset when closed and the view reaches the screen bottom), `spacer` (the same as a height, for containers you can't pad, like the sheet), and the numbers `home` / `offset` (gap to the screen bottom + home). Chat uses `ChatScroll` (iOS: `KeyboardChatScrollView`, which lifts the messages with the keyboard) and `KeyboardSticky` (the composer follows the keyboard by transform, clamped so it never moves down), both given `offset`; keep `list.current.inset` (from `onInsetChange`) in any "scroll to the end" math. Lists use `dismissMode`: `interactive` on iOS (the keyboard follows the finger when you drag down), `on-drag` on Android, `none` on web (react-native-web's `on-drag` blurs the input on every scroll, including auto-scroll to a new reply). Don't pass `useBottomInset` a ref inside a native modal (coordinates there are modal-relative). Form screens use `KeyboardScroll` (same file) instead of a bare `ScrollView`: iOS gets `automaticallyAdjustKeyboardInsets`, Android (no such prop, and since Android 15 the window no longer shrinks for the keyboard) gets keyboard-controller's `KeyboardAwareScrollView`; pass `layout` when the page is `flexGrow: 1` with buttons at the bottom so they move above the keyboard. The chat list dismisses the keyboard on tap (`keyboardShouldPersistTaps="never"`).
- **Native extensions (1.0.5)**: `targets/` holds three Swift targets generated by `@bacons/apple-targets` at prebuild: `share` (share sheet → Zen's Noted with an optional note; since 1.0.6 it no longer asks: a link or files become a saved item, plain text a thought; uploads straight to the server, falls back to an App Group `outbox/` the app flushes on launch), `widgets` (Home / Lock Screen widgets from `GET /api/widget`, plus the Live Activity UI) and `notify` (notification content extension that draws `data.card` for categories `card` and `inbox`). They share App Group `group.<bundle id>` (set in `app.config.js`; extensions derive it from their own bundle id): server URL, app name and language in its UserDefaults, the token in the keychain with that access group, `widget.json` and `outbox/` in its container. `share` and `widgets` each carry the same `MousseShared.swift` (`scripts/sync-target-shared.sh` copies / `--check`s it). The app side is the local module `modules/mousse-native` (Swift + `index.ts`): `setShared`, `writeWidgetSnapshot`, `outbox`, Live Activities (`liveStart` / `liveUpdate` / `liveEnd`, push tokens as events) and the edit-menu hook; glue in `src/api/native.ts` (all no-ops on web, Android and older binaries). `MousseActivityAttributes` is defined twice (module and `targets/widgets/LiveActivity.swift`) and must stay identical. `plugins/withExtensionVersions.js` sets the extensions' `MARKETING_VERSION` to the app's version. The first build after adding a target or entitlement needs an interactive `eas build` with an Apple login (EAS registers the new bundle ids / App Group and makes profiles); `eas build --profile simulator` compiles everything without credentials.
- **Think input edit menu**: the capture bar sends on Return when the native module is present and adds 换行 / 全屏写 to the system long-press menu (`editMenu(key, items, onPick)` in `src/api/native.ts`; the key is the TextInput's `testID`). The hook adds `textView:editMenuForTextInRange:suggestedActions:` to RN's `RCTBackedTextViewDelegateAdapter` at launch and inserts the newline natively (it sets RN's `_textWasPasted` so the return-to-submit check lets it through); if it can't, the event comes back with `handled: false` and JS inserts it at the tracked selection.
- **HealthKit background delivery (1.0.5)**: the healthkit plugin has `background: true`; `startHealthBackground` (`src/api/health.ts`) registers sleep, HRV and resting HR, and a wake-up syncs two days without all metrics and without posting a `foreground` signal. A launch in the background (`AppState.currentState !== 'active'`) also skips the full metrics sync, the foreground signal and starting Live Activities.
- **Hardware (1.0.6, Bluetooth)**: Settings → App → Hardware (`HardwareScreen`, route `Hardware`) connects a Flipper Zero over BLE with `react-native-ble-manager`. Three layers in `src/hardware/`. `ble.ts` is the only file that touches the library: it is `require`d only when `Platform.OS !== 'web'` and `TurboModuleRegistry.get('BleManager')` exists, so the web bundle and pre-1.0.6 binaries never load it (`bleAvailable()` false → the page says it needs the 1.0.6 app). Android 12+ asks BLUETOOTH_SCAN / CONNECT; Android ≤ 11 asks fine location (the plugin declares it only up to SDK 30). The Flipper advertises only the 16-bit `0x3080 | color` UUID, not the serial service, so scans run unfiltered and match `308x` or a "Flipper …" name in JS. Serial: notify `…61fe…` (in) and `…63fe…` (flow), write `…62fe…` with response in chunks of min(flow budget, MTU − 3); the budget is a big-endian uint32, starts at 1024 and is only renewed by a notification after it reaches 0, so never write past it. `flipperRpc.ts` is a hand-written protobuf for Flipper RPC 0.25 (varint-delimited `PB.Main`, non-zero command ids, one request at a time, `has_next` reassembly, `command_id` 0 events, timeouts); run `node scripts/test-flipper-rpc.mjs` after touching it: one malformed frame makes the Flipper drop the session and the BLE link. `flipper.ts` has the actions under the USB bridge's names, arguments, result shapes and path rules (`bridge/flipper_bridge.py`: status / files / read / ir_buttons / ir_send / ping); `handle(action, args)` is the seam for an OTA that makes the phone a second bridge transport (no server side yet; `ir_learn` stays USB-only, RPC has no IR receive). Sending IR: `app_start("Infrared", "RPC")`, wait for both the OK and the unsolicited `APP_STARTED` → `app_load_file` → press-release by name (field 75 when the protocol is ≥ 0.25, else press, 500 ms, release) → `app_exit` always; status 17 = another app is open on the Flipper. The remembered device is `mousse.flipper` in `deviceStore`.
- **In-app notifications go through the banner** (`src/components/Banner.tsx`, `useBanner().show`), never a system notification while the app is in the foreground (`src/api/push.ts` suppresses those). Same source + target replaces the queued one; several within 4 s merge into one expandable summary. Only `level: ring` pushes (or old servers without `level`) get a banner; on web, where there is no push, the unread poll shows one only for replies to your own messages (`mine` went up) and new inbox items.
- **A screen that shows a conversation calls `useThreadOnScreen(threadId)`** (`src/store.tsx`): that thread gets no banner and is marked read (`POST /api/unread/read` with the last `db<id>` on screen) while it is focused and the app is active.
- **Theme** in `src/theme.tsx`: gold = the assistant itself; cyan = data and progress; semantic colors only for state. Chart colors are `t.viz` (see **Chart kit** below); `chartA` / `chartB` equal `t.viz.series[0]` / `[1]` and stay for older code. Both are validated on both backgrounds — do not change casually.
- **Text follows the system text size (Dynamic Type), so fixed widths break**: a fixed-width column holding text (times on the left of the schedule, journal times) gets its width from `useScaledWidth(base)` in `src/components/ui.tsx` (base × font scale, capped at 1.6×) and its clock text `numberOfLines={1}` + `adjustsFontSizeToFit`. A plain `width: 46` wrapped "11:00" into "11:0 / 0" on a phone with larger text (2026-09-28). Web always reports font scale 1, so check this on a device.
- **Agent colors**: `t.tints` / `agentTint()` in `src/theme.tsx`, six soft + fg pairs per mode (fg on soft ≥ 4.5:1 in both; `null` from the server = cyan). Anything that says which Agent something belongs to goes through `GroupBadge` / `SourceBadge` / `SourcePill` (`src/components/SourceBadge.tsx`) so it follows the Agent's color. Agent icons are the 24 keys in `src/components/GroupIcon.tsx` (the server accepts the same set).
- **Dashboards** are ordered by the question you want answered (now → today → this week → long term). Where the data comes from is a small caption on the right of the `SectionLabel` (`Caption` / `HealthCaption` in `LiveBoards.tsx`), not a header; long lists are one row each that expands in place (`Disclosure`).
- **Chat tab** (2026-10-13 redesign, `src/screens/ChatScreen.tsx`, parts in `src/components/ChatParts.tsx`, API `src/api/chats.ts`, server `../server/chats.py`): four tabs (Chats / Zen / Today / Goals); the Agents tab and the chat drawer are gone. The header has Search, New (+) and Settings (`Me`; account initials when signed in), in the same place on both sides. `PillTabs` switches **assistant | Friends** (Friends only when `/api/unread` carries `friends`). The assistant side is the Agent bar (`AgentBar`: `StateFace` around each Agent: a turning cyan arc = working (a reply is running or a background task it started is), an amber dot = waiting for you (an inbox item with its thread or source), otherwise the unread count; tap = its chat, long-press = Pin / Mute / Edit / Delete), then the rows (`ChatRowView` in `SwipeRow`): the main chat, fixed first (it can be muted, never deleted), meetings and Agent groups (kinds `meeting` / `room`; the meetings module supplies them through `/api/chats`, tapping opens route `Meeting`), projects, and at the bottom "Ended meetings · N" / "Archived projects · N" (`ChatArchive`). Swipe left or long-press a row for Pin / Mute / Delete; Delete always asks first and says what happens (`ConfirmDelete`; `useChatActions` is shared with the Info page). Order and unread come from the server and count only your own messages and replies to them (`origin=user`): nightly digests, inbox follow-ups and relays neither reorder a row nor add unread. Pins and mutes live on the server (`PATCH /api/chats/{thread}`; a muted thread gets no push and stays out of the app badge). `useChatList()` overlays what the app knows sooner (typing → working, `inbox` → waiting, a thread missing from `unread.threads` → read) and `useChatBadge()` is the tab badge. Without `supports('chats.list')` the list is built from groups / sideChats / unread (`fallbackList`): no pin or mute, projects can still be deleted. "+" follows the side: assistant = Start a meeting (only with `supports('meetings')` and a `NewMeeting` route) / New Agent / New project / Scan; Friends = Add a friend / Scan (both Scan items greyed on web: phone app only). **Scan** (1.0.6, `src/screens/ScanScreen.tsx`, route `Scan`, full-screen modal; param `kind: pair | friend` only picks the hint line; also the button next to the pairing-code field on the Connect page, which works before any server is connected): expo-camera's `CameraView` reading QR codes only, camera permission asked on entry (refused for good → Open Settings, re-checked when the app comes back). expo-camera is `require`d only on native when the screen renders, so the web bundle never contains it (web shows a note) and a binary without the module shows "needs a newer version of the app". The text goes to `openScanned(text)` in `src/navigation.tsx`: `<scheme>://pair?s=<server>&c=<code>` (what Claw → Add a device and `tokens.py pair` draw) or a bare 8-character code → `openPair` = the Connect page filled in, never connecting by itself (same rule as the pairing deep link); a friend invite (the QR is the invite link itself, `https://<root>/f/i/<token>/<key>`, where the root may be the relay's `https://relay.openmousse.ai/u/<kid>`; `<scheme>://friends/add?code=…` too) → `AddFriend`, or "connect to your server first" when this device has none; anything else keeps the camera open with "not recognized". A code that was already handled or rejected is ignored while it stays in view. Search filters the assistant side locally and offers "Search messages" (→ `History` with `q`); on the Friends side it shows FriendsHome's own search.
- **One chat page** (`ChatHeader`): back / avatar with the same state ring / name + subtitle / ⓘ, for the main chat and projects (`ThreadScreen`, route `Chat`, one screen per thread through `getId`), Agents (`GroupScreen`, now only the chat) and friends (`FriendChatScreen`). The per-thread model, History, pin, mute and delete moved into ⓘ → `Info` (`InfoScreen`, params `kind` = agent | main | project | friend | meeting, `id`, `tab`): an Agent's first screen is its dashboard (`AgentBoard`, exported from GroupScreen), then Memory and Settings (chat model, history, pin, mute, Edit Agent, Delete Agent: its memory isn't deleted, the workspace moves to the archive); the main chat, projects (rename / archive / restore / delete) and friends (`FriendInfoBody`, the old … sheet, plus Delete chat = `POST /api/friends/{id}/clear`, only on your server) each get one settings page. Old links to `Group` with `tab: board | memory` push `Info` over the chat; push target `board` opens `Info` directly.
- **UI copy** (2026-10-05): every string is `L('中文', 'English')`, written like the openmousse.ai site — professional, short, declarative, no chatty particles (吧 / 呢 / 就好 / 一下 / 看看) or cute anthropomorphism. Fixed patterns: success 已保存 / 已发送 / 已复制; failure 保存失败 / 发送失败 / 无法加载 / 无法连接; in progress 正在加载…; buttons are 2–4 character verbs (保存、发送、重试、查看). Terms: Agent (capital A, also in Chinese), 名片 Agent, 好友 / 添加好友 (feature names), 主对话, 世界树, Zen, Doorman, 收件箱, 看板, 连接器. Use 你, never 他 / 她 for a friend (their name or 对方). Text sent to the server or model as the user's own message (e.g. the welcome card's 我第一次用，带我走一遍。, which the onboarding skill matches) stays as is.
- **Assistant name is never hard-coded**: `src/brand.ts` `agentName()` comes from the server's `/api/health` (`app_name`), remembered between launches. Do not write a product name into UI strings.
- **Chat typing stays cheap** (2026-10-05; the main chat lagged on every key twice, 9/28 and 10/5): the composer row is its own memo component (`ChatComposer.tsx`) that owns the draft, voice input and send / stop, so a keystroke re-renders only that row; `ChatView` talks to it through `ComposerHandle` (`set` / `fill` / `focus`). Streamed reply text is not in the store but in `src/api/partial.ts` (`usePartial`), like `progress.ts`: a store change re-renders every `useStore()` consumer in the app, and a reply streams dozens of chunks a second. `Bubble`, `ReplyText`, `ChatInbox`, `ChatTasks` and `Markdown` are `React.memo` and `Bubble` doesn't read the store (avatar and Agent ids come in as props). Keep it that way: everything passed into the memoized message list or the composer must be stable (callbacks through the `handlers` ref, no inline `[]` / `{}` / arrow functions; `useSelect` returns the same empty array). One unstable dependency re-parses the whole day's Markdown on every key: on 10/5 that was 130 ms per key on desktop Chrome for a 40-message main chat; after the split it was 3 ms, and a streamed chunk re-rendered 29 components instead of about 3,500.
- **Unsent drafts** persist per thread through `src/drafts.ts` (`loadDraft` / `saveDraft`) on top of `src/deviceStore.ts` (synchronous small strings on this device): iOS uses React Native's built-in `Settings` (NSUserDefaults, linked in every RN build, so no new native module), web uses localStorage, Android a file in the app's documents directory (`expo-file-system`, loaded only on Android). Don't put drafts in the keychain (`expo-secure-store` may reject values over ~2 KB).
- **First run** (2026-09-28): `/api/health` says `first_run` when the server has no messages and no Agents yet (`probe()` → store `firstRun`). While it's true and the main chat is empty, the Chat tab shows a "Get started" card above the list (Walk me through it sends the line below and opens the main chat), and `ThreadScreen` gives `ChatView` the same card as `welcome`, in the empty state's place (the History link hides too): **Walk me through it** sends 我第一次用，带我走一遍。 / It's my first time here. Walk me through it. (by app language), which the main agent's `packs/core/skills/onboarding` picks up; **I'll explore myself** hides it on this device (`src/welcome.ts`, stored like drafts). Sending anything or creating an Agent sets `firstRun` to false locally; the server agrees on the next probe.
- Data loading is centralized in `src/store.tsx` (`LOADERS`), API calls in `src/api/`. Server routes and the source of truth for every page are documented at the top of `../server/data.py`.

### Chart kit (可视化素材库, 2026-10-13)

- **Every chart, figure and data view goes through `src/components/viz/`** (`import { … } from '../components/viz'`); don't hand-draw charts with Views or SVG in a screen. `charts.tsx` keeps the old names (`Ring`, `Bar`, `DayBars`, `TrendLine`) as thin wrappers for the older boards, and board blocks of type stat / progress / chart render kit components. The showcase is Settings → About → Chart kit (web `?screen=VizKit`): every component with its rule, on fixed example data (`src/screens/vizKitData.ts`: fictional, and the only sample data in the app; never put real records there). A new component gets a card there.
- **Palette `t.viz`** (checked with the dataviz skill's `validate_palette.js` in both modes, on the card and page backgrounds): `series` = six categorical colors in a fixed order (cyan, gold, violet, green, blue, pink; light `#1488A3 #B07D22 #7B5CC7 #2F8A5B #4A72C2 #B24F86`, dark `#2A97B0 #B5873A #8E6FD8 #3E9E6E #5E86D6 #C0679A`); `seq` = a five-step one-hue ramp, low → high (heatmaps; binned cells use steps 1–4, step 0 means "near zero"); `other` = the grey for "Other" and de-emphasis (under 3:1, so always labelled); `emph` = the current item; `grid` / `axis` = hairlines. Status stays `good` / `warn` / `bad`, only ever means state and always comes with an icon and words (`StatusTag`, `ChangeTag`, `StatusGlyph`). Any new or changed color runs through `validate_palette.js` in both modes (`--mode light --surface "#FFFFFF"`, `--mode dark --surface "#14171C"`; add `--pairs all` for forms where any two marks can touch, `--ordinal` for a ramp). Among the first three dark colors any-pair separation is 7.5 (warning band), so forms like the month calendar add shape as a second channel.
- **Rules**: assign categorical colors in order and by identity (pass `slot` so a filtered-out series doesn't repaint the rest); never generate a seventh color, fold the tail into "Other" (`Donut` does it); one series takes slot 0 and needs no legend, two or more always get a `Legend`; text wears ink colors, never the series color; one y-axis per chart (two measures → two charts); label only the key values (current, peak) and let a tap show the rest; big standalone numbers use proportional figures, aligned columns use `tabular-nums`. Marks follow `vizMark`: 2px lines, bars at most 24 wide with a 4px rounded tip and a square base, 8px markers with a 2px surface ring, 2px surface gaps between touching fills, hit targets of 24+. On anything other than a card background wrap the chart in `VizSurface` so rings and gaps use that color.
- **Which component**:
  - one number (with a change and a trend): `StatTile`, several in a row `StatRow`. A one-bar chart or a two-slice pie is a stat tile;
  - progress to one goal: `ProgressRing` / `ProgressBar`; item by item: `SegmentBars`; actual against a target that can be passed: `TargetBar`;
  - trend: `Sparkline` next to a number; `LineChart` with axes (`band` for a target range, `dates` to space points by date, `secondary` for a second source drawn as hollow rings, `area` for one series);
  - compare amounts: `BarChart` (one series), `StackedBar` (parts per category), `HBarChart` (many or long-named categories; `sort="desc"` when they have no order);
  - part to whole: `Donut` for 3–6 parts, `PercentBar` for two, `NutritionRing` for macros by calories;
  - before / after: `BeforeAfter` (dumbbell) with a `ChangeTag`, `CompareList` for several items;
  - time: `HeatCalendar` (one value per day on the ramp), `MonthCalendar` (event / deadline / to-do marks by color and shape, with a legend), `DayGrid` (a day's items sized by duration, long free stretches folded, now line), `Timeline` (time left to deadlines), `Streak`, `SleepStages`;
  - a collection: `DataTable` (sortable headers, tag cells — `tone` for state, `slot` for a choice value so it matches the column dot; `onSort` hands sorting to the caller when the server sorts and pages; also the table twin of a chart via `ChartCard table={…}`), `Kanban` (compact: columns by a field, long-press a card to move it), `KanbanBoard` (full screen: each column scrolls, long-press and drag a card to another column; `onDragging` lets the screen turn its back gesture off). Tags on cards use `cardToneColors` (a neutral tag needs a lighter chip on dark cards), choice tags `slotColors`.
- **Interaction and states**: tapping a mark shows its value (`Tip`; line charts snap a crosshair to the nearest point and follow a drag); `RangeSwitch` (7 / 30 / 90 days) sits above the charts it scopes; `ChartCard` is the titled card with a caption or control on the right and the chart / table toggle. Every component takes `loading` / `error` / `onRetry` / `emptyText` / `onAdd` and shows the empty, loading or error state (`VizEmpty` / `VizLoading` / `VizError`); a reload that already has data dims the chart instead of flashing a skeleton. Each component builds an accessibility label listing its values unless you pass `label`; label columns use `useScaledWidth`, and all chart text is React Native `Text`, so it follows the system text size. The server formats values (`text` on points and items); the kit only draws.

### Server contract (see `../server/`)

- All configuration is `~/.openmousse/server.json` on the server. `/api/*` requires `Authorization: Bearer <token>` (also `X-API-Key`, and `?token=` on GET for files: `<Image>` loads and the web build's `<audio>`); static files are public.
- **Server version** (2026-10-05): `/api/health` has `server` = `{version, commit, api, features, openclaw}` from `../server/version.py` (version is the release date, like OpenClaw's). The app is hot-updated and almost always newer than the server, so new code checks `supports('<feature>')` (`src/api/version.ts`) instead of probing for a 404, and the server change adds that name to `FEATURES` in the same commit. When the app starts relying on something new, bump `API` there and `SERVER_API` here: a server below it shows "update needed" under Settings → My claws, with the update command (`UPDATE_CMD`, re-running the installer). Anything unavailable on an old server says so through `needsUpdate()`, one wording everywhere. Servers from before this have no `server` and count as api 0; once everyone is past a level, the 404 fallbacks for what that level has can go.
- Connection page (`src/screens/ConnectScreen.tsx`): native builds store base URL + token in the keychain (`expo-secure-store`), web uses localStorage and defaults to same-origin. `probe()` returns ok / auth / down. Until the app is connected, the page links to the getting-started guide (`https://openmousse.ai/start.html`).
- Chat (`src/api/client.ts`): SSE streaming; a reply runs to completion on the server even if the client disconnects, and `GET /api/chat/stream?thread=` re-attaches. Long-press a message: copy / quote / edit / rewind (`/api/chat/rewind`) / delete.

### Debugging

- Web supports deep links for screenshots: `?screen=Chat&id=<thread>`, `?screen=Group&id=<id>`, `?screen=Info&kind=agent&id=<id>&tab=board` (also `main` / `project` / `friend` / `meeting` with `id=grp-…`), `?friends=1` (Chat tab on the Friends side), `?screen=今天`, `?screen=VizKit` (the chart kit, no server needed), `?screen=ThinkTalk&id=tp-…`, `?screen=ThinkSearch&q=…`, `?screen=ThinkWrite&zen=1` (with focus time started through the API). `?say=hello` sends a real message after connecting, on the dev server only (`npm run web`); production builds ignore it so a link can never make the agent act.
- `npx expo lint` caches under `.expo/cache/eslint`; a stale `import/namespace` error survives fixing the imported file — delete the cache or run `npx eslint src`.
- Headless Chrome's minimum window width is 500px; screenshots at 390px show a false right-edge crop.
- The Expo ESLint config includes the React Compiler rules: don't write `ref.current` during render (update it in an effect), don't call `setState` synchronously inside an effect (adjust state during render by comparing with the previous value), and keep `Date.now()` out of component bodies.
