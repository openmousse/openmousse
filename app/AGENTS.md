## OpenMousse app conventions

What this is: the iOS / Android / Web client of OpenMousse — a shell for a personal agent that runs on your own OpenClaw. All data comes from your own server ([`../server/`](../server/)); there is no sample data. When the server is unreachable every page shows "not connected" and sending fails loudly (`OfflineApi`) instead of faking a reply.

### Identity and build

- **Per-instance identity stays out of git**: `app.local.json` (name, slug, bundle ids, EAS project id, owner, icon directory; template in `app.local.example.json`) plus the icons in `assets/local/`. `app.json` is the generic template (OpenMousse); `app.config.js` overlays the identity file. Permission strings use `{name}` and get the assistant's name.
- The environment variable `MOUSSE_LOCAL` selects a different identity file (`none` = pure template). This is how one codebase builds two apps under one Apple account: `eas.json`'s `production` profile uses `app.local.json`, `production-openmousse` uses `app.local.openmousse.json`. Pass the same variable when running `eas update` for that app.
- **`.easignore` must live at the git repository root** (`../.easignore`). When it exists EAS ignores `.gitignore`, which is what lets the untracked identity files and icons travel with the build. Check what would be uploaded with `npx eas-cli build:inspect --platform ios --profile production --stage archive --output <dir>`.
- `eas init` writes `extra.eas.projectId` into `app.json`; move it into the identity file afterwards. The template must not carry anyone's project id.
- `runtimeVersion` follows `appVersion`. JS-only changes ship with `eas update --channel production --environment production`; anything native (new module, permissions, entitlements) needs a new build and a bumped `version` first, so old binaries never receive a bundle that references a module they do not have. Never OTA a bundle that imports a native module absent from the installed binary; keep the last known-good update group id for `eas update:republish`.
- `eas update` exports into `dist/` by default, the same folder `../server` serves as the web version, and leaves it without the home-screen tags `scripts/build-web.mjs` adds. Run `npm run web:build` again after every `eas update`.

### Architecture

- **Navigation is React Navigation, not Expo Router**, on purpose: `NavigationContainer` has no `linking`, so the single-file web preview works from any path. Do not migrate.
- **Icons only from `src/components/icons.ts`**. Importing from `lucide-react-native` directly pulls thousands of icons into the bundle. Add a line there for a new icon.
- **Bottom sheets use `src/components/Sheet.tsx`**, not React Native's `Modal` (which escapes the phone frame on web). Inside a native modal screen wrap the page in its own `SheetProvider`. `open` dismisses the keyboard first and the sheet slides in as it goes down; a sheet with its own inputs lifts above the keyboard by itself. Sheets render outside the `NavigationContainer`, so content inside a sheet can't call `useNavigation` (it throws); navigate with `navigationRef` from `src/navigation.tsx`.
- **Keyboard: react-native-keyboard-controller (native since 1.0.5, `KeyboardProvider` in `App.tsx`), never RN's `KeyboardAvoidingView` with a hard-coded `keyboardVerticalOffset`** (it compares a parent-relative layout with screen coordinates; the old `90` left a 90pt gap). `useBottomInset(ref?)` in `src/components/keyboard.ts` measures the view in the window and returns `style` (an animated `paddingBottom` for a `Reanimated.View`: the keyboard height frame by frame, or the home-indicator inset when closed and the view reaches the screen bottom), `spacer` (the same as a height, for containers you can't pad, like the sheet), and the numbers `home` / `offset` (gap to the screen bottom + home). Chat uses `ChatScroll` (iOS: `KeyboardChatScrollView`, which lifts the messages with the keyboard) and `KeyboardSticky` (the composer follows the keyboard by transform, clamped so it never moves down), both given `offset`; keep `list.current.inset` (from `onInsetChange`) in any "scroll to the end" math. Lists use `dismissMode`: `interactive` on iOS (the keyboard follows the finger when you drag down), `on-drag` on Android, `none` on web (react-native-web's `on-drag` blurs the input on every scroll, including auto-scroll to a new reply). Don't pass `useBottomInset` a ref inside a native modal (coordinates there are modal-relative). Form screens use `automaticallyAdjustKeyboardInsets` on their `ScrollView`. The chat list dismisses the keyboard on tap (`keyboardShouldPersistTaps="never"`).
- **Native extensions (1.0.5)**: `targets/` holds three Swift targets generated by `@bacons/apple-targets` at prebuild: `share` (share sheet → Saved or Think, with a note; uploads straight to the server, falls back to an App Group `outbox/` the app flushes on launch), `widgets` (Home / Lock Screen widgets from `GET /api/widget`, plus the Live Activity UI) and `notify` (notification content extension that draws `data.card` for categories `card` and `inbox`). They share App Group `group.<bundle id>` (set in `app.config.js`; extensions derive it from their own bundle id): server URL, app name and language in its UserDefaults, the token in the keychain with that access group, `widget.json` and `outbox/` in its container. `share` and `widgets` each carry the same `MousseShared.swift` (`scripts/sync-target-shared.sh` copies / `--check`s it). The app side is the local module `modules/mousse-native` (Swift + `index.ts`): `setShared`, `writeWidgetSnapshot`, `outbox`, Live Activities (`liveStart` / `liveUpdate` / `liveEnd`, push tokens as events) and the edit-menu hook; glue in `src/api/native.ts` (all no-ops on web, Android and older binaries). `MousseActivityAttributes` is defined twice (module and `targets/widgets/LiveActivity.swift`) and must stay identical. `plugins/withExtensionVersions.js` sets the extensions' `MARKETING_VERSION` to the app's version. The first build after adding a target or entitlement needs an interactive `eas build` with an Apple login (EAS registers the new bundle ids / App Group and makes profiles); `eas build --profile simulator` compiles everything without credentials.
- **Think input edit menu**: the capture bar sends on Return when the native module is present and adds 换行 / 全屏写 to the system long-press menu (`editMenu(key, items, onPick)` in `src/api/native.ts`; the key is the TextInput's `testID`). The hook adds `textView:editMenuForTextInRange:suggestedActions:` to RN's `RCTBackedTextViewDelegateAdapter` at launch and inserts the newline natively (it sets RN's `_textWasPasted` so the return-to-submit check lets it through); if it can't, the event comes back with `handled: false` and JS inserts it at the tracked selection.
- **HealthKit background delivery (1.0.5)**: the healthkit plugin has `background: true`; `startHealthBackground` (`src/api/health.ts`) registers sleep, HRV and resting HR, and a wake-up syncs two days without all metrics and without posting a `foreground` signal. A launch in the background (`AppState.currentState !== 'active'`) also skips the full metrics sync, the foreground signal and starting Live Activities.
- **In-app notifications go through the banner** (`src/components/Banner.tsx`, `useBanner().show`), never a system notification while the app is in the foreground (`src/api/push.ts` suppresses those). Same source + target replaces the queued one; several within 4 s merge into one expandable summary. Only `level: ring` pushes (or old servers without `level`) get a banner; on web, where there is no push, the unread poll shows one only for replies to your own messages (`mine` went up) and new inbox items.
- **A screen that shows a conversation calls `useThreadOnScreen(threadId)`** (`src/store.tsx`): that thread gets no banner and is marked read (`POST /api/unread/read` with the last `db<id>` on screen) while it is focused and the app is active.
- **Theme** in `src/theme.tsx`: gold = the assistant itself; cyan = data and progress; semantic colors only for state. `chartA` / `chartB` are validated on both backgrounds — do not change casually.
- **Text follows the system text size (Dynamic Type), so fixed widths break**: a fixed-width column holding text (times on the left of the schedule, journal times) gets its width from `useScaledWidth(base)` in `src/components/ui.tsx` (base × font scale, capped at 1.6×) and its clock text `numberOfLines={1}` + `adjustsFontSizeToFit`. A plain `width: 46` wrapped "11:00" into "11:0 / 0" on a phone with larger text (2026-09-28). Web always reports font scale 1, so check this on a device.
- **Agent colors**: `t.tints` / `agentTint()` in `src/theme.tsx`, six soft + fg pairs per mode (fg on soft ≥ 4.5:1 in both; `null` from the server = cyan). Anything that says which Agent something belongs to goes through `GroupBadge` / `SourceBadge` / `SourcePill` (`src/components/SourceBadge.tsx`) so it follows the Agent's color. Agent icons are the 24 keys in `src/components/GroupIcon.tsx` (the server accepts the same set).
- **Dashboards** are ordered by the question you want answered (now → today → this week → long term). Where the data comes from is a small caption on the right of the `SectionLabel` (`Caption` / `HealthCaption` in `LiveBoards.tsx`), not a header; long lists are one row each that expands in place (`Disclosure`).
- **Agents tab**: one row per Agent or a two-column grid, switched at the top right and remembered on the device (`loadAgentsView` / `saveAgentsView` in `src/api/base.ts`). Grid tiles show one line of state from the boards (this week's workouts, today's kcal, recovery, next deadline) and fall back to the last line / purpose.
- **Assistant name is never hard-coded**: `src/brand.ts` `agentName()` comes from the server's `/api/health` (`app_name`), remembered between launches. Do not write a product name into UI strings.
- **Unsent drafts** persist per thread through `src/drafts.ts` (`loadDraft` / `saveDraft`): iOS uses React Native's built-in `Settings` (NSUserDefaults, linked in every RN build, so no new native module), web uses localStorage. Don't put drafts in the keychain (`expo-secure-store` may reject values over ~2 KB).
- **First run** (2026-09-28): `/api/health` says `first_run` when the server has no messages and no Agents yet (`probe()` → store `firstRun`). While it's true and the main chat is empty, `ChatScreen` gives `ChatView` a `welcome` card ("Start here") that takes the empty state's place (the History link hides too): **Walk me through it** sends 我第一次用，带我走一遍。 / It's my first time here. Walk me through it. (by app language), which the main agent's `packs/core/skills/onboarding` picks up; **I'll explore myself** hides it on this device (`src/welcome.ts`, stored like drafts). Sending anything or creating an Agent sets `firstRun` to false locally; the server agrees on the next probe.
- Data loading is centralized in `src/store.tsx` (`LOADERS`), API calls in `src/api/`. Server routes and the source of truth for every page are documented at the top of `../server/data.py`.

### Server contract (see `../server/`)

- All configuration is `~/.openmousse/server.json` on the server. `/api/*` requires `Authorization: Bearer <token>` (also `X-API-Key`, and `?token=` on GET for files: `<Image>` loads and the web build's `<audio>`); static files are public.
- Connection page (`src/screens/ConnectScreen.tsx`): native builds store base URL + token in the keychain (`expo-secure-store`), web uses localStorage and defaults to same-origin. `probe()` returns ok / auth / down. Until the app is connected, the page links to the getting-started guide (`https://openmousse.ai/start.html`).
- Chat (`src/api/client.ts`): SSE streaming; a reply runs to completion on the server even if the client disconnects, and `GET /api/chat/stream?thread=` re-attaches. Long-press a message: copy / quote / edit / rewind (`/api/chat/rewind`) / delete.
- **The composer never locks while a reply is running** (2026-09-28): a message sent mid-reply is queued by the server (`queued` SSE event → `onQueued` swaps in the `db<id>` and marks the bubble `queued`; the batch turn's `start` → `onDequeued`), and the connection then streams the batch turn's reply. Several sends can wait on the same reply (`appendMsg` dedupes by id), so "typing" follows the store's per-thread `sending` counter, and both re-attach paths (`loadThreads`, `refreshThread`) re-read the thread when history still had queued messages. With the input empty the send button becomes Stop (`/api/chat/stop`). A reply that answers several messages starts each part with a line `> 「…」`: `ReplyText` / `splitQuotes` in `ChatView.tsx` draw it as a `QuoteChip` that jumps to the matching user message (`resolveQuote`). Long-press → Quote sends `replyTo`, and the user bubble shows `m.replyTo` above the text. When the server talks to the Gateway over its WebSocket channel (`chat.transport: ws`), a mid-reply send cuts into the running turn instead of queueing: the `queued` event carries `steer: true`, the bubble is `steered` ("Cut in"), and the stream then follows the same reply; a `text` SSE event replaces the streamed text wholesale. Background tasks this thread started that are still running show as a strip at the top of the chat (tap → the task, or Tasks when there are several).
- Optional data sources: `/api/health` reports `sources` (workouts, meals, body, calendar, health). `loadLive()` skips missing ones and boards render `NoSourceCard` instead of an error.
- Apple Health (iOS only, `src/api/health.ts`, `@kingstinct/react-native-healthkit`): daily summaries pushed to `/api/health/daily` and `/api/health/metrics`, raw sleep samples to `/api/health/sleep` (every sync; all metrics at most hourly unless `full`); reproductive-health types are excluded and never requested. Derived metrics (recovery, energy balance, fitness trend) are computed on the server. Staged and unstaged sleep both count as asleep: after the wake-up alarm the watch stops staging, so a second sleep only shows up as "asleep (unspecified)".
- Wake-up (`/api/health/wake`, store key `wake`): every return to the foreground re-syncs health if the last sync is over 5 minutes old, then posts a `foreground` signal to `/api/health/signal` (web too). The server counts you as up once there is activity 30+ minutes after the last sleep segment; until then Today shows `WakeCard` with an "I'm up" button (`imUp`, signal `up`), only between 05:30 and 13:00 and only before that day's sleep report card exists.
- Attachments and voice input: `POST /api/chat/upload` (10 files × 30 MB per message), `POST /api/chat/transcribe`. Tapping an attachment in a chat opens `FilePreview` (`src/screens/FilePreviewScreen.tsx`, a full-screen modal; params `items` + `index`, or `file` = attachment ids, also as the web debug link `?screen=FilePreview&file=<id>`): the message's attachments page sideways (arrows / ← → on web); images load `?preview=1` over the cached thumbnail and pinch-zoom on iOS (ScrollView zoom); everything else asks `GET /api/files/{id}/preview` (`src/api/files.ts`) and draws the `view`: `pages` = server-rendered page JPEGs, only the pages near the screen mounted (the binary has no WebView), `doc` = Markdown and `TableBlock` blocks in a FlatList, `text`, `audio` (expo-audio, pauses when paged away), `video` (web only; the phone gets Open in the browser), `none`. Open in the browser adds `inline=1`. A 404 on the preview route (old server) shows a note instead.
- Push: `/api/push/register`; the payload's `data.target` (`thread` / `card` / `inbox` / `today`, falling back to `data.thread` on old servers) says where a tap goes, and the `inbox` category's 同意 button approves without opening the card.
- Inbox (things waiting for your OK): `GET /api/inbox?status=pending|recent`, `GET /api/inbox?thread=<id>` (shown in the chat under the message with id `db<messageId>`), `POST /api/inbox/{id}` `{action}`. Cards render through `src/components/InboxCard.tsx` on Today and in chat; a decision turns the card into a one-line receipt in both places. "Want changes" opens the thread with a quote, and the next message is sent with `inboxId`. Tapping a receipt or a row in Handled (`InboxScreen`) opens the detail sheet (`useInboxDetail`: status, result, what you said when following up, why, changes, details, times); **Follow up** opens the thread with a `follow` quote (sent as the same `inboxId`; the server reopens done / failed items and gives the model the item's context), and **See the chat** opens `HistoryDay` at the item's `day`, focused on `db<messageId>`. When `/api/inbox` 404s the app falls back to `/api/approvals`.
- Chat cards: `GET /api/chat/cards?thread=` returns the thread's handoff cards (the main chat asked an Agent) and task cards (a background task this reply started). They hang on the reply `db<messageId>`: handoffs above its text, tasks below it (`placeCards` in `ChatView.tsx`). While a reply is running they arrive on the chat stream as `event: card` and sit in the in-flight bubble; the store keeps them in `liveCards` until the reply ends and `cardsByThread` is re-read. Components: `src/components/ChatCards.tsx`. "Revise" on a task card puts a `taskId` quote in the composer, and the note goes to `/api/tasks/{id}/revise` (the sub-session), not into the chat. The Agent-side "主对话转来" line is a chip back to the asking reply (`incoming`). The focused thread re-reads its cards every 6 s while any is running. When `/api/chat/cards` 404s there are no cards.
- Schedule and "To remember" (`../server/schedule.py`, store keys `schedule` / `remember`, components in `src/components/Schedule.tsx`): Today shows the merged timeline (`GET /api/schedule`; tap a class to skip it / move its place / add a note, tap your own or an Agent's item to edit it, deadlines have a tick; past days record what actually happened) and one "To remember" card (`GET /api/remember`, grouped; later / no date / email updates start folded; ticking goes to `/api/remember/done`, ticking again undoes). The old `reminder` and `mail_digest` feed cards are hidden. An Agent's change shows in its reply as a `schedule` chat card with Undo (`ScheduleChip`, `store.undoScheduleCard`). "Wrong? Tell …" opens the main chat with a `ref` quote, sent as `ref` so the model knows which entry. Me → Schedule is the iPhone calendar subscription (`webcal://` + `/cal/<token>.ics`). When `/api/schedule` 404s the timeline falls back to the read-only `/api/calendar` and there is no "To remember".
- Board blocks (an Agent's own tables and dashboard, `../server/boards.py`): `GET /api/boards/{agent}` returns the config with every block's data already computed and formatted in the request's language; the app only draws the seven types in `src/components/blocks/` (stat, progress, chart, list, checklist, text, action) and never computes. Built-in dashboards hand their sections to `SectionedBoard` (`src/components/blocks/Sections.tsx`) as a map in default order (`{'diet.today': …, 'diet.next': …}`, section ids are `ANCHORS` in boards.py; add one there and here together): it orders them by the board's `sections`, hides hidden ones, puts the `Slot` for blocks attached after each section, and long-pressing a section opens move up / move down / hide. Agents without a built-in dashboard render `AllBlocks`. The board footer lists the Agent's reminders (`/api/alerts/{agent}`: pause, resume, delete), hidden blocks and sections, and the feature packs that fit (`/api/packs`, install = apply). Unknown block types show "needs a newer app" instead of failing. Your own edits (row sheet, checklist tick, row actions like 用掉 1 份, quick-add form) go straight to `/api/rows` and `/api/collections/{agent}/{name}/rows`; the undo strip reverts with `/api/boards/{agent}/revert`. Inbox cards of kind `block` preview the proposal from `/api/boards/proposal/{inboxId}`, kind `agent` the planned board from `/api/boards/plan/{inboxId}`, kind `push` the notification a reminder would send from `/api/alerts/proposal/{inboxId}` (all in `BoardPreview.tsx`; a 404 means no preview). Push target `board` opens an Agent's dashboard. When `/api/boards` 404s there are no blocks.
- Study desk (2026-09-30; server `../server/study.py` + `studyapp.py` + `courses.py`, API `src/api/study.ts`, board `src/components/StudyBoard.tsx`, screens `src/screens/StudyScreens.tsx` + `AddCourseScreen.tsx`): an Agent whose `dashboard` is `study` (New agent → Start from an example → Study sends `template: 'study'`) shows `StudyBoard` with sections `study.desk` / `study.courses` from `GET /api/study/home` (review count, next step, nearest deadlines, per-course progress). `StudyHome` lists the courses and their sessions (`/api/study/outline`; a session without a page opens a sheet: what's missing, or Generate when its materials are in). `StudySession` has the tabs path / self-test / cards / quiz / files / ask on `/api/study/unit` + `/api/study/generated`: self-test answers live on the server (`GET` / `PUT /api/study/self`, shared with the desktop `/study` page), Didn't get it / a wrong quiz answer / a missed card go to `/api/study/review/add`, files open in `FilePreview` through `Attachment.study` (`/api/study/file/preview`, `/api/study/file/page`), Ask streams `/api/study/ask`. `AddCourse` is the phone version of the desktop five-step wizard (`/api/study/courses/*`) with the study Agent's chat under it (sent with `study: "<course>|<step>"`, only this visit's messages shown). An Agent's course change arrives as a chat card of kind `course` (`CourseChip`: Undo / Redo via `/api/study/courses/{course}/undo/{changeId}`, Open the session). Schedule and remember entries with `study` open that course / session (`openTarget({type: 'study'})`), and Today has a Study row while something waits for review. The monitor button makes a one-time login link for the desktop page (`POST /api/study/login-link`) and copies it; web just opens `/study`. When `/api/study/home` 404s the board and the Today row stay empty.
- Projects (`../server/projects.py`, store keys `sideChats` + `projects`, components in `src/components/ProjectCard.tsx`): the sidebar's "Projects" section is the old side chats, each row showing its nearest deadline (`projectLine`). A project chat has `ProjectPanel` on top: collapsed to one line (next deadline + next steps left), expanded (at most half the screen, scrolls inside) to goal / deadlines / next steps / decided / progress / tasks; tap a row for its sheet, the ticks go through `updateProjectItem` (deadlines are schedule items, so Today and "To remember" follow). Archived projects show `SummaryCard` (a spinner while the summary is being written). An Agent's change shows in its reply as a `project` chat card (`ProjectChip`, undo via `store.undoProjectCard`; in another thread the card opens the project). Inbox cards of kind `project` preview the proposal from the item's `project` field and the receipt gets an Open link. Schedule and remember entries with `project` show a tappable project tag. When `/api/projects` 404s the app falls back to plain side chats.
- Nightly proposals (`../server/proposals.py`): after the nightly digest the main chat proposes "add a skill" or "create an Agent" as inbox cards of kind `skill` / `agent`. Their preview comes in the item's `skill` / `agent` field (`InboxProposalInfo`: the quotes it was based on, which Agents get the skill, the full skill text without frontmatter, the new Agent's purpose); `InboxCard`'s `ProposalPreview` shows up to three quotes and folds the full skill text, and kind `agent` still draws the planned board. Approving is done by the server (the skill is installed, or the Agent created); the card becomes a receipt with the result, or "didn't work" with the reason.
- Goals (`../server/goals.py`, store keys `goals` (with `goalsClosed`, `goalChanges`, `goalMetrics`, `goalsEditable`) and `weightTrend`, components in `src/components/Goals.tsx`, API in `src/api/goals.ts`): the Goals tab lists active goals by category (the stored values 健康 / 学业 / 职业 / 财务 are compared, only the labels are translated). Tap a goal for its sheet (edit / mark done / drop / go to board); "Add a goal" in the header opens the editor, which PATCHes only the fields that changed (`null` clears). Current values, progress (`progress`, `direction`, `state`) and staleness come from the server; the app never computes readings, and body fat is never derived. The weight trend (`GET /api/goals/trend?metric=weight`: the body source as the line, Apple Health as hollow dots, `TrendLine` in `charts.tsx` with the weight goal's range as a band) sits inside the weight goal's card, or as its own card under Health when there is no weight goal. Agent changes from the last 24 h (`recent`) show as an undo strip at the top (`/api/goals/undo/{log}`, "Got it" = `/api/goals/seen`); done and dropped goals fold at the bottom. Pull-to-refresh asks for `fresh=1`. When `/api/goals` has no `closed` (old server) the page is read-only; when `/api/goals/trend` 404s there is no weight chart.
- Memory tree (`../server/memtree.py`, store key `tree`, action `treeAction`, `src/screens/TreeScreen.tsx`): Me → Memory tree is the memory all the user's AI apps share. `GET /api/tree` gives branches in pre-order (`leaves` = directly on it, `total` = with its small branches), current leaves, the trunk (profile) count and counts by `origin`; a leaf rewritten by the weekly pruning has `source: prune` and its original app in `origin` (pills and "By source" use `origin`). `POST /api/tree/{id}` `{action: confirm | forget | move, branch?}` (the trunk's name hangs it straight on the trunk). ### Debugging

- Web supports deep links for screenshots: `?screen=Group&id=<id>&tab=board`, `?screen=今天`, `?drawer=1`, `?screen=ThinkTalk&id=tp-…`, `?screen=ThinkSearch&q=…`, `?screen=ThinkWrite&zen=1` (with focus time started through the API). `?say=hello` sends a real message after connecting, on the dev server only (`npm run web`); production builds ignore it so a link can never make the agent act.
- `npx expo lint` caches under `.expo/cache/eslint`; a stale `import/namespace` error survives fixing the imported file — delete the cache or run `npx eslint src`.
- Headless Chrome's minimum window width is 500px; screenshots at 390px show a false right-edge crop.
- The Expo ESLint config includes the React Compiler rules: don't write `ref.current` during render (update it in an effect), don't call `setState` synchronously inside an effect (adjust state during render by comparing with the previous value), and keep `Date.now()` out of component bodies.
